TokenThe unit a model reads and writes: a word, part of a word, or punctuation. English averages roughly four characters per token.
TokenizerThe fixed lookup that turns text into token ids and back. Most use byte-pair encoding (BPE): common character sequences become single tokens.
Embedding modelA model that turns a piece of text into one vector (a list of, say, 1,024 numbers) so that texts with similar meaning get nearby vectors.
Generative model (LLM)A model that, given a sequence of tokens, outputs a score for every possible next token. Run repeatedly, it writes text.
Context windowThe maximum number of tokens the model can take in one call: instructions, evidence, conversation and its own output so far.
LogitsThe raw scores for every token in the vocabulary at one step, before they are turned into probabilities.
PrefillThe model's first pass over the whole prompt, done in parallel. Sets the time to first token.
DecodeGenerating the answer one token at a time, each step feeding the new token back in.
KV cacheStored intermediate results (attention keys and values) for every token so far, so each decode step does not reprocess the prompt.
Tool callStructured output (a name and JSON arguments) asking your code to run a function. The model never runs anything itself.
EvalA repeatable measurement of whether the system's outputs are right, on a fixed set of inputs.
ServingRunning models for many users at once: batching requests on GPUs, queueing, rate limits.

AI engineering looks like a hundred separate topics: tokenizers, transformers, sampling, embeddings, vector databases, agents, evals, GPUs. It is really one path that every request travels, with each topic owning one hop. If you can follow a single request from the keyboard to the answer, naming what happens at each hop and roughly how long it takes and what it costs, every later topic has a place to hang, and most interview questions become "which hop is this about?".

The questions this page prepares you for:

  1. Walk me through what happens when a user sends a message to an LLM application.
  2. Where does the time go, and where does the money go?
  3. What does the model know by itself, and what must the application give it?
  4. An answer is wrong, slow or expensive: which part would you change?

The running example is one request to the course's capstone, an internal support assistant. A support agent types:

"Can an enterprise customer on annual billing get a partial refund after a mid-term downgrade?"

We follow it through nine hops. Where a hop runs on a hosted API whose internals are private, we use a public open model of known shape (8 billion parameters, 32 layers) on one H100 GPU to show the mechanism with real arithmetic. Every number is computed in the code at the end.

Models do not read characters or words. The tokenizer splits the text into pieces from a fixed vocabulary (about 100,000 entries for the tokenizer used here; each model family has its own) and replaces each with its id. Our 93-character, 15-word question becomes 17 tokens: most words are one token each (" enterprise", " billing", " refund"), while "mid-term" splits into " mid" and "-term".

Why care about tokens? Because everything downstream is measured in them. The model's limit is a token count, prices are per token, and generation speed is tokens per second. Rare strings fragment: an invoice code like "INV-ADJ-CR" becomes six tokens with little meaning each, which is why exact codes are hard for meaning-based search (Step 2). Details in tokens, context and cost.

The generative model was trained on public text up to some date. It has never seen this company's refund policy. So before the model writes anything, the application must find the relevant policy passages and put them in front of it. That is retrieval, and it uses a different model.

An embedding model turns the question into a vector of 1,024 numbers. Every chunk of the company's 1,200 policy documents (about 40,000 chunks) was turned into a vector the same way when it was indexed. Texts with similar meaning point in similar directions, so the closest chunks by cosine similarity (the cosine of the angle between two vectors) are likely relevant. Comparing against all 40,000 by brute force is about 41 million multiply-adds, a few milliseconds; at millions of chunks an approximate index such as HNSW visits only a few thousand.

The capstone does more than that: it also runs keyword search (to catch exact terms), merges both rankings, and reranks the top 30 with a more precise model to keep the best 5. For our question it should return the enterprise refund policy and the downgrade billing rules. If it does not, nothing later can save the answer. That is why this is the hop teams measure first, and why the course spends a whole stage on it, starting with embeddings and the RAG pipeline.

So an LLM application has two engines: an embedding model that finds things, and a generative model that writes. Everything else is plumbing around them.

The model sees only one thing: the token sequence the application sends. For our request the application assembles about 3,500 tokens:

PartTokensPurpose
System instructions and output format~1,200"answer only from the sources, cite each claim, say INSUFFICIENT_EVIDENCE if they don't cover it"
Five retrieved chunks, numbered~2,000the evidence
Conversation so far and the question~300what to answer

This is the whole of what the model "knows" about the request. It has no memory of earlier calls and no access to the database unless the application puts results into this text. Instructions matter (prompt anatomy), but the most important tokens here are the evidence: a perfectly worded prompt with the wrong five chunks produces a confident wrong answer.

Inside the model, each of the 3,500 token ids is replaced by a learned vector, and the vectors pass through 32 identical layers. In each layer, attention lets every token gather information from the tokens before it (this is how "it" gets linked to "refund", and the question to the evidence), and a feed-forward block transforms each token's vector. The output for the last position is a score for every token in the vocabulary. How these layers work is in transformers.

Processing the prompt costs about 2 floating-point operations per parameter per token:

\[ 2 \times 8.03 \times 10^{9} \times 3{,}500 \approx 5.6 \times 10^{13}\ \text{FLOPs} \]

An H100 peaks near 989 trillion operations per second on this kind of work; at a realistic 40% of that, prefill takes about 0.14 s. All prompt tokens are processed in parallel, which is why prefill is fast per token.

Prefill also leaves behind the KV cache: for each layer and token, the attention keys and values, so they never need recomputing. For this model shape (32 layers, 8 key-value heads of 128 numbers, 2 bytes each, for both keys and values) that is 128 KiB per token, 437.5 MiB for our prompt. It is the reason long contexts and many simultaneous users compete for GPU memory.

The model's output is not text but one score per entry in its vocabulary: about 128,000 scores for the 8B example model. Say the top candidates for the first answer token are "Yes" (3.1), "Enterprise" (2.2), "No" (1.0) and "It" (0.4). Softmax turns scores into probabilities: at temperature 1 they are 0.626, 0.255, 0.077 and 0.042. The capstone answers policy questions at temperature 0.2, which divides the scores by 0.2 before softmax and sharpens the distribution: "Yes" becomes 0.989.

Which token is chosen is a decision made outside the model, by the sampler, and it is yours: low temperature for factual answers, higher for brainstorming, constrained decoding when the output must be valid JSON. This one hop explains why the same model can be repetitive or creative and why "temperature 0" is still not perfectly repeatable. See decoding.

The chosen token is appended, the model runs again on just that one new token (attending to everything earlier through the KV cache), picks the next, and so on until it emits an end token or hits the length limit. Our answer is about 250 tokens: "Yes, as a prorated account credit for the unused term [1], provided the downgrade is…", each claim with a citation number pointing at one of the five chunks.

Each decode step does little arithmetic (about 16 billion operations) but must read every one of the model's 16 GB of weights from GPU memory. At 3.35 TB/s of memory bandwidth, that takes about 4.8 ms per token, so 250 tokens take about 1.2 s for a single request: generation is limited by memory bandwidth, not compute. Hosted mid-tier models are larger and shared between many users; the capstone's budget assumes about 80 tokens per second, so the answer streams for about 3 s. That is why output length is the biggest latency lever and why tokens appear one by one. Mechanics in inference internals.

Our question needed only documents. Had the agent typed "ORD-114532 was charged twice, sort it out", the first hop after the gateway (a small router model that classifies each request) would have sent it down the agent path instead. There the model receives tool definitions as part of the prompt and, instead of answering, outputs a structured request:

{"type": "tool_use", "name": "get_charges", "input": {"order_id": "ORD-114532"}}

The application validates it, runs the real function, appends the result to the conversation and calls the model again. That loop, model proposes and code executes, repeated until the model answers or a budget runs out, is the entire idea of an agent. Every loop re-sends the growing conversation, so cost grows faster than the number of steps, and every write action needs checks the model cannot override. See what an agent is and tool calling.

Before the answer reaches the screen, plain code checks it: every citation number refers to a supplied chunk, and policy claims carry citations. If the model said INSUFFICIENT_EVIDENCE, the question goes to a human with the retrieved chunks attached. Every step (router verdict, retrieved chunk ids, token counts, latencies, the answer) is written to a trace.

After the fact, this request might be one of the questions in the offline eval set, where its answer is graded for correctness and groundedness every time a prompt, model or index changes. In production, a sample of answers is graded by a calibrated judge model, and thumbs-down and edits from the support agent feed a weekly review. Evals are what turn "it seemed fine when I tried it" into a number that can block a bad release. See evals and observability.

Our request did not run alone. At peak, 15 others were in flight. The model provider batches many users' decode steps together, so each read of the weights serves dozens of requests; that is how hosted models are affordable. The application's own limits are the provider's tokens-per-minute quota and its rate limiter, not its CPUs. See serving.

This script reproduces the numbers above. It needs numpy and the tiktoken tokenizer package (which downloads its vocabulary file on first use).

import numpy as np
import tiktoken                       # OpenAI's BPE tokenizer; downloads its table once

question = ("Can an enterprise customer on annual billing get a partial "
            "refund after a mid-term downgrade?")
enc = tiktoken.get_encoding("cl100k_base")
ids = enc.encode(question)
print("hop 1  tokens:", len(ids), [enc.decode([i]) for i in ids][-5:])

# hop 2: retrieval scores are cosine similarities between unit vectors
rng = np.random.default_rng(0)
chunks = rng.standard_normal((40_000, 1024)).astype(np.float32)
chunks /= np.linalg.norm(chunks, axis=1, keepdims=True)
q = chunks[123] + 0.03 * rng.standard_normal(1024).astype(np.float32)  # a query near chunk 123
q /= np.linalg.norm(q)
sims = chunks @ q
top5 = np.argsort(-sims)[:5]
print("hop 2  %d multiply-adds; top hit chunk %d at cosine %.2f, runner-up %.2f"
      % (chunks.size, top5[0], sims[top5[0]], sims[top5[1]]))

# hop 4: prefill compute and KV cache for an 8B, 32-layer, 8-KV-head model in bf16
params, prompt = 8.03e9, 3500
flops = 2 * params * prompt
print("hop 4  prefill %.1e FLOPs = %.2f s on one H100 at 40%% utilisation"
      % (flops, flops / (0.4 * 989e12)))
kv_per_token = 2 * 32 * 8 * 128 * 2
print("       KV cache %.1f MiB for the prompt" % (kv_per_token * prompt / 2**20))

# hop 5: logits to probabilities for the first answer token
logits = np.array([3.1, 2.2, 1.0, 0.4])            # "Yes", "Enterprise", "No", "It"
for T in (1.0, 0.2):
    p = np.exp(logits / T - (logits / T).max()); p /= p.sum()
    print("hop 5  T=%.1f -> %s" % (T, np.round(p, 3)))

# hop 6: decoding is bandwidth-bound: read all weights for every token
weight_bytes, bandwidth = 16.06e9, 3.35e12
print("hop 6  %.1f ms per token, %.1f s for 250 tokens at batch 1"
      % (1e3 * weight_bytes / bandwidth, 250 * weight_bytes / bandwidth))

# hop 9: what the request cost on a hosted API (illustrative prices)
router = 400 * 0.25e-6 + 30 * 1.25e-6
answer = 3500 * 3e-6 + 250 * 15e-6
print("hop 9  $%.4f = router $%.4f + answer $%.4f + retrieval $0.0004"
      % (router + answer + 0.0004, router, answer))

It prints 17 tokens ending in " mid", "-term", " downgrade", "?"; the brute-force search finding the planted chunk (random vectors are nearly orthogonal, so the runner-up scores low; real embeddings sit closer together); 5.6e13 FLOPs and 0.14 s; 437.5 MiB of KV cache; the two probability rows; 4.8 ms per token and 1.2 s for 250 tokens; and $0.0148 for the request.

  • "The model knows our data." It knows its training data. Company facts reach it only as tokens in the prompt, which retrieval or tools put there.
  • "The model remembers the conversation." Each call is independent; the application re-sends the history every time.
  • "Words are the unit." Tokens are. Limits, prices and speeds are all per token, and rare strings cost several.
  • "The model runs the tools." It writes a request; your code decides whether and how to run it.
  • "Generation is slow because the maths is heavy." Each token needs little arithmetic; it is slow because all the weights are read from memory for every token.
  • "A better prompt fixes wrong answers." Most wrong answers in grounded systems start at retrieval: the right passage never arrived.
  • "Temperature is a creativity dial inside the model." It is applied outside the model, to its scores, when choosing a token.
Name the two engines of an LLM application and what each contributes to our request.
The embedding model turns the question into a vector to find the five relevant policy chunks; the generative model reads the assembled prompt and writes the cited answer.
The prompt grows from 3,500 to 7,000 tokens. Using the 8B example, what happens to prefill compute and KV cache?
Both double: about \(1.1 \times 10^{14}\) FLOPs (about 0.28 s at 40% of an H100) and about 875 MiB of KV cache. Cost per call roughly doubles on the input side too.
Answers are about 250 tokens and take 3.1 s to stream. Product wants every answer to finish streaming within 2 s of its first token. What is the most direct lever?
Shorter answers: at about 80 tokens per second, 2 s of streaming is about 160 tokens, so ask for concise answers and set max_tokens near that, or use a faster model.
Why does the model's own knowledge not answer "partial refund after a mid-term downgrade" for this company?
The policy is private and changes over time; it was never in the training data, and even if similar text were, the model cannot know this company's current rule. It must come from retrieved documents in the prompt.
A single decode step for the 8B model does about 16 billion operations and reads 16 GB. Is it compute-bound or memory-bound on an H100, and why?
Memory-bound: about 1 operation per byte, while the H100 can do about 295 operations per byte of bandwidth before compute becomes the limit. The weights take about 4.8 ms to read; the arithmetic would take a fraction of that.
The answer is wrong and cites chunk [2], which turns out to be an old version of the policy. Which hop failed, and what fixes it?
Retrieval and indexing: a withdrawn or outdated document is still in the index. Ingestion must delete or replace chunks when documents change, and the eval set should include a question that catches stale policy.
