Control flowThe decision about which step runs next and when the whole process stops. Who owns it is the line between a workflow and an agent.
AgentA system in which a language model chooses the next action, sees its result, and repeats until it decides the task is done (or a budget stops it).
WorkflowA system where code fixes the sequence of steps and the model only fills in parts of them, such as a classification or a draft.
Augmented LLMOne model call given extra powers, such as retrieved documents or one round of tool use, but no loop.
ToolA function the model may ask your code to run, described to it by a name, a description and an argument schema.
EnvironmentEverything outside the model that the agent observes and changes: databases, APIs, files, a browser, the user.
ObservationWhat comes back from the environment after an action: a tool result, an error, a user reply.
Action spaceThe full set of things the agent may do at a step: each tool with its allowed arguments, plus "answer and stop".
PolicyThe rule that maps what the agent has seen so far to its next action. In an LLM agent, the policy is the model plus its prompt.
TrajectoryThe full record of one run: every model output, action, observation and the final answer, in order.
AutonomyHow many decisions the system makes without a human or fixed code making them: which step, which tool, when to stop, whether to act on the world.
AgenticAn adjective for degree, not a category: a system is more agentic the more of its control flow the model decides.

"Agent" is the most overloaded word in AI engineering. Vendors call a chatbot with a search box an agent; researchers mean a model that runs for hours on its own. An interviewer is not asking for a definition you memorised. They want to know whether you can tell, for a given product, how much of the decision-making to hand to the model, and what that costs.

The questions you will be asked, in some form:

  1. What makes something an agent rather than an LLM application with a few calls in it?
  2. When would you build a workflow instead of an agent, and how would you decide with numbers?
  3. Why do agents fail more than single calls, and what does that do to cost and latency?
  4. What are the main ways to structure an agent, and when is each one right?

The running example. An online shop gets this support message:

"I think I was charged twice for order ORD-482913. Can you sort it out?"

The shop has three internal functions: get_order(order_id), get_charges(order_id) and refund(order_id, charge_id, amount). The truth, which nobody knows yet, is that the order cost $59.99 and the card was charged twice. We will build the assistant four ways, from a single model call up to a full agent, and measure each one. By the end you should be able to say exactly which of the four is an agent, and which one you would ship.

Start with the simplest design: send the message to a model with the refund policy in the system prompt, and return its reply. The model can be polite, restate the policy and ask for details. What it cannot do is find out whether the customer was charged twice, because the charges live in a payments database. A model call is a function from input text to output text: it cannot read anything that is not in its input, and it cannot change anything in the world (see what an LLM is). Two capabilities are missing: seeing facts in your systems, and doing things such as issuing a refund.

The next design, the augmented LLM, adds seeing. Either code looks up the order and charges and pastes them into the prompt, or the model is shown the tools and gets one round to request some. Now it can say "I can see two charges of $59.99". It is still one decision: if it needs a fact that only becomes knowable after the first result (the charge IDs, which it needs before it can refund), one round cannot get there.

For many products this is the right design. A documentation bot is an augmented LLM: retrieve, then answer. Nothing loops, so cost and latency are predictable. Climb above this rung only with a reason.

To actually resolve the duplicate charge, several steps must happen in order: fetch the order, fetch the charges, decide whether the second charge is a duplicate, refund it, tell the customer. A workflow writes that order down in code:

message ──► get_order ──► get_charges ──► LLM: "duplicate?" ──yes──► refund ──► LLM: write reply
                                               │
                                               └──no──► escalate to a human

The model is used twice: once as a classifier and once as a writer. Code decides everything else: which function runs first, what the branch condition is, and when the process ends. If the model's answer to "duplicate?" is wrong, the damage is limited to the branches you drew.

Workflows come in a few recurring shapes worth naming:

ShapeWhat code fixesFits when
Prompt chainingA fixed sequence of model calls, each consuming the last one's output, with checks between themA task splits cleanly into known stages (extract, then draft, then translate)
RoutingA classifier call picks one of several fixed pathsRequests fall into distinct types that need different handling
ParallelisationSeveral calls run at once on parts of the input, or on the same input for a voteIndependent sub-parts, or you want several opinions
Orchestrator-workersOne call splits the task into sub-tasks at runtime; workers run them; a final call mergesThe sub-tasks cannot be known in advance but each is simple
Evaluator-optimiserOne call drafts, another critiques, loop until the critic passes or a limit hitsClear quality criteria and iteration measurably helps

The last two already hand a little control to the model: the orchestrator decides how many sub-tasks exist, the evaluator decides when to stop. That is the first hint that "workflow versus agent" is a spectrum, not a switch.

Measure design 3 on our request. It makes two model calls. With a 1,000-token classification prompt (instructions, order and charges) returning about 30 tokens, and an 800-token reply prompt returning about 150 tokens, it uses 1,800 input and 180 output tokens. At an illustrative price of $3 per million input tokens and $15 per million output tokens, that is:

\[ 1800 \times \tfrac{3}{10^6} + 180 \times \tfrac{15}{10^6} = 0.0054 + 0.0027 = \$0.0081 \]

Under a cent, two model calls, and a latency you can predict to within a second.

Now remove the diagram. Give the model the three tools and a goal, and let it decide what to do, one step at a time:

            ┌───────────────────────────────────────────────┐
goal ──────►│ model reads everything so far                 │
            │   │                                           │
            │   ├── chooses a tool + arguments ──► your code runs it
            │   │                                     │     │
            │   │◄──────── observation (result) ──────┘     │
            │   │                                           │
            │   └── chooses "answer and stop" ──────────────┼──► reply
            └───────────────────────────────────────────────┘
                 (your code stops it anyway after N steps)

A run on our request looks like this:

  1. Model: call get_order("ORD-482913"). Observation: total $59.99, delivered.
  2. Model: call get_charges("ORD-482913"). Observation: two charges, ch_1 and ch_2, both $59.99.
  3. Model: call refund("ORD-482913", "ch_2", 59.99). Observation: ok.
  4. Model: answer "I found two charges of $59.99 and refunded the second one." Stop.

The tool calls are the same ones the workflow made. What changed is who decided. Nothing in the code says "fetch charges after the order" or "refund the later charge". The model chose each step after reading the previous observation, and it chose when to stop. That is the definition this course uses:

An agent is a system in which the model decides the control flow: which action to take next, with what arguments, and when the task is finished. It does this in a loop of observe, decide, act, against an environment it can read and change.

Three consequences follow directly from the definition:

  • The number of steps is not known in advance. If the customer had typed the wrong order number, the agent might call get_order, see "not found", and ask the customer, a path nobody drew. The same code might take 2 steps on one request and 9 on another.
  • The model sees its own results. Each decision is conditioned on the observations so far. That is what lets it recover from an error or change plan, and what lets errors accumulate.
  • The loop still belongs to you. Your code runs the tools, enforces a step limit, checks permissions and decides what the model is allowed to see. The model proposes; the runtime disposes. The details are in the agent loop.

The useful one-line test, then, is not "does it use tools?" (the augmented LLM does) or "does it make several calls?" (the workflow does). It is: if you read the code, can you predict the sequence of steps? If yes, it is a workflow. If the sequence is only knowable by running it, it is an agent.

The words agent, environment, observation, action and policy come from reinforcement learning, and the mapping is exact:

RL termIn an LLM agentIn the running example
EnvironmentThe systems the tools touch, plus the userThe orders and payments databases
ObservationA tool result, an error message, a user reply"two charges, ch_1 and ch_2, $59.99"
Action spaceThe tool list with argument schemas, plus "answer"get_order, get_charges, refund, answer

Two lessons fall out. The action space is a design decision: an agent can never do what its tools do not allow, and can always attempt what they do allow. A generic run_sql(query) instead of get_charges(order_id) turns three narrow actions into every possible query, including DELETE. And the state is only what you put in the context window: the model has no memory between calls, so a fact not in the messages cannot influence the policy. That is why memory and context engineering is a core agent skill.

Each row hands one more decision to the model, so "agentic" is a matter of degree. You will hear AI agent for one concrete system of the design-4 kind (a support agent, a coding agent) and agentic AI for the broader style where models plan, act and coordinate, often several agents with memory and long-running goals. The difference is scope. In an interview, say what is delegated: "the model picks tools and decides when to stop; code owns the budget, the permissions and the approval step for refunds." That sentence is worth more than any definition.

Each model decision has some chance of being wrong: the wrong tool, a wrong argument, a misread result, stopping too early. Suppose each step is right with probability \(p\), independently, and a run needs \(n\) steps to all be right. Then the run succeeds with probability:

\[ P(\text{success}) = p^{\,n} \]
Per-step accuracy \(p\)3 steps5 steps10 steps20 steps

A step accuracy of 95% sounds excellent, yet a 10-step task then fails 4 times in 10. This is the single most important number in agent design, and it explains several things practitioners do:

  • They shorten trajectories: one tool that returns the order with its charges removes a step.
  • They move decisions that do not need judgement into code: if a refund always follows a confirmed duplicate, code can do it, and its accuracy is 1.
  • They add checks that catch a wrong step before the next one builds on it.

The formula is a pessimistic simplification. Real agents can notice an error ("order not found") and correct it, so steps are not independent and a wrong step is not always fatal. That self-correction is the reason to build an agent at all. But the direction is right: every extra model-made decision is another chance to fail, and long unattended runs fail more often than short ones.

A model has no memory between calls, so every step of the loop re-sends the whole conversation so far. Model the agent's run on our request with a 1,500-token system prompt plus tool definitions, a 50-token user message, and each step adding about 120 tokens of model output and 250 tokens of tool result:

Add 4 × 120 = 480 output tokens and the cost is \(8420 \times 3/10^6 + 480 \times 15/10^6 \approx \$0.032\): four times the workflow's $0.0081. Because each call carries everything before it, the total input tokens of a run grow with the square of the number of steps: call \(k\) sends \(1550 + 370(k-1)\) tokens, so \(n\) calls send \(1550n + 370\,n(n-1)/2\). The same agent at 8 steps sends 22,760 input tokens; at 16 steps, 69,200, about $0.24 a run. Prompt caching cuts the price of the repeated prefix but not the growth.

Latency adds up the same way, because steps are sequential: each one waits for the previous observation. With an illustrative 0.5 s to the first token and 80 output tokens per second, the workflow's two calls plus tools take about 3.5 s; the agent's four calls plus three tool calls take about 8.6 s. For a chat window that difference is noticeable; for a background job it does not matter. Latency targets therefore push towards workflows for interactive paths and allow agents for asynchronous ones.

If agents are less reliable, slower and more expensive, why build them? Because a workflow only handles the paths you drew. Real support traffic has a long tail: "charged twice but one is pending", "charged twice on two different cards", "charged once but my bank shows two holds", "refund went to an expired card". Each needs a different sequence of lookups. A workflow either grows a branch for each, or sends them to a human.

An agent with the same tools can handle many of these without new code, because it reads each observation and decides what to look up next. Whether that is worth it is an arithmetic question. Take 10,000 requests a day, a human handling cost of $4 per escalated ticket, a model cost of $0.0081 per request for the workflow (Step 2) and $0.035 per request for the agent (a little above Step 7's $0.032, because tail requests take more steps), and these illustrative accuracies. The router runs the workflow's classifier on every request and the agent only on the 22% the workflow does not cover.

Three lessons from the table. First, model cost is tiny next to the cost of failure; arguing about cents per call misses where the money is. Second, the hybrid wins: deterministic paths for the common, well-understood cases, the agent for the tail. Many production "agents" are shaped like this. Third, the table assumes every failure is detected and escalated. An agent that confidently refunds the wrong charge costs far more than $4. That is why the write action (refund) stays behind a policy check and, above a threshold, a human approval, however good the model is.

Once the model owns control flow, there are a few standard ways to organise its thinking. Each gets its own lesson; here is the map:

  • Tool-calling loop (ReAct style). One model, one loop: think, act, observe, repeat. The default, and what the running example used. Mechanics in the agent loop and tool calling.
  • Plan-and-execute. One call writes a plan of several steps; an executor carries them out, re-planning if something fails. Fewer expensive decisions, at the risk of a stale plan. See reasoning patterns.
  • Reflection. The agent, or a separate critic, reviews a draft or a failed attempt and tries again with the critique in context. Useful when correctness can be checked (code, tests).
  • Router plus specialists. A cheap classifier sends each request to a workflow or to a narrow agent with a small tool set. The hybrid from Step 8.
  • Multi-agent. Several model instances with separate contexts, coordinated by an orchestrator or by handoffs. Buys parallelism and context isolation at a large token cost. See multi-agent systems.

All of them share one core: a model that decides, tools that define what it can see and do, and a runtime that runs the loop and enforces limits.

A decision procedure you can say in an interview:

  1. Can one call with the right context do it? Then build an augmented LLM. Most Q&A, summarisation and extraction stops here.
  2. Can you write the steps down? If the path is the same for most inputs, build a workflow. Use routing for a few distinct request types.
  3. Is the path genuinely unknowable in advance, and is a wrong step recoverable or checkable? Only then build an agent, with a narrow tool set.
  4. Bound it. Step limit, token and money budget, timeouts, and human approval for irreversible writes.
  5. Measure it on a task set, run several times each, before and after any change. If an agent and a workflow score the same, ship the workflow.

Too much autonomy shows in traces: the agent takes the same 3 steps every time (write them as a workflow), or failures cluster on a decision code could make. Too little shows in the escalation queue: requests that needed one extra lookup, and a workflow that grows a branch every week.

This runs as-is. The model is replaced by plain Python functions so you can see exactly where the decisions live: in the workflow they are in workflow(), in the agent they are in policy(), which stands in for the LLM.

# Tools: the same three functions both designs can use.
ORDERS = {"ORD-482913": {"total": 59.99, "status": "delivered"}}
CHARGES = {"ORD-482913": [{"id": "ch_1", "amount": 59.99}, {"id": "ch_2", "amount": 59.99}]}
REFUNDS = []

def get_order(order_id):   return ORDERS.get(order_id, {"error": "ORDER_NOT_FOUND"})
def get_charges(order_id): return CHARGES.get(order_id, [])
def refund(order_id, charge_id, amount):
    REFUNDS.append((order_id, charge_id, amount))
    return {"ok": True, "refunded": amount}

TOOLS = {"get_order": get_order, "get_charges": get_charges, "refund": refund}

# --- Design 1: a workflow. Code owns the control flow; the model fills one blank.
def classify(order, charges):            # stands in for ONE LLM call
    return "duplicate" if len(charges) == 2 and charges[0]["amount"] == charges[1]["amount"] else "other"

def workflow(order_id):
    order, charges = get_order(order_id), get_charges(order_id)   # fixed step 1, 2
    if classify(order, charges) == "duplicate":                     # fixed branch
        return refund(order_id, charges[-1]["id"], charges[-1]["amount"])
    return {"escalate": True}

# --- Design 2: an agent. The model chooses the next action and when to stop.
def policy(history):                     # stands in for the LLM; reads everything so far
    seen = [h["tool"] for h in history if "tool" in h]
    if "get_order" not in seen:   return {"tool": "get_order", "args": {"order_id": "ORD-482913"}}
    if "get_charges" not in seen: return {"tool": "get_charges", "args": {"order_id": "ORD-482913"}}
    charges = next(h["result"] for h in history if h.get("tool") == "get_charges")
    if len(charges) == 2 and "refund" not in seen:
        c = charges[-1]
        return {"tool": "refund", "args": {"order_id": "ORD-482913", "charge_id": c["id"], "amount": c["amount"]}}
    return {"final": "Refunded the duplicate charge of $59.99."}

def agent(task, max_steps=6):
    history = [{"user": task}]
    for step in range(max_steps):          # the loop is ours; the choices are the model's
        action = policy(history)
        if "final" in action:
            return action["final"], step + 1
        result = TOOLS[action["tool"]](**action["args"])
        history.append({"tool": action["tool"], "args": action["args"], "result": result})
    return "stopped: step budget", max_steps

print(workflow("ORD-482913"))           # {'ok': True, 'refunded': 59.99}
REFUNDS.clear()
print(agent("I think I was charged twice for ORD-482913"))   # (..., 4) -> four policy calls
print(REFUNDS)                          # [('ORD-482913', 'ch_2', 59.99)]

Both refund ch_2. The difference is where you would look to change behaviour: in the workflow you edit workflow(); in the agent you can only change the policy's inputs (the prompt, the tool descriptions, the tools themselves) and the limits in agent(). Replace policy() with a real model call and you have the loop from the next lesson; the step count of 4 is the four model calls costed in Step 7.

  • "It calls tools, so it is an agent." A single call that uses a tool once is an augmented LLM. The test is whether the model decides the sequence of steps and when to stop.
  • "More autonomy is more advanced, so better." Each model-made decision is another chance to fail (\(p^n\)) and another full-context call. Use the least autonomy that solves the task.
  • "The model controls the agent." The model proposes actions; your runtime executes them, and owns the budget, permissions, approvals and what the model sees. Safety lives in the runtime, not the prompt.
  • "A 95%-accurate step is good enough." At 10 dependent steps that is about a 60% success rate. Shorten paths and move routine decisions into code.
  • Judging by model cost alone. In the Step 8 table, model cost was 1 to 7% of the total. Failures, escalations and wrong actions dominate.
  • Giving the agent broad tools for flexibility. A generic SQL or shell tool makes the action space everything the tool can do, including damage. Narrow, typed tools make agents safer and more accurate.
  • Arguing about "agent" versus "agentic". State which decisions the model makes and which code makes; that is the useful content.
A system retrieves five documents, then makes one model call to answer with citations. Is it an agent? What would make it one?
No: code fixes the steps (retrieve, then answer), so it is an augmented LLM. It becomes an agent when the model decides at runtime whether to search again, with what query, and when it has enough to answer, as in agentic RAG.
Each step of a 6-step agent task is right 97% of the time. Roughly what is the end-to-end success rate, and what are two ways to raise it?
\(0.97^6 \approx 0.833\), about 83%. Raise it by cutting steps (a combined tool, or moving fixed decisions into code) and by adding checks that catch a wrong step before the next one depends on it (validation, a verifier, approval on writes).
Using Step 7's model (1,550 input tokens on the first call, each step adding 370), how many input tokens does a 6-call run send in total?
The calls send 1,550, 1,920, 2,290, 2,660, 3,030 and 3,400 tokens, totalling 14,850. It grows with the square of the step count because each call re-sends everything before it.
What one question best separates a workflow from an agent when you read the code?
"Can I predict the sequence of steps from the code?" If yes, code owns control flow and it is a workflow. If the sequence is only knowable by running it, the model owns it and it is an agent.
Your support traffic is 85% three well-understood request types and 15% a varied tail. Escalation costs $4. What do you build and why?
A router: deterministic workflows for the three common types (cheap, fast, highly reliable) and a narrow agent for the tail, with escalation on failure. As in Step 8, the reduction in escalations on the tail is worth far more than the extra model cost, while the common cases keep workflow reliability.
Why is "the agent decides when to stop" not enough on its own, and what does the runtime add?
Models can loop, repeat a failing call, or never judge the task done. The runtime adds a hard step limit, token and money budgets, timeouts, and a fallback (partial answer or escalation) when any is hit.
A teammate proposes giving the support agent a single run_sql(query) tool "so it can answer anything". What is your response?
It enlarges the action space to every possible query, including writes and data the user should not see, and makes the model write correct SQL against your schema, which lowers per-step accuracy. Offer narrow, typed tools (get_order, get_charges) with access control in code; add new tools when traces show a real gap.
