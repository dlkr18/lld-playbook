StateThe one shared record a graph run reads and writes: a typed dict (or Pydantic model) such as messages, the order being refunded, an approval flag.
ChannelOne key of the state. Each channel has its own rule for how new values are merged in.
ReducerThe merge rule for a channel: a function of (old value, update). Default is "overwrite"; add_messages appends.
NodeA function that receives the current state and returns a partial update (only the keys it changes).
Edge / conditional edgeA fixed transition from one node to the next, or a router function that looks at the state and returns the name of the next node.
Super-stepOne tick of the runtime: run every node scheduled for this tick, merge all their updates, then decide which nodes run next.
CheckpointerThe storage backend (memory, SQLite, Postgres, ...) that saves a snapshot of the state after every super-step.
ThreadOne run's history of checkpoints, named by a thread_id you choose, typically a conversation or ticket ID.
InterruptA deliberate pause: the run stops, its state is saved, and it waits until someone resumes it with a value.
CommandAn object a node or caller can return or send to update state and choose where to go next, including Command(resume=...) to continue after an interrupt.
SendA way for a router to launch the same node many times in parallel with different inputs (map-reduce fan-out).
Recursion limitA cap on the number of super-steps per run, so a looping agent cannot run forever.

A chain runs each step once, in order. An agent does not: it calls a model, the model asks for a tool, the tool's result goes back to the model, and this repeats an unknown number of times. Real agents also need to stop and wait (for a human to approve a refund, for a webhook), survive a server restart mid-run, and let an engineer replay exactly what happened. LangGraph is a runtime for this: you describe the agent as a graph of nodes over a shared state, and it executes the graph step by step, saving the state after every step.

Interviewers ask:

  1. How is a LangGraph agent executed: what are state, reducers and super-steps, and why are they designed that way?
  2. How does checkpointing make a run durable and resumable, and what does that demand of your nodes?
  3. How do you put a human approval in the middle of an agent without holding a process open for hours?
  4. When is LangGraph the right tool, versus a plain loop, an LCEL chain or a workflow engine?

Running example: the electronics shop from LangChain now wants its assistant to act. A customer writes: "Refund order A1042, the headphones arrived broken." The agent must look up the order (a tool call), check the amount, and issue the refund. Shop policy: any refund over $100 needs a human reviewer's approval, which may take hours. Order A1042 is $149. We will build this as a graph, run it, crash it, pause it and resume it.

Write the refund agent as boxes and arrows before writing any code:

The agent node routes to lookup_order or issue_refund or ends the run; after a tool the graph always returns to the agent, and a refund over $100 pauses for human approval first.

Two kinds of thing appear. Nodes do work: the agent node calls the model, lookup_order and issue_refund run tools. Edges decide what runs next. Some edges are fixed (after a tool, always go back to the agent); one is conditional (after the agent, go to whichever tool it asked for, or end).

This is a state machine, and drawing it shows where control lives. In a "let the model decide everything" agent, the model's output alone picks the next action. In a graph, the model proposes and your router function disposes: it can refuse to route to issue_refund unless the order lookup has happened, enforce the $100 rule in code rather than in a prompt, and end the run if a budget is exceeded. Rules that must hold belong in edges, not in prompts.

All nodes read and write one state object, declared up front:

class RefundState(TypedDict):
    messages: Annotated[list, add_messages]   # reducer: append
    order: dict                               # default: overwrite
    approved: bool

A node does not return the whole state. It returns a partial update, only the keys it changed: lookup_order returns {"order": {...}, "messages": [tool_result]}. The runtime merges that update into the state using each key's reducer. For order the default reducer overwrites. For messages, add_messages appends the new messages to the list (and replaces a message if one with the same ID already exists, which is how you edit history).

Why partial updates and reducers, instead of letting each node mutate a shared dict? Three reasons:

  • Parallel nodes. If two nodes run in the same step and both add messages, appending both is well defined; two in-place mutations would race. When two parallel nodes write a key that has no reducer, LangGraph raises an error rather than guessing which one wins.
  • Checkpoints are cheap and exact. The runtime knows precisely what each step changed, so it can record it.
  • Nodes stay testable. A node is a pure-looking function from state to update: give it a state dict, assert on the dict it returns.

Design state to be small and explicit. Every value in it is saved at every step (Step 5) and much of it is sent to the model, so a state that accumulates raw tool outputs (whole web pages, whole order histories) gets expensive quickly.

Building the graph is three kinds of call on a builder: add_node(name, fn), add_edge(a, b) for fixed transitions, and add_conditional_edges(a, router) where router(state) returns the next node's name (or END). Special names START and END mark the entry and the exit. Then compile() validates the structure (for example, that every edge points at a real node) and returns a Runnable, so it has invoke, stream and batch like any LangChain step.

The router for the refund agent reads the last message: if the model asked for lookup_order, go there; if it asked to refund and an order is loaded, go to issue_refund; otherwise end. The router is ordinary Python, so it is where you put the guarantees: "never refund without a loaded order", "end after 8 model calls". A model can be talked into ignoring a prompt rule; it cannot be talked out of an if statement.

Prebuilt helpers exist (a ready-made tool-executing node and a ready-made ReAct agent graph) and are worth using for the plain tool loop. Write your own nodes when the business rules are the point, as here.

LangGraph's runtime is modelled on Pregel, a graph-processing design from Google: computation proceeds in synchronised rounds. Each round is a super-step:

  1. Run every node that was triggered for this step. Several can run at once.
  2. Collect all their partial updates and apply them to the state through the reducers. Nodes in the same step never see each other's updates.
  3. Follow the edges out of the nodes that ran to decide which nodes are triggered next.
  4. Save a checkpoint. If nothing is triggered, the run is finished.

The refund run, step by step:

Super-stepNodeUpdate returnedNext
1agentmessage: "call lookup_order(A1042)"lookup_order
2lookup_orderorder = {A1042, $149}; message: tool resultagent
3agentmessage: "refund of $149 needs approval"issue_refund (but interrupted first)
4issue_refundrefunded = true; message: "refund R-77 created"agent
5agentmessage: "refund of $149 issued"END

The synchronised rounds give a deterministic order for merging, which makes runs reproducible from their checkpoints even when nodes run in parallel. They also give a natural place to count: a recursion limit caps the number of super-steps per run, and hitting it raises an error. That is the backstop for an agent stuck calling the same tool forever; set it deliberately rather than relying on the default.

Compile the graph with a checkpointer and invoke it with a thread ID:

graph = builder.compile(checkpointer=PostgresSaver(conn))
graph.invoke({"messages": [user_msg]}, {"configurable": {"thread_id": "ticket-8812"}})

After every super-step the checkpointer saves a checkpoint: the state's channel values, which nodes are due next, and metadata (step number, parent checkpoint). Checkpoints for one thread_id form that thread's history. Invoking again with the same thread ID loads the latest checkpoint and continues from there, which is how a multi-turn conversation keeps its history without your API servers holding anything in memory. Any server can serve the next request.

Durability is the second payoff. Suppose the process dies during super-step 4, after issue_refund has called the payment API but before the checkpoint is written. On restart, the run resumes from the last saved checkpoint (end of step 3) and runs issue_refund again. The checkpointer records completed steps, not half-finished side effects. So:

Nodes with side effects must be idempotent. Pass an idempotency key derived from the state (for example "A1042-refund") to the payment API, so a replayed call returns the original refund instead of paying twice. This is the same rule as any at-least-once system; see Reliability engineering.

Storage has a cost you should estimate. If a refund thread averages 6 checkpoints of about 10 KB each and the shop handles 20,000 such threads a day, full snapshots come to about \(6 \times 10\ \text{KB} \times 20{,}000 = 1.2\) GB a day. Implementations reduce this by writing only channels that changed, but you still need a retention policy (delete or archive threads after, say, 30 days) and you should keep bulky data (documents, images) out of the state, storing a reference instead.

The $100 rule needs a person. The naive approach (block the request handler until a reviewer clicks approve) ties up a worker for hours and loses everything on a deploy. With checkpoints, a pause costs nothing:

  1. The run reaches the point that needs approval and interrupts. The state, including which node is due next, is already checkpointed. invoke returns to your API, which shows the reviewer the pending refund.
  2. No process is waiting. The thread is just rows in Postgres.
  3. Hours later, the reviewer clicks approve. Your API calls graph.invoke(Command(resume=True), config) with the same thread ID. The runtime loads the checkpoint and continues, passing True to the waiting point.

There are two ways to declare the pause. A static one, interrupt_before=["issue_refund"] at compile time, stops before that node every time. A dynamic one calls interrupt(payload) inside a node, which pauses only when your code decides to (only for refunds over $100) and sends a payload to show the reviewer. The resume value becomes the return value of interrupt(...).

One mechanism detail catches people: when a run resumes after a dynamic interrupt, the node that called interrupt starts again from its first line, and this time interrupt returns the resume value instead of pausing. Any code before the interrupt call runs twice. Put side effects after the interrupt, or in a separate node.

The same machinery supports editing: update_state(config, values) writes a correction into the thread (the reviewer changes the refund amount to $120), and the run continues from the edited state.

Because every super-step is a saved checkpoint, a thread's history is a list you can read: get_state_history(config) returns each checkpoint with its state and next nodes. Two uses:

  • Debugging. A customer complains the agent refunded the wrong order. Read the thread: you see the exact message list the model had at step 3 and the exact tool result at step 2, not a reconstruction from logs.
  • Forking. Invoke with a config naming an earlier checkpoint_id and the run continues from that point as a new branch, leaving the original history intact. Engineers use it to test "what would the agent have done with the fixed prompt from this exact state?"

Replaying is deterministic in the graph's control flow, not in the model: re-running a model node calls the model again and may produce different text. To reproduce exactly, read the saved outputs rather than regenerating them.

An agent run can take 10 to 60 seconds, so users need to see progress. graph.stream(input, config, stream_mode=...) offers several views of the same run:

  • "updates": after each super-step, which node ran and what it returned. Good for a progress line ("Looking up order A1042...").
  • "values": the full state after each step. Good for debugging, heavy for a UI.
  • "messages": model tokens as they are generated, from inside whichever node is calling the model. Good for typing the final answer out.
  • "custom": anything your node chooses to emit, such as "fetched 3 of 10 pages".

Modes can be combined. The typical chat UI uses updates for status and messages for the answer text.

Nodes that are triggered in the same super-step run in parallel. If after the order lookup you want to check the fraud score and the warranty status at the same time, give lookup_order two outgoing edges; both nodes run in the next super-step and their updates are merged by the reducers. A node that both point to runs once, in the step after both finish; to join branches of different lengths, declare one edge from the list of branch nodes to the join node.

When the number of parallel tasks is only known at run time (one check per item in a five-item order), a router returns a list of Send objects, Send("check_item", {"item": x}), one per item. The runtime runs the node once per Send in the same super-step, each with its own input, and a reducer on the results key collects them. This is map-reduce inside an agent.

Subgraphs are compiled graphs used as nodes in a bigger graph, for example a "refund" subgraph and a "shipping question" subgraph behind one router. They keep large agents modular and are how multi-agent designs are usually built in LangGraph: each agent is a subgraph, and edges or a supervisor node decide who acts next. See Multi-agent systems for when that is worth it.

The graph runtime itself is cheap. The cost of an agent is model calls, and the loop makes them grow faster than you might expect, because each call re-sends the whole message history. Suppose the system prompt and tool definitions are 1,500 tokens, the user message is 30, and each iteration adds about 300 tokens (the model's tool request plus the tool result). Input tokens for call \(i\) (starting at 0) are \(1{,}530 + 300\,i\), so over \(n\) calls:

\[ \text{total input} = \sum_{i=0}^{n-1} (1{,}530 + 300\,i) = 1{,}530\,n + 150\,n(n-1) \]
  • The refund run makes 3 model calls: 5,490 input tokens.
  • A 10-call run: 28,800 tokens, nearly double the 15,300 it would be if history did not grow.
  • A 20-call run: 87,600 tokens, almost three times 30,600.

The quadratic term is why long-running agents need context management: summarise or drop old tool outputs, keep bulky results in state but out of the messages, and use provider prompt caching for the fixed prefix. Latency adds up the same way: 5 super-steps with a model call of about 1.5 s and tools of about 0.3 s each is roughly 5 s before any human wait. See Memory and context and Cost and latency.

LangGraph is not installed in every environment, so first a 40-line model of its runtime: partial updates merged by reducers, one checkpoint per step, a recursion limit, a static interrupt, and resume from storage. It runs as is.

import copy, json

def append(old, new):            # reducer for the message list
    return old + new

class Graph:
    """A toy of LangGraph's runtime: reducers, super-steps, checkpoints, interrupts."""
    def __init__(self, reducers):
        self.reducers, self.nodes, self.edges = reducers, {}, {}
    def node(self, name, fn, then):           # then: a node name, or a router function
        self.nodes[name], self.edges[name] = fn, then
    def run(self, store, thread, state=None, start="agent", interrupt_before=(), resume=None):
        if resume is not None:                # pick up exactly where the checkpoint left off
            state, nxt = copy.deepcopy(store[thread][-1])
            state["approved"] = resume
        else:
            nxt = start
        steps = 0
        while nxt != "END":
            if nxt in interrupt_before and resume is None:
                store.setdefault(thread, []).append((copy.deepcopy(state), nxt))
                return state, f"paused before {nxt}"
            resume = None
            update = self.nodes[nxt](state)                    # a node returns a partial update
            for k, v in update.items():                        # reducers merge it into the state
                state[k] = self.reducers.get(k, lambda o, n: n)(state.get(k), v)
            then = self.edges[nxt]
            nxt = then(state) if callable(then) else then
            store.setdefault(thread, []).append((copy.deepcopy(state), nxt))  # checkpoint
            steps += 1
            if steps > 25:
                raise RuntimeError("recursion limit")
        return state, "done"

# --- the refund agent: a scripted "model" so the run is reproducible ---
def agent(s):
    if "order" not in s:
        return {"messages": ["AI: call lookup_order(A1042)"]}
    return {"messages": [f"AI: refund of ${s['order']['amount']} {'issued' if s.get('refunded') else 'needs approval'}"]}

def lookup_order(s):
    return {"order": {"id": "A1042", "amount": 149}, "messages": ["TOOL: order A1042, $149, delivered 6 days ago"]}

def issue_refund(s):
    if not s.get("approved"):
        return {"messages": ["SYSTEM: refund rejected by reviewer"]}
    return {"refunded": True, "messages": ["TOOL: refund R-77 created (idempotency key A1042-refund)"]}

def route(s):
    last = s["messages"][-1]
    if "call lookup_order" in last: return "lookup_order"
    if "needs approval" in last and "refunded" not in s and "approved" not in s: return "issue_refund"
    return "END"

g = Graph(reducers={"messages": append})
g.node("agent", agent, route)
g.node("lookup_order", lookup_order, "agent")
g.node("issue_refund", issue_refund, "agent")

store = {}                                     # stands in for a Postgres checkpointer
state, status = g.run(store, "t-1", {"messages": ["USER: refund A1042, broken headphones"]},
                      interrupt_before=("issue_refund",))
print(status, "| checkpoints:", len(store["t-1"]))
# ... hours later, a different process, same thread id ...
state, status = g.run(store, "t-1", resume=True)
print(status, "| checkpoints:", len(store["t-1"]))
print(json.dumps(state["messages"], indent=1))

It prints paused before issue_refund | checkpoints: 4, then done | checkpoints: 6, then the six messages of the run. The second call receives no state from the caller: everything comes from the stored checkpoint, which is the point. Unlike the real runtime, the toy runs one node per step and has no parallel branches.

The same agent in LangGraph, using a dynamic interrupt so only refunds over $100 pause:

# Needs langgraph, langchain-openai and a Postgres checkpointer package; written against the documented API.
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.types import interrupt, Command

class RefundState(TypedDict):
    messages: Annotated[list, add_messages]

model = llm.bind_tools([lookup_order])                 # a LangChain chat model

def agent(state):
    return {"messages": [model.invoke(state["messages"])]}

def refund(state):
    amount = current_order_amount(state)               # read from the tool result in state
    if amount > 100:
        approved = interrupt({"order": "A1042", "amount": amount})   # pauses here
        if not approved:
            return {"messages": [("system", "Refund rejected by reviewer.")]}
    payments.refund("A1042", amount, idempotency_key="A1042-refund")  # side effect after interrupt
    return {"messages": [("system", f"Refund of ${amount} issued.")]}

def route(state):
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return "refund" if wants_refund(last) else END

b = StateGraph(RefundState)
b.add_node("agent", agent)
b.add_node("tools", ToolNode([lookup_order]))
b.add_node("refund", refund)
b.add_edge(START, "agent")
b.add_conditional_edges("agent", route, ["tools", "refund", END])
b.add_edge("tools", "agent")
b.add_edge("refund", "agent")
graph = b.compile(checkpointer=checkpointer)

cfg = {"configurable": {"thread_id": "ticket-8812"}, "recursion_limit": 12}
graph.invoke({"messages": [("user", "Refund order A1042, the headphones arrived broken.")]}, cfg)
# later, from any server:
graph.invoke(Command(resume=True), cfg)
  • "Nodes mutate the state." Nodes return partial updates; reducers merge them. Mutating the input dict in place bypasses the reducers and the checkpoint record.
  • Forgetting a reducer on a list key. Without add_messages (or another reducer), each update overwrites the list, and the history silently shrinks to the last message.
  • "Checkpoints mean exactly-once." A crash mid-step re-runs that step from the last checkpoint. Side-effecting nodes must be idempotent.
  • Code before interrupt() running twice. On resume the node restarts from its first line. Keep side effects after the interrupt or in another node.
  • Using the in-memory checkpointer in production. It vanishes on restart and is not shared between servers, so interrupts and multi-turn threads break. Use a database-backed one.
  • Putting business rules only in the prompt. The router is code; put rules that must hold (approval thresholds, step budgets) there.
  • Letting state grow without limit. Every value is checkpointed every step and messages are re-sent every call; token cost grows quadratically with loop length.
  • "Replay reproduces the run." Control flow replays; model calls are made again and can differ. Read saved outputs to reproduce exactly.
Two nodes run in the same super-step and both return {"messages": [m]}. What happens with and without the add_messages reducer?
With it, both messages are appended in a deterministic order. Without a reducer, two writes to the same key in one step conflict and LangGraph raises an error instead of picking one; for a single writer, it would overwrite the list.
The process crashes after issue_refund called the payment API but before the step's checkpoint was saved. What happens on resume, and how do you make it safe?
The run resumes from the previous checkpoint and runs issue_refund again, calling the payment API a second time. Make it safe with an idempotency key derived from the state (such as the order ID), so the provider returns the original refund instead of creating a new one.
Why can a reviewer approve a refund six hours after the run paused, on a different server, without anything having been kept in memory?
At the interrupt the full state and the next node were saved by the checkpointer under the thread ID. Resuming with Command(resume=...) and the same thread ID loads that checkpoint on any server and continues from the paused point.
A node logs "approval requested" to an audit table, then calls interrupt(). Why do you see two audit rows per approval?
On resume, the node re-runs from its first line, so the audit write before interrupt() executes again. Move it into a separate node before this one, or make the write idempotent.
System prompt plus tools are 1,500 tokens, the user message 30, and each loop iteration adds 300 tokens. How many input tokens does a 10-call run consume, and what would you change first?
\(1{,}530 \times 10 + 150 \times 10 \times 9 = 15{,}300 + 13{,}500 = 28{,}800\). First, trim what each iteration adds (summarise or drop old tool outputs, keep bulky results in state but out of messages); then cache the fixed 1,500-token prefix with prompt caching and cap iterations in the router.
For each, LangGraph or not: (a) retrieve and answer, (b) a tool loop with a refund approval step, (c) a 14-day onboarding workflow across five services with timers.
(a) No: an LCEL chain or plain code. (b) Yes: state, interrupt and durable checkpoints are exactly the requirement. (c) Probably a workflow engine such as Temporal, with LLM calls as activities; it specialises in long timers and cross-service durability.
Why are super-step updates applied only at the end of the step?
So nodes running in parallel in the same step all see the same input state and their updates are merged in a defined order by the reducers. That keeps runs deterministic and makes each checkpoint a consistent snapshot.
