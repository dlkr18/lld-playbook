01 — The pipeline end to end

Foundation

OFFLINE  load → parse/clean → chunk → embed → index (+ metadata, ACLs)
ONLINE   query → rewrite → retrieve (vector + keyword) → fuse → rerank
         → filter/dedupe → build prompt with citations → generate → validate

Every arrow is a place quality can leak. Senior answers name which stage they measured and tuned, rather than "we used a vector DB".

02 — Parsing and chunking

Core

  • Parsing is underrated: PDFs with tables, headers/footers, code blocks and HTML boilerplate wreck retrieval before embeddings ever matter.
  • Split on structure (headings, sections, paragraphs) first, then cap size (~300–800 tokens) with 10–20% overlap.
  • Prepend context to each chunk: document title and section path ("Kafka docs › Consumers › Offsets"). Cheap, large recall gains. "Contextual retrieval" goes further: an LLM writes a one-line summary of where the chunk sits.
  • Store metadata (source, date, product, permissions) for filtering.

03 — Hybrid search and reciprocal rank fusion

Core

Dense embeddings catch paraphrase; BM25 catches exact tokens (error codes, IDs, config keys, names). Run both and fuse by rank, which needs no score normalization:

RRF(d) = Σ_lists 1 / (k + rank_list(d)),   k ≈ 60
-- Postgres: pgvector + full-text search, fused with RRF
WITH v AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS r
  FROM chunks ORDER BY embedding <=> $1 LIMIT 50),
k AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS r
  FROM chunks, plainto_tsquery('english', $2) q
  WHERE tsv @@ q ORDER BY ts_rank_cd(tsv, q) DESC LIMIT 50)
SELECT id, SUM(1.0 / (60 + r)) AS score
FROM (SELECT * FROM v UNION ALL SELECT * FROM k) u
GROUP BY id ORDER BY score DESC LIMIT 20;

04 — Reranking

Core

Retrieve wide (top 20–50, cheap bi-encoder + BM25), then rescore with a cross-encoder (e.g. bge-reranker, Cohere Rerank) that reads query and chunk together, keep the top 3–8. Typically the biggest single precision gain, at 50–200 ms of added latency. An LLM can also rerank, slower and pricier.

05 — Query understanding

Core

  • Rewrite conversational follow-ups into standalone queries ("what about its default?" → "default value of Kafka consumer auto.offset.reset").
  • Decompose multi-part questions into sub-queries, retrieve for each.
  • Extract filters (date range, product, version) into structured metadata filters.
  • HyDE: embed a hypothetical answer instead of the question, closer in embedding space to real answers.

06 — Grounded generation

Core

  • Number each chunk in the prompt; require citations like [2] per claim; verify cited ids exist.
  • Instruct: answer only from context, say "not found in the docs" otherwise. Measure that abstention rate.
  • Put the most relevant chunks first and last; models attend less to the middle of long contexts.
  • Structured output (JSON schema) when downstream code consumes the answer.

Quick way to build the golden set: have an LLM write questions from random chunks (so the source chunk is the label), then hand-review and add real user questions. Diagnose order: if recall@k is low, nothing downstream can fix it.

08 — Production concerns

Advanced

  • Freshness: incremental re-indexing on document change; delete stale chunks; track index version per answer.
  • Access control: filter by user permissions at retrieval time, never after generation.
  • Latency budget: embed query ~20 ms, hybrid search ~20–50 ms, rerank ~100 ms, generation dominates. Stream tokens.
  • Caching: embedding cache, retrieval cache, semantic cache for repeated questions.
  • Injection: retrieved documents can contain instructions; treat them as data, never let them trigger tools without checks.
  • When not RAG: structured data questions ("revenue last quarter") need text-to-SQL or an API tool, not chunk search. That's where agents come in.

09 — Check yourself

Users ask about an error code and RAG returns irrelevant chunks.
Dense embeddings handle rare exact tokens poorly; add BM25 (hybrid), and include the code in chunk metadata.
Recall@20 is 95% but answers are often wrong.
Retrieval finds it but ranking/generation fails: add a reranker to put the right chunk in the top few, check faithfulness, check lost-in-the-middle.
How do you evaluate retrieval without labels?
Generate questions from chunks (chunk = label), review a sample by hand, then add real queries labeled over time.
