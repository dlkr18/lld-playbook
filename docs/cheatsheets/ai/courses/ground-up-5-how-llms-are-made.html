How an LLM is made // AI from the ground up · Part 5

The pipeline from raw web text to a helpful assistant, and how to tell whether a model is actually good.

5 Core3 Advanced

01 — Pretraining

Core

  • Data: trillions of tokens of web, code, books, papers. Most of the work is filtering (quality classifiers, language ID), deduplication (MinHash near-dup), and removing toxic or private data. Data mix ratios matter enormously.
  • Objective: next-token cross-entropy, nothing else.
  • Scale: thousands of GPUs for weeks or months, 3D parallelism (Part 9), checkpointing every few hours because hardware fails constantly.
  • Result: a base model. It continues text; it doesn't follow instructions or know when to stop.
  • Mid-training / annealing: final phase on higher-quality, math/code-heavy, long-context data with decaying LR.

02 — Supervised fine-tuning (instruction tuning)

Core

Train the base model on (prompt, ideal response) pairs formatted as conversations. Same loss, but only on response tokens. Tens of thousands of high-quality examples are enough to teach format, tone and instruction-following; SFT teaches how to answer, it adds little new knowledge.

03 — Chat templates and special tokens

Core

<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
What is 2+2?<|im_end|>
<|im_start|>assistant
4<|im_end|>

Every model family has its own template (ChatML above for Qwen; Llama 3 uses <|start_header_id|> etc.). The model only learned its own. Use tokenizer.apply_chat_template(messages, add_generation_prompt=True); never hand-format.

Trap

a missing end-of-turn token in fine-tuning data makes the model ramble forever; a mismatched template quietly degrades quality.

04 — RLHF

Advanced

  1. Collect human comparisons: for a prompt, which of two responses is better?
  2. Train a reward model to predict those preferences (Bradley–Terry: P(a ≻ b) = σ(r(a) − r(b))).
  3. Optimize the LLM with RL (PPO) to maximize reward, with a KL penalty to the SFT model so it doesn't drift into gibberish that fools the reward model (reward hacking).

Powerful but heavy: four models in memory (policy, reference, reward, value), unstable hyperparameters.

05 — DPO and friends

Advanced

Direct Preference Optimization shows the RLHF objective has a closed-form optimal policy, so you can optimize preferences with a simple classification-style loss, no reward model, no RL:

L = −log σ( β [ log π(y_w|x)/π_ref(y_w|x) − log π(y_l|x)/π_ref(y_l|x) ] )

Increase the chosen answer's likelihood relative to the reference more than the rejected one's. β sets how far you may move from the reference. Variants: IPO, KTO (needs only thumbs up/down), ORPO, SimPO. In TRL: DPOTrainer.

06 — Reasoning models and RL with verifiable rewards

Advanced

Recent models are trained with RL on tasks where correctness can be checked automatically (math answers, unit tests). The model learns to produce long chains of thought before answering; algorithms like GRPO compare a group of sampled answers to each other instead of training a value model. Takeaway: more test-time compute (longer thinking) buys accuracy.

07 — Evaluating LLMs

Core

  • Benchmarks: MMLU (knowledge), GSM8K/MATH (math), HumanEval/SWE-bench (code), IFEval (instruction following). Useful but saturated and often contaminated (test data in pretraining).
  • LLM-as-judge: a strong model grades outputs. Cheap and scalable; biased toward longer answers, its own style, and first position. Randomize order, use rubrics, spot-check by hand.
  • Human preference arenas: pairwise votes, Elo ratings.
  • Your own task eval is the only one that matters for a product: 100–500 real examples with an automatic metric (exact match, JSON validity, SQL execution, unit tests). Build it before you tune anything.

08 — Prompting vs RAG vs fine-tuning

Core

ProblemReach for
Model can do it, needs instructions or examplesPrompting, few-shot
Needs private or fresh knowledgeRAG (Part 7)
Needs consistent format, style, or a narrow skill; or a smaller/cheaper model must match a big oneFine-tuning (Part 6)
Too slow or expensiveDistill to a small model, quantize, better serving (Part 8)

Order of operations at a startup: prompt a strong API model → build an eval set → collect outputs → fine-tune/distill a small open model when cost, latency or privacy demands it.

09 — Check yourself

Base vs instruct model?
Base continues text; instruct has been SFT'd (and usually preference-tuned) to follow chat-formatted instructions and stop properly.
Why the KL penalty in RLHF?
Keeps the policy near the SFT model so it stays fluent and doesn't exploit reward-model weaknesses.
DPO vs RLHF?
DPO optimizes preferences directly from pairs with a supervised loss; no reward model or PPO. Simpler and stable; RL can still win with good reward signals and online sampling.
Your fine-tuned model scores well on MMLU but users hate it.
Benchmark ≠ product. Build a task-specific eval from real usage and judge on it.
