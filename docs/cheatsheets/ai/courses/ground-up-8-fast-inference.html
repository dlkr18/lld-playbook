Compression and fast inference // AI from the ground up · Part 8

Distillation, quantization, vLLM, ONNX and TensorRT, all explained from one idea: whether a step is limited by arithmetic or by moving bytes.

01 — Prefill, decode, and the metrics

Core

  • Prefill: process the whole prompt at once. Large matrix–matrix multiplies → compute-bound. Sets TTFT (time to first token).
  • Decode: one token per step; each step reads every weight (and the KV cache) from HBM to do a skinny matrix–vector multiply → memory-bandwidth-bound. Sets TPOT/ITL (time per output token).
batch-1 decode ceiling ≈ HBM bandwidth / bytes read per token
7B bf16 = 14 GB on A100 (2.0 TB/s) → ≤ ~140 tok/s
same model 4-bit (~4 GB)           → ≤ ~500 tok/s (in theory)

Two consequences explain the whole field: batching reuses each weight read across many requests (throughput up almost free), and shrinking bytes (quantization, smaller KV) directly speeds decode.

Report: TTFT, TPOT, throughput (total tokens/s), p50/p99 latency, max concurrency at an SLO, cost per million tokens.

02 — Quantization basics

Core

symmetric:   s = max|x| / (2^{b−1} − 1),   q = round(x / s),   x̂ = s·q
asymmetric:  s = (max − min)/(2^b − 1),  z = round(−min/s),  q = round(x/s) + z
int8 example: weights in [−0.5, 0.5] → s = 0.5/127 ≈ 0.0039; 0.123 → q = 31 → x̂ = 0.122
  • Granularity: per-tensor (one scale), per-channel (one per output row), per-group (e.g. 128 weights). Finer → less error, slightly more storage.
  • What gets quantized: weights only (W8A16, W4A16) helps memory-bound decode; weights + activations (W8A8, FP8) uses low-precision tensor cores and helps compute-bound prefill and large batches; KV cache (FP8/INT8) for long context.
  • PTQ vs QAT: post-training quantization needs only a small calibration set; quantization-aware training simulates rounding during training (straight-through estimator) for better low-bit accuracy.

03 — LLM quantization methods

Advanced

The core difficulty: LLM activations contain a few channels with values 100× larger than the rest. One shared scale then crushes everything else to zero.

  • LLM.int8(): detect outlier channels, run them in fp16, the rest in int8.
  • SmoothQuant: divide activations by a per-channel factor and multiply the weights by it (math unchanged), moving the difficulty into weights, which tolerate it. Enables W8A8.
  • GPTQ: quantize weights column by column; after rounding each, adjust the remaining columns using second-order (Hessian) information from calibration data to cancel the error. Good 4-bit.
  • AWQ: about 1% of weight channels matter most, identified by activation magnitude; scale them up before quantizing so they keep precision. Fast, robust 4-bit, well supported in vLLM.
  • GGUF (llama.cpp): block-wise k-quants (Q4_K_M etc.) for CPU, Apple Silicon and local inference.
  • FP8 on H100/L40S/Ada: near-lossless W8A8 with simple per-tensor scaling; often the first thing to try on modern GPUs.

Rule of thumb: 8-bit is nearly free; 4-bit weight-only usually costs ~1–2 points on benchmarks, more on math/code; below 4 bits degrades fast. Always measure on your own eval.

04 — Knowledge distillation

Core

A large teacher's output distribution says not just "the answer is cat" but "dog is somewhat plausible, car is not". That "dark knowledge" gives a student far more signal per example than one-hot labels.

L = α · CE(y, s) + (1 − α) · T² · KL( softmax(t/T) ‖ softmax(s/T) )
T: temperature (2–5 typical) softens both distributions
T²: restores gradient scale, which softening shrinks by 1/T²
  • Logit (white-box) distillation: needs teacher logits and a shared tokenizer.
  • Sequence-level (black-box) distillation: the teacher generates responses; SFT the student on them. Works through any API; how most small "distilled" LLMs are made.
  • On-policy distillation: the student generates, the teacher scores or corrects; avoids train/test mismatch.

Startup pattern: prototype with a frontier API model, log inputs/outputs, distill into a fine-tuned 1–8B open model that's 10–50× cheaper to serve.

05 — Pruning and sparsity

Advanced

Remove weights or whole structures. Unstructured pruning (zero individual weights, e.g. SparseGPT, Wanda) keeps accuracy at 50% sparsity but needs sparse kernels to be faster. 2:4 structured sparsity (2 zeros in every 4) is accelerated by Ampere+ tensor cores. Structured pruning removes heads, channels or layers, then distills to recover (e.g. Minitron).

06 — vLLM: PagedAttention and continuous batching

Core

The problem: naive servers pre-allocate a contiguous KV buffer per request sized for max length. Most of it sits unused, so few requests fit and the GPU idles on bandwidth.

PagedAttention: split each sequence's KV cache into fixed-size blocks (e.g. 16 tokens), allocated on demand and mapped by a block table, exactly like OS virtual memory pages. Waste drops to under one block per sequence, so far more sequences fit. Blocks can be shared copy-on-write (parallel sampling, common prefixes).

Continuous (iteration-level) batching: static batching waits for the longest sequence before admitting new work. vLLM's scheduler re-forms the batch every decode step: finished sequences leave, waiting ones join, preempting or swapping when memory runs out. GPU stays saturated.

Also: chunked prefill (mix prefill chunks into decode batches to protect TPOT), automatic prefix caching (reuse KV of shared system prompts), multi-LoRA, tensor parallelism, speculative decoding, an OpenAI-compatible server.

vllm serve Qwen/Qwen2.5-1.5B-Instruct --max-model-len 4096 \
  --gpu-memory-utilization 0.9 --enable-lora --lora-modules sql=./adapter

07 — Speculative decoding

Advanced

Because decode is memory-bound, scoring k tokens in one forward pass costs about the same as generating one. So:

  1. A cheap drafter (small model, n-gram lookup, or extra heads as in Medusa/EAGLE) proposes k tokens.
  2. The target model runs once over all k and gets its own probabilities at each position.
  3. Accept each draft token with probability min(1, p_target / p_draft); on the first rejection, resample from the corrected distribution and stop.

This rejection scheme makes outputs exactly distributed as the target model's. Speedup 2–3× when the drafter agrees often (code, structured output), less for creative text and large batches.

08 — ONNX, ONNX Runtime, TensorRT

Core

  • ONNX: an open, framework-neutral format for a model's computation graph and weights. torch.onnx.export(model, example_inputs, "m.onnx", dynamic_axes=…) (or the newer dynamo-based exporter).
  • ONNX Runtime: runs ONNX graphs with graph optimizations (constant folding, operator fusion) and pluggable execution providers: CPU, CUDA, TensorRT, CoreML, DirectML. Supports int8 quantization. Great for CPU or edge serving of encoders and classifiers.
  • TensorRT: NVIDIA's inference compiler. Parses the graph, fuses layers, picks the fastest kernel for each op on the exact GPU (autotuning), runs FP16/INT8/FP8 with calibration. Output "engine" is specific to GPU model and TensorRT version.
  • TensorRT-LLM: LLM-specific runtime (in-flight batching, paged KV, FP8, speculative decoding); often the throughput leader on NVIDIA at the cost of build complexity.

Rule of thumb: LLM generation → vLLM/SGLang/TensorRT-LLM. Embedding models, rerankers, classifiers, vision → ONNX Runtime or TensorRT (or Triton Inference Server hosting them).

09 — Kernel fusion and why compilers help

Advanced

Every separate GPU op reads its input from HBM and writes its output back. A chain like matmul → add bias → GELU → dropout does four round-trips; a fused kernel does one. Fusion, FlashAttention, torch.compile, TensorRT and Triton custom kernels are all applications of one principle: minimize bytes moved between HBM and the compute units.

10 — A production serving setup

Core

  • API layer (FastAPI) handles auth, rate limits, request validation, streaming tokens to clients via SSE.
  • Inference server (vLLM) on GPU nodes behind a load balancer; prefix-aware routing to maximize cache hits.
  • Autoscale on queue depth or KV-cache utilization, not CPU.
  • Structured output via JSON-schema constrained decoding; timeouts and max-token caps.
  • Log prompts, outputs, latency and user feedback to Postgres for evals and future fine-tuning data.

This maps neatly onto your ad-serving instincts: tail latency, caching, admission control, and per-request cost.

11 — Check yourself

Why does 4-bit weight-only quantization speed up decode when the matmul still runs in fp16?
Decode is bound by reading weights from HBM; 4-bit cuts bytes ~4×, dequantization in registers is cheap.
Why does continuous batching beat static batching?
Sequences end at different times; static batches idle finished slots until the longest finishes. Iteration-level scheduling refills slots every step.
What problem does PagedAttention solve?
KV-cache fragmentation and over-reservation; paging lets memory be allocated on demand and shared, raising concurrency.
Why multiply the distillation KL term by T²?
Softening by T scales its gradients by 1/T²; multiplying keeps them comparable to the hard-label term.
Does speculative decoding change the output distribution?
No; the accept/reject rule preserves the target model's distribution exactly.
TTFT is fine but tokens stream slowly under load.
Decode is bandwidth/KV-bound: quantize weights and KV, enable chunked prefill, cap batch size for TPOT SLO, or add replicas/tensor parallelism.
