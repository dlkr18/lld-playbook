Agents and tool use // Evals, RAG and agents · Part 3

An agent is just a loop. What separates a demo from a production agent is bounded autonomy, good tool design, context management, safety, and evaluation of trajectories, not only final answers.

1 Foundation6 Core1 Advanced

01 — What an agent is

Foundation

An LLM that, given a goal, repeatedly decides the next action (call a tool, ask a question, or finish), observes the result, and continues. The ReAct pattern: reason → act → observe → repeat.

Tool calling (function calling) is the mechanism: you describe tools with a name, description and JSON schema; the model replies with a structured call instead of text; your code executes it and appends the result to the conversation. The model never runs anything itself.

02 — The agent loop in code

Core

def run_agent(task, tools, llm, max_steps=10, budget_tokens=200_000):
    msgs = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": task}]
    used = 0
for step in range(max_steps):
        resp = llm(msgs, tools=[t.schema for t in tools.values()])
        used += resp.usage_tokens
        msgs.append(resp.message)
        if not resp.tool_calls:                      # model chose to answer
return resp.text
        for call in resp.tool_calls:
            tool = tools.get(call.name)
            try:
                if tool is None: raise ValueError(f"unknown tool {call.name}")
                if tool.side_effect and not approved(call): out = "DENIED by user"
else: out = tool(**call.args)
            except Exception as e:
                out = f"ERROR: {e}" # let the model recover
            msgs.append({"role": "tool", "tool_call_id": call.id,
                         "content": truncate(str(out), 4000)})
        if used > budget_tokens:
            msgs = compact(msgs)                     # summarize old turns
return "Stopped: step limit reached"

Every production concern is visible here: step and token budgets, unknown tools, errors fed back, side-effect approval, output truncation, context compaction.

03 — Workflows vs agents (pick the least autonomy that works)

Core

Anthropic's "Building effective agents" framing, widely used in interviews:

PatternShapeUse when
Prompt chainingfixed sequence of LLM steps with checks betweenTask splits into known stages
Routingclassify input, send to a specialized pathDistinct input types
Parallelizationrun sub-tasks or votes concurrently, aggregateIndependent parts, or need consensus
Orchestrator–workersLLM plans sub-tasks dynamically, workers executeSub-tasks not known in advance
Evaluator–optimizerone LLM drafts, another critiques, loopClear quality criteria exist
Autonomous agentopen loop with toolsOpen-ended path, verifiable progress

Workflows are predictable and cheap; agents are flexible and costly. Saying "I started with an agent, moved most of it to a workflow, and kept the agent only for X" is a strong signal.

04 — Designing tools the model can use well

Core

  • Few, well-named tools with clear descriptions and examples beat many overlapping ones. Tool descriptions are prompts.
  • Return concise, structured, model-readable results (not 50 KB of raw JSON); include ids for follow-up calls.
  • Helpful error messages ("date must be YYYY-MM-DD") let the model self-correct.
  • Make tools idempotent where possible; separate read tools from write tools.
  • MCP (Model Context Protocol): an open standard for exposing tools, resources and prompts to any LLM app through a server, so integrations are reusable across clients.

05 — Context and memory management

Core

  • Long tasks overflow the context window and degrade quality before they hit the limit.
  • Compaction: summarize older turns and tool outputs, keep decisions and open items.
  • External memory: write notes/state to a file or DB, read back as needed (a scratchpad or to-do list).
  • Sub-agents: hand a focused sub-task to a fresh context, get back only a summary. Keeps the main context clean.
  • Prompt caching of the stable prefix (system prompt, tool definitions) cuts cost and latency a lot.

06 — Multi-agent systems

Advanced

Orchestrator plus specialized sub-agents running in parallel works well for breadth-first tasks (research across many sources). Costs: many more tokens, coordination failures, harder debugging. LangGraph models agents as explicit state graphs (nodes, edges, checkpoints), which makes control flow inspectable and resumable.

07 — Reliability and safety

Core

  • Bounds: max steps, token/cost budget, wall-clock timeout, loop detection (same call repeated).
  • Human-in-the-loop for irreversible actions (send, pay, delete); dry-run modes.
  • Prompt injection: web pages, emails, documents can carry instructions. Treat tool output as data; never let it widen permissions; isolate high-privilege tools from untrusted input.
  • Least privilege: scoped credentials, sandboxed code execution, allow-lists of domains.
  • Observability: trace every step (prompt, tool call, result, latency, tokens) so failures can be replayed.

08 — Evaluating agents

Core

  • Task success rate on a suite of realistic tasks with programmatic checks of the end state (row in DB, file correct, test passes).
  • Consistency: run each task k times; pass^k (succeeds every time) matters for production.
  • Trajectory metrics: correct tool chosen, invalid calls, redundant steps, steps and cost per success.
  • Safety cases: injected instructions, tasks that should be refused or escalated.
  • Error analysis on traces, as in Part 1: categorize where runs go wrong (planning, tool choice, argument errors, premature finish).

09 — Check yourself

Your agent loops calling the same search forever.
Add loop detection and step caps, improve tool results (say explicitly when nothing was found), give the model a "give up / ask user" option, check the stop condition in the prompt.
When would you not use an agent?
When the steps are known in advance: a fixed workflow is cheaper, faster, more testable.
How do you defend an email-reading agent against injection?
Email content is data; require user confirmation for sends/forwards; restrict recipients; separate the reading model from privileged actions; test with injection cases.
