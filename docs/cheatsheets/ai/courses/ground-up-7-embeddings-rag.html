Embeddings, vector search, and RAG // AI from the ground up · Part 7

Most AI products ground a model in private data. Know how text becomes searchable vectors, how nearest-neighbor search scales, and how a retrieval pipeline is built and measured.

5 Core1 Advanced

01 — Sentence embeddings

Core

An embedding model maps a whole text to one vector (often 384–4096 dims) so that similar meanings are close by cosine similarity. Usually an encoder transformer (or a decoder) with mean pooling or a special token, trained specifically for similarity.

Two shapes of model:

  • Bi-encoder: embed query and document separately, compare vectors. Fast: documents are embedded once, offline.
  • Cross-encoder: feed (query, document) together, output a relevance score. Much more accurate, too slow to run over a whole corpus, ideal for reranking a shortlist.

02 — Contrastive learning (InfoNCE)

Advanced

Train embeddings by pulling matching pairs together and pushing non-matching ones apart. With a batch of N (query, positive) pairs, every other positive in the batch serves as a negative:

L = −log [ exp(sim(q, p⁺)/τ) / Σⱼ exp(sim(q, pⱼ)/τ) ]

It's cross-entropy where the "class" is which document matches. Bigger batches and hard negatives (similar but wrong documents) make better embeddings. CLIP uses the same loss between images and captions.

03 — Vector search: exact and approximate

Core

Exact k-NN compares the query to every vector: O(N·d), fine to ~1M vectors on a GPU, too slow beyond. Approximate nearest neighbor (ANN) trades a little recall for big speed:

  • HNSW: a multi-layer proximity graph; greedy-walk from a sparse top layer down to dense lower layers. Excellent recall/latency, memory-heavy. Tunables: M (links per node), ef_search.
  • IVF: k-means cluster the vectors; search only the nprobe nearest clusters.
  • PQ (product quantization): split vectors into chunks, encode each chunk as a codebook id; compresses 10–50× for huge corpora.

Tools: FAISS (library), pgvector (Postgres extension with HNSW and IVFFlat indexes), Qdrant, Milvus, Weaviate. For many products, pgvector next to your existing Postgres is enough.

04 — The RAG pipeline

Core

  1. Ingest: parse documents, split into chunks, embed, store vectors with metadata.
  2. Retrieve: embed the query; get top-k by vector similarity, often combined with BM25 keyword search (hybrid) via reciprocal rank fusion.
  3. Rerank: cross-encoder rescoring of the top 50 → keep the best 5.
  4. Generate: put the chunks in the prompt with instructions to answer only from them and cite sources.

Why RAG instead of fine-tuning knowledge in: facts change, access control per user, citations, and no retraining. Fine-tuning shapes behavior; RAG supplies facts.

05 — Chunking, query rewriting, and failure modes

Core

  • Chunk size: 200–800 tokens with some overlap is a common start. Too small loses context; too large dilutes the embedding and wastes prompt space. Splitting on document structure (headings, paragraphs) beats fixed windows.
  • Query rewriting: turn a follow-up like "and for last year?" into a standalone query; HyDE embeds a hypothetical answer instead of the question.
  • Failures: right answer not retrieved (retrieval problem), retrieved but ignored or contradicted (generation problem), lost in the middle of a long context. Diagnose which before fixing.

06 — Measuring retrieval and RAG

Core

  • Retrieval: recall@k (is a correct chunk in the top k?), MRR, nDCG on a labeled set of (question, relevant chunk) pairs.
  • Generation: faithfulness (is every claim supported by retrieved text?), answer correctness, citation accuracy, usually via LLM-as-judge plus human spot checks.

Fix retrieval first: generation can't use what it never sees.

07 — Check yourself

Bi-encoder vs cross-encoder?
Bi-encoder embeds separately (fast, precomputable, less accurate); cross-encoder scores the pair jointly (accurate, slow). Use bi-encoder to retrieve, cross-encoder to rerank.
Why hybrid search?
Embeddings miss exact terms (IDs, rare names, codes); BM25 catches them. Combined recall is higher.
HNSW vs IVF?
HNSW: graph, high recall at low latency, more memory, slower builds. IVF: clustering, cheaper memory, recall depends on nprobe; pairs with PQ at billion scale.
Users report confidently wrong answers from your RAG bot.
Check retrieval recall on those questions; if chunks were retrieved, tighten the prompt to answer only from context and abstain otherwise, and add faithfulness evals.
