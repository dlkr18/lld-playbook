Context engineering — the real production skill // 6.6

Bigger than prompt engineering. The job: decide what's in the window each turn, because it's finite and quality drops as it fills.

Part 6 · AgentsChapter 6.6

01 — Overview

Prompt engineering asks "how do I phrase this?" Context engineering asks "of everything I could put in the window — system prompt, tool schemas, history, retrieved documents, memories, scratchpad — what earns its tokens this turn?" Two facts make this the job. First, the window is a hard budget: overflow is an API error. Second, and less obvious: quality degrades before you hit the limit. Long contexts bury the needle — models attend less reliably to material in the middle of a 150k-token window, and every irrelevant document you "helpfully" include is a distractor competing with the relevant one. More context is not more better; more relevant context is.

Token budgeting

allocate the window explicitlypython
WINDOW=200_000; RESERVE_OUT=4_000
budget = WINDOW - RESERVE_OUT - count(SYSTEM) - count(tools_schema)
while count(history) > budget*0.6: history = compact(history)  # keep history lean
retrieved = retrieve(q)[:budget_left()]                       # RAG fills the rest, capped

That sketch is the idea; production wants it as a class — one owner for the arithmetic, so no call site can quietly blow the window:

context_budget.py — the window as a managed resourcepython
class ContextBudget:
    """Explicit allocation of the context window. All numbers are tokens."""
def __init__(self, count_tokens, window=200_000, reserve_output=4_000,
                 headroom=0.10):
        self.count = count_tokens                # provider tokenizer, or estimate
self.window, self.reserve_out = window, reserve_output
        self.headroom = int(window * headroom)   # slack for counting error/growth
self.spent = {}                          # component → tokens
def charge(self, name, text_or_msgs) -> int:
        n = (self.count(text_or_msgs) if isinstance(text_or_msgs, str)
             else sum(self.count(json.dumps(m)) for m in text_or_msgs))
        self.spent[name] = self.spent.get(name, 0) + n
        return n

    def remaining(self) -> int:
        used = sum(self.spent.values())
        return self.window - self.reserve_out - self.headroom - used

    def fit(self, name, chunks, per_chunk_overhead=10) -> list:
        """Greedy-fill ranked chunks (best first) into what's left."""
        out, left = [], self.remaining()
        for c in chunks:
            n = self.count(c) + per_chunk_overhead
            if n > left: break # ranked list → stop at first miss
            out.append(c); left -= n
        self.charge(name, "".join(out))
        return out

    def report(self) -> str:                     # log this every turn in dev
        lines = [f"{k:>12}: {v:>7,}" for k, v in self.spent.items()]
        return "\n".join(lines + [f"{'remaining':>12}: {self.remaining():>7,}"])

# per turn:
bud = ContextBudget(count_tokens)
bud.charge("system", SYSTEM); bud.charge("tools", json.dumps(tools))
if bud.charge("history", buffer.view()) > 0.5 * bud.window:
    buffer.compress(); bud.spent["history"] = bud.charge("history", buffer.view())
docs = bud.fit("rag", ranked_chunks)             # RAG gets whatever's left

The design choice worth stealing is the allocation order: fixed costs first (system, tools — you can't shrink them per-turn), then history (shrinkable via compaction), then retrieval (elastic — it takes whatever remains). And the report(): the first time you print it you'll usually find a surprise, like tool schemas eating 9k tokens because someone pasted three example outputs into a description. Worked example (illustrative): system 3k + tools 6k + history 41k + retrieval 30k = 80k input per turn at ~$3/M is $0.24/turn. After compaction (history → 8k) and top-4 retrieval instead of top-12 (→ 10k): 27k/turn ≈ $0.08 — and answer quality typically rises, because the 8 dropped chunks were mostly distractors.

Compaction — summarize old turns (how long sessions survive)

compact.pypython
def compact(msgs):
    head, tail = msgs[:-6], msgs[-6:]            # keep last 6 turns raw
    s = llm("Summarize. PRESERVE: decisions, facts, open tasks, IDs, file paths."
            + render(head))
    return [{"role":"user","content":f"[EARLIER SUMMARY]\n{s}"}] + tail

The preserve-list is the entire art. Here's the productionized version — an explicit, extensible list, plus a verification pass that checks the summary didn't lose pinned strings:

compact_v2.py — preserve-list + lossless-pin verificationpython
PRESERVE = ["decisions made and their stated reasons",
            "user-stated facts, preferences, corrections",
            "open tasks / promises / unresolved questions",
            "exact identifiers: order numbers, ticket IDs, emails, amounts",
            "exact file paths, URLs, branch names, error strings",
            "constraints ruled OUT (things we tried that failed, and why)"]

PIN_RE = re.compile(r"\b(?:[A-Z]{2,5}-\d+|#\d{4,}|ORD[_-]?\w+|/[\w./-]{6,}"
r"|[\w.+-]+@[\w-]+\.\w+)\b")   # ids, paths, emails
def compact(llm, msgs, keep_recent=6):
    head, tail = msgs[:-keep_recent], msgs[-keep_recent:]
    raw = render(head)
    pins = sorted(set(PIN_RE.findall(raw)))         # strings that MUST survive
    s = llm("Summarize this conversation for an assistant that will continue it.\n"
"PRESERVE, verbatim where applicable:\n- " + "\n- ".join(PRESERVE) +
            f"\nThese exact strings MUST appear: {pins}\n\n{raw}")
    lost = [p for p in pins if p not in s]
    if lost:                                        # verify — cheap and priceless
        s += "\n[preserved identifiers]: " + ", ".join(lost)
    return [{"role": "user", "content": f"[EARLIER SUMMARY]\n{s}"}] + tail

What a good vs bad summary keeps — same 40-turn refund-investigation session, two summaries:

good vs bad — the diff that bites 30 turns latertext
BAD (fluent, useless):
  "The user contacted support about a billing issue. The assistant
   investigated several orders and payment records, discussed refund
   policy, and they worked toward a resolution. The tone was cooperative."

GOOD (dense, continuable):
  "User maria.g@example.com disputes duplicate charge on ORD-88231
   (2×$149.99, 2026-08-30). VERIFIED: second charge is a distinct order
   ORD-88232 created 41s later, same cart — likely double-submit.
   DECIDED: refund ORD-88232 in full (policy §4.2, <30 days). Refund
   API returned RF-5521 status=pending. OPEN: (1) confirm RF-5521
   settles within 48h, (2) user asked for invoice PDF — not yet sent.
   RULED OUT: fraud (device match), subscription renewal (none active)."

Every sentence of the bad summary is true, and the next 30 turns are doomed: turn 55's "so was that second charge fraudulent?" forces re-investigation the model already did — or worse, a fresh guess that contradicts the earlier finding. The good summary is barely longer, and notice its shape mirrors the preserve-list: identifiers verbatim, decisions with reasons, open items, and — most often forgotten — negative results. "RULED OUT: fraud" is what stops the agent from re-walking dead ends; dropped negatives are the classic silent compaction loss.

Prompt caching — static first → ~90% cheaper repeated input

mark a cacheable prefixpython
system=[{"type":"text","text":BIG_STATIC_SYSTEM,
         "cache_control":{"type":"ephemeral"}}]   # everything above is cached
# prefix must be BYTE-IDENTICAL across calls → pin prompt versions; volatile content LAST.

Mechanics. Providers cache the internal state (the processed prefix) keyed on the exact byte sequence of everything up to the cache marker. On the next call, if the prefix matches byte-for-byte, the provider skips reprocessing it and bills those tokens at a deep discount (on Anthropic's scheme: cache writes cost ~1.25× base input, cache reads ~0.1×; entries expire after ~5 minutes of disuse unless refreshed by another hit). Three consequences fall out of "byte-identical prefix": (1) order your prompt static→volatile: system prompt and tool schemas first, per-user profile next, conversation last — one changed byte at position N invalidates everything after N; (2) a timestamp or request-ID in the system prompt destroys caching entirely (a depressingly common self-inflicted wound); (3) agent loops are the perfect cache customer, because each step re-sends the previous steps verbatim — the growing history is itself a stable prefix, so you also mark the last message with a cache point on providers that support incremental (multi-breakpoint) caching.

Cache-hit arithmetic (illustrative prices: $3/M input, $0.30/M cached read, $3.75/M cache write). A 10-step agent run with 5k of static prefix (system+tools) and history growing ~3k/step:

ScenarioInput tokens billed (10 steps)Input cost
No caching — every step re-sends everything5k+8k+11k+…+32k ≈ 185k @ $3/M≈ $0.555
Cache static prefix only (5k)write 5k once + 9 reads of 5k + ~135k fresh @ $3/M≈ $0.44
Incremental caching of the whole transcripteach step: read all prior (~0.1×) + write only its new ~3k≈ $0.17

~3× cheaper on the same tokens, and cached tokens also skip reprocessing so time-to-first-token drops on every step. At fleet scale this is the difference between agents being affordable and not: 100k runs/day × $0.38 saved ≈ $38k/day (illustrative, but the ratio is real). The gotcha is the 5-minute TTL: a user who replies after 6 minutes pays the write price again — fine, unless your "optimization" assumed 100% hit rate in the unit economics.

Sub-agents as context isolation

A major reason to go multi-agent (Part 7) is memory management, not just specialization: a sub-agent runs in its own clean window and returns only a distilled result, keeping the parent's context lean.

In code, isolation is just: fresh messages list, task-scoped prompt, and a contract on the return size — the parent never sees the sub-agent's working mess:

subagent.py — burn a clean window, return a distilled resultpython
async def run_subagent(task: str, tools, impls, *, max_return_tokens=800):
    """Fresh context; the parent pays only for `task` in and the digest out."""
    sub_system = (f"You are a focused sub-agent. Complete ONLY this task:\n{task}\n"
f"Your final message is your report to the orchestrator: "
f"≤{max_return_tokens} tokens, findings + citations only — "
f"no narration of your process.")
    text, usage = await run_agent(task, tools, impls,       # ch. 52's loop —
                                  max_steps=10)             # its OWN msgs list
if count_tokens(text) > max_return_tokens:              # enforce the contract
        text = await llm(f"Compress to ≤{max_return_tokens} tokens. Keep all "
f"identifiers, numbers and citations:\n{text}")
    return text                                             # parent sees ONLY this
# parent — three investigations, zero pollution of the parent window:
digests = await asyncio.gather(
    run_subagent("Analyze error logs for service A, 06:00-09:00. Top 3 causes.", T, I),
    run_subagent("Check deploy diffs merged in the same window. Risky changes?", T, I),
    run_subagent("Summarize related incident tickets from the last 90 days.", T, I))
answer = await llm(SYNTH_PROMPT + "\n\n".join(digests))     # ~2.4k tokens, not 300k

The arithmetic that justifies it: each sub-investigation might churn through 100k tokens of logs and diffs. Done inline, the parent's window holds ~300k tokens of raw material (over the limit, and mostly noise by synthesis time). With sub-agents, the parent's window holds three ~800-token digests. The parent stays cheap, cacheable, and sharp for the actual decision; the expensive mess was spent in disposable windows. That's context engineering's whole thesis in one pattern: spend tokens where they inform the next decision; quarantine tokens that don't.

02 — The per-turn checklist

  • System prompt: static, versioned, cache-marked. No timestamps, no per-request IDs.
  • Tools: only the tools this task can need — 20 schemas the model never calls are pure distractor cost. Route first, then expose.
  • History: compact past the threshold; preserve-list with pins; recent turns raw.
  • Retrieval: ranked, floored (min relevance), capped by remaining budget — never "top-20 just in case."
  • Memories/profile: small, always-on facts in the prefix (cacheable); episodic recalls only above a score floor.
  • Big jobs: quarantined into sub-agents that return digests with size contracts.
  • Log the budget report: if you can't say where your input tokens went last turn, you're not doing context engineering yet.

Mini-scenario: the agent that got dumber every hour

Your ops agent works great at 9 am and is useless by lunch. Nothing changed — except its context. Each incident investigation appended raw kubectl output (8–20k tokens a pop); by turn 60 the window held 140k tokens, 90% of it stale pod listings. Symptoms: it re-asks answered questions, misses the one relevant line, and each turn costs 6× the morning rate. The fix took an afternoon: truncate tool results to 2k with a "full output at <path>" pointer, compaction at 50k with the pin-verification above, and log bud.report() per turn. Same model, same prompts — the agent "got smarter" purely by carrying less. When quality degrades over a session's lifetime, suspect the context before the model.

Compaction gotcha

A naive summary silently drops the one ID/decision you needed 30 turns later. Always pin "what to preserve," and keep recent turns raw. Related traps: (1) compacting mid tool-exchange — never summarize away an assistant tool_use whose tool_result is still in the tail, or the API rejects the transcript; compact only at turn boundaries. (2) Summarizing the summary: after 3–4 generations of rolling compaction, early facts have been paraphrased four times — pin-verification catches IDs, but decisions blur; re-anchor critical state in external memory (the scratchpad file, previous chapter) instead of letting it live only in summaries. (3) Cache-oblivious compaction: every compaction rewrites the transcript prefix and invalidates your incremental cache — batch compactions (compact rarely, cut deep) rather than trimming a little every turn.

Takeaway

Context engineering is a budget problem with four levers: allocate (explicit per-component budgets, elastic retrieval last), compress (compaction with preserve-lists and pin checks), reuse (caching: static first, byte-identical, volatile last), and isolate (sub-agents return digests, not transcripts). The teams whose agents feel "smart all day" aren't using secret models — they're just refusing to let junk tokens ride along.
