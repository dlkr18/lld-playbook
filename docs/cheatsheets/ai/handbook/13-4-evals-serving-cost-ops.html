Here is the middle tier wired end to end, because it's the one teams hand-wave. Cases live in JSONL next to the code; a runner executes them against the real stack (staging DB, real retrieval, real models); a calibrated judge grades text; deterministic assertions grade trajectories.

run_evals.py — the runner (staging stack, parallel, budgeted)python
def run_case(case) -> CaseResult:
    reset_fixtures(case.get("fixtures"))                 # deterministic world per case
    t0 = time.monotonic()
    out, trace = handle(case["question"], staff_user)    # the REAL entry point, not a mock
    checks = []
    exp = case["expect"]
    if "trajectory" in exp:
        checks += trajectory_asserts(trace, exp["trajectory"])   # deterministic, free
    if "must_contain" in exp or exp.get("grounded"):
        checks += string_asserts(out, exp)                        # deterministic, free
        checks.append(judge(case["question"], trace.sources, out))  # LLM, costs money
    return CaseResult(case["case_id"], checks,
                      latency_s=time.monotonic()-t0, cost_usd=trace.cost())

def trajectory_asserts(trace, exp):
    yield Check("called", all(trace.called(t) for t in exp["must_call"]))
    if exp.get("call_order"):
        yield Check("order", trace.first("get_order") < trace.first("refund_order", default=99))
    yield Check("max_refunds", trace.call_count("refund_order") <= exp["max_refunds"])
    yield Check("steps", trace.steps <= exp["max_steps"])
    yield Check("policy", not trace.policy_violations)

results = parallel_map(run_case, load_jsonl("evalset/e2e.jsonl"), workers=8)
report(results, gates={"kb_pass": 0.90, "agent_pass": 0.95, "redteam_pass": 1.00})
# full run: 120 cases ≈ 4 min at 8 workers, ≈ $0.9 in judge+system tokens (illustrative)
judge.py — the judge, and the calibration that makes it admissiblepython
JUDGE = """Given QUESTION, SOURCES, ANSWER: score 0/1 each —
correct (matches sources), grounded (no claim beyond sources),
complete (addresses the whole question). Return JSON. Be strict."""

def judge(question, sources, answer) -> Check:
    v = llm(model=JUDGE_MODEL, system=JUDGE, temperature=0,
            user=fmt(question, sources, answer), json_schema=VERDICT)
    return Check("judge", v["correct"] and v["grounded"] and v["complete"], detail=v)

# CALIBRATION PROCEDURE — run before trusting, re-run on every judge-model change:
# 1. sample 50 (question, sources, answer) triples from real traces
# 2. two humans label each independently; discuss disagreements → gold labels
#    (record inter-human agreement first; if humans agree < 0.9, fix the rubric,
#     not the judge — the judge can't hit a target the humans can't)
# 3. run the judge; require Cohen's kappa ≥ 0.7 AND raw agreement ≥ 0.85 vs gold
# 4. inspect every disagreement: systematic (judge lenient on partial answers?)
#    → tighten JUDGE prompt and repeat. Random → accept, note the noise floor.
# 5. freeze {judge model id + prompt hash} into the versioned ship unit below.
# A judge that drifted is worse than no judge: it green-lights regressions.

Where cost worksheets lie

Three omissions that wreck the neat table: (1) retries and escalation re-asks — a 5% retry rate plus escalated conversations that get re-litigated adds 8–12% to the LLM line; budget it. (2) conversation growth — the per-question input estimate assumes turn one; a 6-turn thread carries prior turns each call unless you summarize (Part 6 context management). (3) the judge at 100% — someone will propose judging every response "for safety"; that alone is ≈$0.009/question, half the answer cost. Sample, don't blanket.

03 — Step 3 — serving & rollout discipline

stateless FastAPI workers (agent state in Redis) → horizontal scale; the real
ceiling is provider rate limits → per-tenant token buckets + a queue (Part 12).

rollout of ANY behavior change (prompt, model, index, tool schema):
  CI evals green → shadow (log, don't serve) → canary 5% with auto-rollback on
  resolution-rate or red-team regression → 100%. The versioned unit that ships =
  {model id, prompts, index build, tool schemas, judge} TOGETHER (Part 12 MLOps).

Concretely — the whole deployment is small enough to read in one screen. Compose for staging, the same three containers under k8s in prod:

docker-compose.yml + k8s notes — the entire footprintyaml
services:
  api:
    build: .
    command: uvicorn app:app --host 0.0.0.0 --port 8080
    environment:

  postgres: { image: pgvector/pgvector:pg16, volumes: [pgdata:/var/lib/postgresql/data] }

# k8s (prod) — same shape, three additions worth having:
#   Deployment api: replicas 3, readinessProbe hits /v1/health (which checks
#     provider reachability + index freshness), resources requests 0.5cpu/512Mi
#   HPA: min 3 max 8 on p95 latency custom metric, NOT cpu (workers idle-wait on APIs)
#   PodDisruptionBudget minAvailable 2 — a node drain must not take the service down

# canary config (whatever your router/mesh — the CONTRACT is what matters):
canary:
  traffic_percent: 5
  duration: 4h
  auto_rollback_when:
    - metric: resolution_rate       drop_gt: 3%      vs: baseline_7d
    - metric: escalation_rate       rise_gt: 4%      vs: baseline_7d
    - metric: redteam_suite         below: 100%      run_every: 30m
    - metric: p95_latency_s         above: 6.0
    - metric: cost_per_resolved     above: 0.03
  promote: manual_click_after_green  # a human promotes; a robot only rolls BACK
rollback_drill.sh — practiced monthly, before it's neededbash
#!/usr/bin/env bash
set -euo pipefail
# Rollback = repoint to the previous SHIP_VERSION. Because the unit is versioned
# TOGETHER, this reverts prompts+model+schemas atomically. The index is the slow
# part — index builds are kept for the last 3 versions, so rollback = repoint,
# never rebuild.
PREV=$(ship-registry previous --env prod)
echo "rolling back prod to ${PREV}"

kubectl set env deploy/api SHIP_VERSION="${PREV}" -n support-agent
kubectl rollout status deploy/api -n support-agent --timeout=180s

# verify with the smoke slice (12 cases, ~40s), not vibes:
python evals/run_evals.py --set evalset/smoke.jsonl --env prod --gate all=1.0

# drill scoring: time-to-green under 10 minutes = pass. Log it:
ship-registry record-drill --version "${PREV}" --minutes "${SECONDS}" --operator "${USER}"

The versioned ship unit is the whole trick

Prompts in one repo, model ID in an env var, index rebuilt on a cron, tool schemas in another service — that's four things that can disagree, and "works in staging, broken in prod" is usually two of them disagreeing. One SHIP_VERSION hash naming all five (model, prompts, index build, tool schemas, judge) makes deploy, canary, and rollback each a single pointer move — which is why the rollback drill above is boring, and boring is the goal.

04 — Step 4 — close the flywheel

weekly: pull traces where (thumbs-down OR escalated OR judge<perfect OR heavily edited)
  → cluster failures:  retrieval miss? → chunking/hybrid fix (2/4 table gets a new row)
                       wrong tool path? → tool description fix, new trajectory test
                       bad synthesis?  → prompt fix, new judge case
  → every fix ships with the eval case that would have caught it
  → quarter later: enough (question → great answer) pairs accumulate
    → NOW fine-tuning a small model on your distribution is a measured decision (Part 8),
      not a hope. The flywheel earned the data.

The weekly triage is one SQL query over the tables from 1/4, run Monday morning, reviewed in 30 minutes:

triage.sql — the Monday query (traces + feedback, 1/4 schema)sql
WITH bad AS (
  SELECT t.request_id,
         max(c.intent)                              AS intent,
         bool_or(f.thumbs = -1)                     AS thumbed_down,
         bool_or(c.status = 'escalated')            AS escalated,
         bool_or(t.kind='validation' AND t.is_error) AS validation_reject,
         max(CASE WHEN t.kind='llm' AND t.name='judge'
THEN (t.payload->>'score')::float END) AS judge_score,
         max(length(f.edited_text))                 AS edit_len
  FROM traces t
  LEFT JOIN feedback f      USING (request_id)
  LEFT JOIN conversations c ON c.conv_id = t.conv_id
  WHERE t.created_at > now() - interval '7 days'
GROUP BY t.request_id
)
SELECT request_id, intent,
       CASE WHEN escalated         THEN 'escalated'
WHEN thumbed_down      THEN 'thumbs_down'
WHEN validation_reject THEN 'validation_reject'
WHEN judge_score < 1.0 THEN 'judge_flagged'
WHEN edit_len > 200 THEN 'heavily_edited' -- human rewrote the answer
 END AS why
FROM bad
WHERE escalated OR thumbed_down OR validation_reject
   OR judge_score < 1.0 OR edit_len > 200
ORDER BY intent, why;
-- typical week (illustrative): 3K×5 days ≈ 15K requests → ~180 flagged (1.2%)
-- → skim ~40 traces, cluster, file 2–4 fixes. Sustainable forever.

Flagged traces get a cluster label from a fixed taxonomy — fixed, because a taxonomy that grows a new category per week is a mood diary, not a measurement:

And when the quarter's data has accumulated, the fine-tune question gets answered with a memo, not a meeting. The template forces every number the decision needs:

finetune_memo.md — the decision template (Part 8 applied)text
FINE-TUNE DECISION MEMO — support agent, Q_
1. CANDIDATE TASK: which component? (router / answer synthesis / never the
   policy engine). One component per memo.
2. DATA EARNED: N accepted (question → final human-approved answer) pairs from
   feedback.edited_text + thumbs-up traces. Dedup'd? PII-scrubbed? License to train?
3. BASELINE: current component metric + current $/question for this slice.
4. HYPOTHESIS: small model fine-tuned on (2) matches mid-tier quality on the
   COMMON slice, at ~1/10 token price. Expected saving: $___/month (show the
   worksheet delta — e.g. answer slice $0.0127 → ~$0.003 ≈ $600/month at our volume).
5. COST TO RUN THE EXPERIMENT: tuning $___ + 2 eng-weeks + new eval runs.
   Payback period at (4): ___ months. If > 6, stop here.
6. EVAL PLAN: same 120-case suite + slice gates; ship only via the canary
   pipeline above. Fine-tuned model joins the versioned ship unit.
7. FRESHNESS RISK: what in this component's knowledge changes weekly? (If the
   answer is "policies" — the tune must be style/format-only; facts stay in RAG.)
8. ROLLBACK: previous SHIP_VERSION; hosted mid-tier stays available. Kill
   criteria: any slice −3% or red-team < 100%.
DECISION: go / no-go / revisit in Q_, signed by eng + support lead.

What this part demonstrated

Spec → shape decision → measured retrieval → contracted tools → bounded loop → tiered evals → cost arithmetic → staged rollout → flywheel. Fourteen parts of this book, one coherent system. Nothing exotic; every step boring, measured, and defensible — which is exactly what production AI looks like when it works.

Exercises

  1. Wire the smallest complete harness for any LLM feature you own: 10 JSONL cases, a runner that hits the real entry point, one deterministic assertion per case, and a CI job that fails under a gate. Time yourself — the point is discovering it's an afternoon, not a quarter.
  2. Calibrate a judge for real: 30 outputs, label them yourself and get a colleague to label independently, compute raw agreement between you two before computing judge agreement. Report both numbers and what the disagreements taught you about your rubric.
  3. Fill in the cost worksheet with current real prices for two providers, including the caching column. Find the traffic level (questions/day) at which self-hosting a mid-tier open model breaks even — show the arithmetic, including the on-call cost you're tempted to omit.
  4. Run the rollback drill against a staging deploy of anything you operate: revert to the previous version, prove health with a smoke eval, and record time-to-green. If any step required tribal knowledge not in the script, the script is incomplete — fix it and run it again.
  5. Write the Monday triage query for your own system's logs (whatever schema you have), run it over last week, and cluster 20 flagged items using the taxonomy table. Count how many are corpus_gap or policy_friction — failures no model change can fix — and notice how much roadmap that reframes.
