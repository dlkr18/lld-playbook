Reliability: surviving flaky models & APIs // 12.2

LLM APIs rate-limit, time out, and occasionally return garbage. Agents compound small errors: a 2% failure rate per step is an 18% failure rate over a 10-step trajectory (0.98¹⁰ ≈ 0.82). Engineer for it — this chapter is the module you drop into the thin harness from the build-vs-buy chapter.

01 — Retries, backoff, circuit breaker, fallback — the module

The one-liner version first, because it's the shape to memorize:

call_with_retry — the minimal shapepython
def call_with_retry(**kw):
    for attempt in range(5):
        try: return client.messages.create(**kw, timeout=60)
        except (RateLimitError, APIStatusError) as e:
            if attempt == 4: raise
            sleep(min(2**attempt + jitter(), 30))   # exponential backoff + jitter

Production needs three more ideas layered on: classify errors (retrying a 400 is a waste; retrying a 429 without honoring retry-after is rude and slow), a circuit breaker (after repeated failures, stop calling the dead thing and fail fast), and a fallback chain (another region/model when the primary is genuinely down). Here is the whole module:

reliability.py — retry + breaker + fallback, ~70 lines you ownpython
import random, time

class CircuitOpen(Exception): pass

RETRYABLE   = (RateLimitError, APITimeoutError, InternalServerError)  # 429/timeout/5xx
NON_RETRY   = (BadRequestError, AuthenticationError)                   # 400/401: fix, don't retry
class Breaker:
    """CLOSED -> (N consecutive fails) -> OPEN -> (cooldown) -> HALF_OPEN -> probe."""
def __init__(self, fail_threshold=5, cooldown_s=30):
        self.fails, self.threshold, self.cooldown = 0, fail_threshold, cooldown_s
        self.opened_at = None
def allow(self) -> bool:
        if self.opened_at is None: return True # CLOSED
if time.monotonic() - self.opened_at >= self.cooldown:
            return True # HALF_OPEN: one probe
return False # OPEN: fail fast
def record(self, ok: bool):
        if ok: self.fails, self.opened_at = 0, None # any success closes it
else:
            self.fails += 1
if self.fails >= self.threshold:
                self.opened_at = time.monotonic()

def backoff_s(attempt: int, retry_after: float | None) -> float:
    if retry_after: return min(retry_after, 60)       # server told us — believe it
    base = min(2 ** attempt, 30)                      # 1,2,4,8,16,30 cap
return random.uniform(0, base)                    # FULL jitter (decorrelates herds)
def reliable_call(fn, *, max_attempts=5, breaker: Breaker, deadline_s=45):
    """Retry fn() with classified errors, backoff, breaker, and a hard deadline."""
    t0 = time.monotonic()
    for attempt in range(max_attempts):
        if not breaker.allow(): raise CircuitOpen("primary is open")
        remaining = deadline_s - (time.monotonic() - t0)
        if remaining <= 0: raise APITimeoutError("deadline exhausted")
        try:
            out = fn(timeout=min(remaining, 30))      # per-try timeout ≤ remaining
            breaker.record(ok=True); return out
        except NON_RETRY:
            breaker.record(ok=True); raise # our bug, not their outage
except RETRYABLE as e:
            breaker.record(ok=False)
            if attempt == max_attempts - 1: raise
            time.sleep(min(backoff_s(attempt, getattr(e, "retry_after", None)),
                           max(remaining - 1, 0)))

# ---- fallback chain: try primary, then alternates, sharing one deadline -------
BREAKERS = {name: Breaker() for name in ("primary", "alt_region", "alt_provider")}

def call_llm(messages, tools, deadline_s=45):
    last = None
for name, fn in (("primary",      lambda **k: primary.chat(messages, tools, **k)),
                     ("alt_region",   lambda **k: alt_r.chat(messages, tools, **k)),
                     ("alt_provider", lambda **k: alt_p.chat(messages, tools, **k))):
        try:
            return reliable_call(fn, breaker=BREAKERS[name],
                                 max_attempts=3, deadline_s=deadline_s)
        except (CircuitOpen, *RETRYABLE) as e:
            last = e; continue # next hop in the chain
raise last                                        # all hops down: surface it

Design notes worth stealing: full jitter (uniform 0..base) rather than base+jitter — when 400 workers retry a provider blip simultaneously, decorrelation is what prevents the self-inflicted second outage. Per-try timeout ≤ remaining deadline — otherwise attempt 1 eats the whole budget and "5 attempts" is fiction. A 400 closes the breaker — a bad request means the service is fine and your payload isn't; don't let your own bug lock you out of a healthy provider.

02 — Idempotency: retry-safe side effects

Retries multiply attempts, and agents add a second multiplier: the model may call the same tool twice in one trajectory. Any tool that charges, emails, or creates must be idempotent. The mechanism is a key that makes "do X" mean "do X at most once."

idempotency.py — keys derived from intent, results cachedpython
import hashlib, json

def idem_key(run_id: str, tool: str, args: dict) -> str:
    """Same run + same tool + same args => same key => executed once."""
    blob = json.dumps(args, sort_keys=True)
    return f"{tool}:{hashlib.sha256(f'{run_id}|{blob}'.encode()).hexdigest()[:32]}"
def run_effectful(tool, args, run_id, store) -> str:
    key = idem_key(run_id, tool.name, args)
    # 1 · atomically claim the key (INSERT ... ON CONFLICT DO NOTHING / SETNX)
    state = store.claim(key)                  # -> "new" | "in_flight" | row
if state == "in_flight":
        return "PENDING: identical operation already executing" # don't double-run
if isinstance(state, dict):
        return state["result"]                # replay: return the ORIGINAL result
# 2 · execute, passing the key downstream — payment APIs accept it natively
try:
        result = tool.fn(**args, idempotency_key=key)
        store.finish(key, result)             # persist result for future replays
return result
    except Exception:
        store.release(key)                    # let a retry attempt it again
raise
  • Key scope matters. Keyed on run_id+args: a retry of this request can't double-charge, but the user asking again tomorrow can refund again (correct!). If the business rule is "one refund per order ever," the key is order_id — an idempotency key is a business decision wearing an infrastructure costume.
  • Store the result, not just a flag. A replayed call must return the original outcome ("refund r_8812 issued") so the model's context stays truthful.
  • Pass the key downstream. Stripe-style APIs dedupe on it server-side, covering the crash window between your execute and your finish().

03 — Timeout budgets: a worked example

Timeouts must nest, outermost largest, or the layers fight. Take a chat SLA of p95 ≤ 20s and allocate downward — every inner budget is what's left after its siblings, minus headroom:

LayerBudgetReasoning
Client / load balancer25sSLA + 5s so the LB never kills a nearly-done request
Gateway request timeout22sinside the LB; returns a clean 504 with a request id
Orchestrator run deadline20sthe actual SLA; the loop checks it every iteration
· LLM call #1 (plan/route)6s (2 tries × 3s)small-model call; fast or fallback
· Tool calls (parallel where read-only)4s each, 6s for the batchDB/API lookups; slow tool → partial result note
· LLM call #2 (answer, streaming)8s to first tokenstreaming: after first token, stall-timeout (3s between tokens), not total
Headroom~2sserialization, guardrails, network — it's never zero

The arithmetic discipline: 6+6+8 = 20s of budgeted work fits the 20s deadline only because the deadline is shared — a fast call #1 (800ms) donates its slack to the rest via the remaining computation in reliable_call. And note what falls out: with a 20s deadline you get at most 2 attempts on any single LLM call. "5 retries with exponential backoff" is an async-job policy (there, with a 10-min deadline, 5 attempts and 30s sleeps are fine); on the chat path it's a fairy tale. This is why retry policy must be a parameter, not a constant.

04 — Graceful degradation: decide the fallbacks before the outage

Every dependency gets a written answer to "what do we do when it's down?" — decided in a design review, not improvised at 3am. A partial answer beats a 500, and the user is told it's partial.

Dependency downDegraded behaviorUser-visible noteNever do
Primary LLMfallback chain (region → provider); route to smaller model for simple intentsnone (transparent)queue chat requests "until it's back"
All LLMsstatic help / FAQ search / human handoff"AI assistant is unavailable; here's what I can still do"fake it with canned "AI" answers
Vector DBanswer from model knowledge + conversation only"I can't search the knowledge base right now — this answer may be incomplete"silently answer without RAG as if grounded
Rerankeruse raw vector top-knonefail the request over a quality-only stage
Side-effectful tool (payments)read-only mode: explain, collect intent, enqueue action for later confirmation"I've noted the refund; you'll get a confirmation shortly"retry blindly into an erroring payment API
Session storestateless turn (answer from current message only)"I may have lost our earlier context"crash the turn over lost history
Observability backendbuffer locally, drop if full — samplednoneblock or fail requests because tracing is down

Fallback & circuit breaker

If the primary model/region fails, fall back to another. Trip a breaker after repeated failures so you fail fast instead of hammering a dead dependency — the module above is the drop-in.

Idempotency

Tools with side effects (charge, email, create) must be safe to retry — use idempotency keys so a retry doesn't double-charge, and scope the key to the business rule.

Output validation

Validate structured outputs against a schema; on failure, re-ask or repair. Never trust raw model JSON. Budget the repair loop (max 2 re-asks) or it becomes its own cost bug.

Graceful degradation

Vector DB down? Answer without RAG (and say so). A partial answer beats a 500 — but only if honesty about the degradation is part of the response.

Reliability gotchas that only show up in agents

Retry amplification: gateway retries × orchestrator retries × provider-SDK internal retries = one user click became 27 upstream calls. Retry at ONE layer (the orchestrator); make the others pass errors through. The half-done trajectory: a timeout at step 6 of 8 leaves real side effects behind — on failure, either compensate (undo steps), resume from checkpoint, or report precisely what was done; silently rerunning from step 1 is the worst option, and it's the default. Breaker + fallback interaction: when the primary's breaker opens, the whole fleet stampedes the fallback, which then rate-limits and opens ITS breaker — stagger with per-hop concurrency caps. Validation retries fighting timeouts: a schema-repair re-ask near the deadline yields a second truncated response; check remaining budget before re-asking.

Reliability levers

Verify/critic loops before committing · independent skeptics + majority vote for high-stakes · push exact logic into deterministic code · cap iterations · validate every tool input/output. And underneath all of it: classified retries with full jitter, breakers per dependency, idempotency keys scoped to the business rule, nested timeout budgets, and a degradation matrix written before the outage.
