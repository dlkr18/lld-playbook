Fine-tuning in practice: SFT, LoRA, QLoRA // 8.1

You've exhausted prompting and RAG, and you need consistent behavior — a format, a style, a narrow skill — baked in. Now, and only now, you fine-tune.

Part 8 · Model adaptationChapter 8.1

01 — The decision ladder (always in this order)

1. PROMPTING     behavior change via input           — try first, always
2. RAG / TOOLS   knowledge change                    — NEVER fine-tune to inject facts
3. FINE-TUNING   consistent behavior/format/skill,   — when evals prove 1–2 insufficient,
                 or shrinking a huge prompt             or for latency/cost at scale

The ladder exists because each rung down costs roughly 10× more engineering. A prompt change ships in an hour. A RAG index change ships in a day. A fine-tune needs data curation, a training run, before/after evals, a regression suite, and a serving story — a week if you've done it before, a month if you haven't. Worse, a fine-tune is opaque: when a prompt misbehaves you read it; when an adapter misbehaves you re-train it. So the honest trigger for fine-tuning is a written eval showing prompting plateaued, plus one of: (a) you need a strict output format at very high reliability, (b) you're pasting a 6K-token instruction block into every call and want it amortized into weights, (c) you need a small cheap model to imitate a big one's behavior on a narrow task.

A mini-scenario to keep in mind

You're building a support-ticket triage system. The model must emit strict JSON: {"queue": …, "severity": …, "summary": …} with a fixed taxonomy of 40 queues. Prompting with few-shot examples gets you 91% valid-and-correct; the remaining 9% is format drift and taxonomy confusion, and your 3K-token prompt costs real money at 500K tickets/month. This is the textbook fine-tune: consistent behavior + format + prompt-shrink, no new facts needed. We'll use it throughout this chapter.

02 — The methods

MethodWhat trainsWhen
Full fine-tuningall weightsrarely you — expensive, catastrophic forgetting, whole new model to serve
LoRAsmall low-rank adapters ΔW = B·A (rank 8–64) injected into attention/MLP projections; base frozenthe default. ~0.1–1% of params train; adapters are swappable per task on one base
QLoRALoRA on a 4-bit-quantized basefine-tune a 7–13B model on a single 24–48GB GPU
Distillationa small model mimics a big one's outputscompress capability for cheap serving

Why low-rank works: the change needed to specialize a model is far simpler than the model itself — a low-rank matrix (remember SVD from Part 1) captures it. That's the whole trick. Concretely: a frozen weight matrix W of shape 4096×4096 has 16.8M parameters; a rank-16 LoRA on it adds B (4096×16) and A (16×4096) — 131K parameters, 0.8% of the original — and at inference you compute Wx + (α/r)·B·A·x. At serve time you can merge W' = W + (α/r)·B·A and the adapter costs literally zero latency.

03 — Step 0: curate the data (this is where fine-tunes are won)

Before any trainer runs, you dedupe, filter, and format. Three rules: (1) every example must look exactly like an inference-time conversation, chat template included; (2) near-duplicates teach nothing and inflate epochs — kill them; (3) a bad example hurts more than a good example helps, so filter aggressively. For the triage scenario, we mine 6 months of human-triaged tickets and keep only ones where the human's triage was never re-routed later (a free quality label).

curate.py — dedupe + quality filter before any trainingpython
import json, hashlib, re
from datasets import Dataset

RAW = [json.loads(l) for l in open("tickets_raw.jsonl")]   # ~50K mined examples
def normalize(text: str) -> str:
    # collapse whitespace + lowercase so trivial variants hash identically
return re.sub(r"\s+", " ", text.strip().lower())

def quality_ok(ex: dict) -> bool:
    """Cheap deterministic filters first — they remove most junk for free."""
    out = ex["label"]                       # the human triage decision
if out["queue"] not in QUEUE_TAXONOMY:  # stale queue names from old tooling
return False
if ex["rerouted_later"]:                # human got it wrong → not gold
return False
if len(ex["ticket_text"]) < 40:         # empty/auto-generated tickets
return False
if len(ex["ticket_text"]) > 8000:       # truncation risk at train time
return False
return True
# 1) exact/near dedupe on normalized input text
seen, kept = set(), []
for ex in filter(quality_ok, RAW):
    h = hashlib.sha1(normalize(ex["ticket_text"]).encode()).hexdigest()
    if h in seen:
        continue
    seen.add(h)
    kept.append(ex)

# 2) enforce label balance — cap any single queue at 5% of the set,
#    otherwise "password_reset" (30% of traffic) dominates the gradient
from collections import Counter
cap = int(0.05 * len(kept))
counts, balanced = Counter(), []
for ex in kept:
    q = ex["label"]["queue"]
    if counts[q] < cap:
        counts[q] += 1
        balanced.append(ex)

print(f"raw={len(RAW)} → quality={len(kept)} → balanced={len(balanced)}")
# typical (illustrative): raw=50000 → quality=19400 → balanced=6200
Dataset.from_list(balanced).train_test_split(test_size=0.05, seed=42) \
       .save_to_disk("triage_ds")   # the 5% test split is SACRED — never train on it

For fuzzier dedup (paraphrased duplicates), embed each input and drop pairs with cosine similarity > 0.95 — same idea as RAG dedup (Part 7). 6,200 excellent examples is a large set for a narrow-format task; 1–3K often suffices. Data quality ≫ quantity is not a slogan, it's the observed scaling behavior of SFT: quality sets the ceiling, quantity just gets you to it faster.

04 — The complete QLoRA run (Hugging Face TRL + PEFT — the de-facto open stack)

The original snippet, now grown into the whole thing: 4-bit load, chat-template formatting, LoRA config, training args, eval before/after, and adapter save/merge.

qlora_triage.py — end-to-end QLoRA fine-tune of an 8B model on one 24GB GPUpython
import torch
from datasets import load_from_disk
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, prepare_model_for_kbit_training
from trl import SFTTrainer, SFTConfig

BASE = "meta-llama/Llama-3.1-8B-Instruct"
# ── 1. load the base in 4-bit (NF4) — this is the "Q" in QLoRA ──────────────
bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",            # NormalFloat4: information-optimal for
    bnb_4bit_use_double_quant=True,       #   normally-distributed weights
    bnb_4bit_compute_dtype=torch.bfloat16 # matmuls dequantize to bf16 on the fly
)
model = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb,
                                             device_map="auto")
model = prepare_model_for_kbit_training(model)  # grad checkpointing hooks, casts
tok = AutoTokenizer.from_pretrained(BASE)

# ── 2. format examples with the model's OWN chat template ───────────────────
SYSTEM = "You are a ticket triage engine. Reply with JSON only."
def to_messages(ex):
    return {"messages": [
        {"role": "system",    "content": SYSTEM},
        {"role": "user",      "content": ex["ticket_text"]},
        {"role": "assistant", "content": json.dumps(ex["label"])},
    ]}
ds = load_from_disk("triage_ds").map(to_messages)
# SFTTrainer applies tok.apply_chat_template and (with the default collator)
# masks loss to assistant tokens — you train the ANSWER, not the question.
# ── 3. LoRA config — see the decision table below for r/alpha/targets ───────
peft_cfg = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05, bias="none",
    task_type="CAUSAL_LM",
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj"],   # attn + MLP
)

# ── 4. training args — small LR, few epochs, checkpoint every epoch ──────────
args = SFTConfig(
    output_dir="triage-qlora",
    num_train_epochs=2,                    # small sets memorize by epoch 3
    per_device_train_batch_size=2,
    gradient_accumulation_steps=8,         # effective batch 16
    learning_rate=2e-4,                    # LoRA tolerates ~10× full-FT LR
    lr_scheduler_type="cosine", warmup_ratio=0.03,
    bf16=True, gradient_checkpointing=True,
    max_length=4096, packing=False,        # packing off: keep examples intact
    logging_steps=10, eval_strategy="epoch", save_strategy="epoch",
    load_best_model_at_end=True, metric_for_best_model="eval_loss",
)

trainer = SFTTrainer(model=model, args=args, peft_config=peft_cfg,
                     train_dataset=ds["train"], eval_dataset=ds["test"],
                     processing_class=tok)

# ── 5. eval BEFORE, train, eval AFTER — never skip the before ────────────────
print("pre-train eval:", trainer.evaluate())   # baseline eval_loss on held-out
trainer.train()
print("post-train eval:", trainer.evaluate())

# ── 6. save the adapter (tiny) and optionally merge (zero-latency serving) ───
trainer.save_model("triage-qlora/adapter")     # ~170 MB of safetensors, not 16 GB

merged = trainer.model.merge_and_unload()      # W' = W + (α/r)·B·A, adapter gone
merged.save_pretrained("triage-merged")        # a normal model dir; vLLM-servable
tok.save_pretrained("triage-merged")
# alternative: skip the merge and let vLLM serve base + many adapters:
#   vllm serve BASE --enable-lora --lora-modules triage=triage-qlora/adapter

eval_loss going down is necessary, not sufficient. The eval that matters is task-level: run your frozen test tickets through the tuned model, parse the JSON, and score queue accuracy and format validity — plus a regression probe of ~50 generic instructions ("summarize this", "write a python function…") judged against the base model, to catch capability damage. In the triage scenario a realistic (illustrative) outcome: valid-JSON rate 99.7% (was 96%), queue accuracy 96.4% (was 91%), regression probe within noise, and the 3K-token instruction prompt shrinks to a 1-line system message — at 500K tickets/month and ~3K saved input tokens each, that's ~1.5B input tokens/month you stop paying for.

05 — Choosing r, alpha, and target modules

Intuition first: r is the capacity of the change you're learning; alpha scales how loudly the adapter speaks at inference (effective scale = α/r — the common convention is α = 2r, giving scale 2); target modules decide where the model can change. Format/style tasks need less capacity than skill/domain tasks.

Task shaperalphatarget_modulesWhy
Output format / JSON schema / tone8–1616–32q_proj, v_projsmall behavioral nudge; attention re-weighting suffices; smallest adapter, least forgetting
Style + domain vocabulary (support voice, legal register)16–3232–64all attention (q,k,v,o_proj)needs to reshape what the model attends to, not just how it phrases
Narrow skill (SQL dialect, DSL, classification taxonomy)16–642×rattention + MLP (gate,up,down_proj)MLP layers hold "knowledge-ish" transformations; skills live there — the QLoRA paper found all-linear-layers matters more than large r
Heavy domain adaptation (new language, big corpus)64–1282×rall linear layers, consider higher dropoutapproaching full-FT territory; also reconsider whether you want full FT

Two practical notes. First, r has sharply diminishing returns — the QLoRA ablations showed target-module coverage beats rank; going 16→64 on q,v only is usually worse than staying at 16 and adding MLP targets. Second, if you double r, halve nothing else: keep α = 2r so the effective scale stays put, otherwise you've silently changed the learning dynamics too.

06 — Worked example — GPU memory for an 8B QLoRA run

Llama-3.1-8B, NF4 base, LoRA r=16 on all linear layers, seq 4096, micro-batch 2,
gradient checkpointing ON, paged 8-bit Adam. All numbers approximate.

BASE WEIGHTS (frozen, 4-bit)   8e9 params × 0.5 byte            ≈ 4.0 GB
  + quant metadata (scales, double-quant)                        ≈ 0.4 GB
LoRA PARAMS   r×(d_in+d_out) summed over targets:
  per layer:  q 131K + k 82K + v 82K + o 131K
              + gate 295K + up 295K + down 295K  ≈ 1.31M
  × 32 layers                                    ≈ 42M params
  adapter weights (bf16)        42M × 2 B                        ≈ 0.08 GB
  gradients (fp32)              42M × 4 B                        ≈ 0.17 GB
  Adam m+v (8-bit paged)        42M × 2 B                        ≈ 0.08 GB
ACTIVATIONS  with grad ckpt: ~sqrt-depth memory; at seq 4096,
  micro-batch 2, hidden 4096                                     ≈ 3–5 GB
KV/misc/CUDA context/fragmentation headroom                      ≈ 1–2 GB
                                                        ─────────────────
TOTAL                                                   ≈ 9–12 GB  → fits a 24 GB
                                                          GPU with room to spare
Sanity checks the formula gives you for free:
  • same run WITHOUT quantization (bf16 base = 16 GB): ≈ 21–24 GB — the edge of 24 GB
  • full fine-tune bf16 + Adam fp32: 16 (w) + 32 (grad fp32? no—16 bf16)
    realistically ≥ 16+16+64 = 96 GB before activations → multi-GPU territory
  • double the sequence length → activations roughly double; batch too

The takeaway shape: in QLoRA, the frozen quantized base is the big rock (4.4 GB), the trainable state is trivial (<0.4 GB), and activations are the knob you actually tune — via micro-batch size, sequence length, and gradient checkpointing. When you OOM, cut micro-batch and raise gradient_accumulation_steps; the effective batch (and the math) is unchanged.

07 — What actually determines success (not the trainer flags)

  1. Data quality ≫ quantity. 1K excellent, diverse, deduplicated examples beat 50K scraped ones. Format them exactly like inference-time prompts — same system message, same chat template, same truncation policy.
  2. Eval before/after on a held-out set — including regression checks on general ability, not just the target task.
  3. Watch for overfit: small sets memorize in 1–3 epochs; track eval loss per epoch and keep load_best_model_at_end=True.
  4. One change per run. If you touch data, r, and LR together, the win (or loss) is unattributable. Fine-tuning is an experiment; run it like one.

Failure modes

  • Fine-tuned to add facts → confident hallucination (facts belong in RAG). SFT teaches the model to sound like your data; it does not build a retrievable knowledge store.
  • Style leakage — the model now answers everything in the tuned register. Your triage model starts emitting JSON when someone asks it a plain question. Mitigate with a small % of general chat data mixed in, and a system-message gate.
  • Forgetting — narrow tuning degrades general instruction-following; measure it with a fixed regression probe set, or you'll discover it from users.
  • Eval leakage — test examples (or near-duplicates of them) in training data → fake wins. This is why dedup runs before the train/test split, never after.
  • Chat-template mismatch — training with one template and serving with another (or double-applying it) is the most common silent killer: loss looks fine, live outputs are subtly broken. Print one fully-rendered training example and one live prompt; diff them by eye.
  • Loss on the prompt tokens — forgetting completion-only masking makes the model learn to imitate tickets, not triage. Check that your collator masks user/system tokens.
  • Quantized-merge drift — merging a LoRA into a 4-bit base and re-quantizing can shift behavior vs adapter-on-base serving. Eval the exact artifact you deploy.

Takeaways

Fine-tune for behavior, never facts. QLoRA = 4-bit frozen base + tiny trainable adapters; an 8B run fits in ~10–12 GB. Curation (dedupe, filter, balance, exact inference formatting) is most of the work. r matters less than target-module coverage; α = 2r. Eval before and after, at the task level, with a regression probe — and eval the artifact you actually deploy.
