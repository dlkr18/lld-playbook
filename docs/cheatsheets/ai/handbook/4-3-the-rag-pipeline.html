RAG: retrieve, augment, generate // 4.3

Retrieval-Augmented Generation is how you make a model answer from your data without retraining it — and the #1 cure for hallucination.

Part 4 · Knowledge & RAGChapter 4.3

01 — The pattern

question ─► embed ─► vector search ─► top-K chunks ─┐
                                                    ▼
              prompt = [system] + [retrieved facts] + [question]
                                                    ▼
                                    LLM ─► grounded answer (+ citations)

That's the whole trick: instead of hoping the model memorized your facts, you look the facts up and paste them into the prompt, then instruct the model to answer only from them. The LLM becomes a reading-comprehension engine over text you control. Everything else in this chapter — chunking, hybrid retrieval, reranking, packing, citation checks — is engineering to make the pasted facts be the right facts.

Why not just fine-tune?

Fine-tuning bakes knowledge into weights: expensive to update (retrain per docs change), impossible to cite ("which weight said that?"), and leaky across users. RAG keeps knowledge in a database: update = upsert, cite = point at the chunk, per-user security = a metadata filter. See the takeaway box at the end.

02 — Phase 1 — Ingestion (offline)

The original sketch, kept for orientation:

ingest.py — the minimal sketchpython
def chunk(text, size=800, overlap=120):     # split docs into overlapping windows
    toks = tok.encode(text)
    return [tok.decode(toks[i:i+size]) for i in range(0, len(toks), size-overlap)]

chunks = [c for d in docs for c in chunk(d.text)]
vectors = embed_batch(chunks)                   # embed many at once (cheaper)
db.upsert("kb", [{"id":i,"vector":v,"payload":{"text":c,"src":d.id}}
                  for i,(c,v) in enumerate(zip(chunks,vectors))])

And here is the production-shaped version: structure-aware chunking, stable IDs (so re-ingesting doesn't duplicate), batched embedding with retry, and metadata that the query phase will need. This is a complete module, not a fragment:

ingest_full.py — parse → chunk → embed → upsert, idempotentlypython
import hashlib, time
from dataclasses import dataclass

CHUNK_TOKENS, OVERLAP, EMBED_BATCH = 700, 100, 128
@dataclass
class Chunk:
    id: str; text: str; doc_id: str; title: str; section: str; pos: int
def parse(raw: bytes, mime: str) -> tuple[str, list[tuple[str, str]]]:
    """Return (title, [(section_heading, section_text), ...]).
    Real life: pymupdf for PDF, BeautifulSoup for HTML, markdown headings for .md.
    Parsing is where most silent garbage enters — log what you extract."""
    ...

def chunk_section(heading: str, text: str, tok) -> list[str]:
    """Token-window split WITHIN a section; sections never bleed together."""
    toks = tok.encode(text)
    step = CHUNK_TOKENS - OVERLAP
    return [tok.decode(toks[i:i + CHUNK_TOKENS]) for i in range(0, max(len(toks), 1), step)]

def build_chunks(doc_id: str, raw: bytes, mime: str, tok) -> list[Chunk]:
    title, sections = parse(raw, mime)
    out = []
    for heading, text in sections:
        for pos, piece in enumerate(chunk_section(heading, text, tok)):
            body = f"{title} — {heading}\n\n{piece}" # prepend context: cheap, big win
            cid = hashlib.sha1(f"{doc_id}:{heading}:{pos}:{body}".encode()).hexdigest()
            out.append(Chunk(cid, body, doc_id, title, heading, pos))
    return out

def embed_batch(texts: list[str], client, retries: int = 3) -> list[list[float]]:
    """Batched + retried. Never embed one-by-one: 100k chunks = 100k round-trips."""
    vecs = []
    for i in range(0, len(texts), EMBED_BATCH):
        batch = texts[i:i + EMBED_BATCH]
        for attempt in range(retries):
            try:
                vecs.extend(client.embed(batch)); break
except TransientError:
                if attempt == retries - 1: raise
                time.sleep(2 ** attempt)                    # backoff: 1s, 2s, 4s
return vecs

def ingest(docs, db, client, tok):
    chunks = [c for d in docs for c in build_chunks(d.id, d.raw, d.mime, tok)]
    vecs = embed_batch([c.text for c in chunks], client)
    db.upsert("kb", [                                       # sha1 id ⇒ re-runs are no-ops
        {"id": c.id, "vector": v,
         "payload": {"text": c.text, "doc_id": c.doc_id, "title": c.title,
                     "section": c.section, "pos": c.pos, "ingested_at": time.time()}}
        for c, v in zip(chunks, vecs)])
    print(f"ingested {len(chunks)} chunks from {len(docs)} docs")

Worked cost check (illustrative prices): 5,000 docs → ~40,000 chunks × ~700 tokens = 28M tokens. At $0.02/M tokens for a small embedding API that's $0.56 total, in ~40k/128 ≈ 313 batched calls. Ingestion cost is almost never the problem; ingestion quality is.

Chunking strategies — and where each one breaks

Take one concrete document: your Employee Handbook, a 40-page PDF with sections like "4. Leave Policy" containing "4.2 Parental Leave," which holds a paragraph of eligibility rules, a table of leave durations by country, and a note referencing "the process in section 7.1."

StrategyHowWhere it breaks on the handbook
Fixed token window (the sketch above)Every N tokens, with overlapSplits the country table in half mid-row; one chunk starts "…and Germany: 14 weeks" with no clue it's about parental leave. A window can also straddle "4.1 Sick Leave" and "4.2 Parental Leave," producing a chunk that matches both queries and answers neither.
Sentence/paragraph splitBreak at sentence or blank-line boundaries, merge to target sizeBetter prose integrity; still blind to structure — the eligibility paragraph is separated from its table, so "how long is parental leave in Germany?" retrieves the rules but not the number.
Structure-aware (recursive by heading, used in ingest_full.py)Split at headings; window only inside long sections; prepend title+heading to each chunkThe right default. Still breaks on: giant tables (needs table-to-text or row-wise chunks), and the "see section 7.1" cross-reference — the answer lives in a chunk that shares no vocabulary with the query (parent-child retrieval helps; next chapter).
Semantic chunkingEmbed sentences, cut where adjacent similarity dropsElegant, ~2× embedding cost at ingest, marginal wins over structure-aware on well-formatted docs; shines mainly on unstructured transcripts with no headings.

The two rules that matter

(1) A chunk must make sense read alone, because that's exactly how both the embedder and the LLM will read it. Prepending title — section to every chunk is the cheapest retrieval upgrade in this book. (2) Start at ~600–1,000 tokens with ~15% overlap, structure-aware; only get fancier after evals (next chapter) tell you where it breaks.

03 — Phase 2 — Query (online)

The original sketch:

answer.py — the minimal sketchpython
def answer(q):
    hits = db.search("kb", embed([q])[0], limit=30)   # ① over-fetch candidates
    hits = rerank(q, hits)[:5]                       # ② rerank, keep best 5 (see next ch)
    ctx = "\n\n".join(f"[{i}] {h.payload['text']}" for i,h in enumerate(hits))
    return llm(system="Answer ONLY from sources. Cite [n]. If absent, say you don't know.",
               user=f"SOURCES:\n{ctx}\n\nQ: {q}")

The production query path has four stages: hybrid retrieval → fusion → rerank → pack. Each exists because the previous one alone fails on some query class (embeddings miss exact codes; BM25 misses paraphrase; both return "roughly related" where you need "actually answers it"; and the winners must still fit a token budget).

query_path.py — hybrid search, RRF fusion, cross-encoder rerankpython
from collections import defaultdict

def rrf_fuse(rankings: list[list[str]], k: int = 60) -> list[str]:
    """Reciprocal Rank Fusion: score(d) = Σ 1/(k + rank_i(d)).
    Rank-based, so it never has to compare cosine scores with BM25 scores —
    that's the whole reason RRF beats naive score averaging."""
    score = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):            # rank 0 = best
            score[doc_id] += 1.0 / (k + rank + 1)
    return sorted(score, key=score.get, reverse=True)

def retrieve(q: str, db, bm25, embedder, n: int = 30) -> list[dict]:
    dense  = [h.id for h in db.search("kb", embedder.embed([q])[0], limit=n)]
    sparse = [h.id for h in bm25.search(q, limit=n)]
    fused  = rrf_fuse([dense, sparse])[:n]
    return db.get_many("kb", fused)                        # hydrate payloads
def rerank(q: str, hits: list[dict], ce, keep: int = 6) -> list[dict]:
    """Cross-encoder reads (query, chunk) TOGETHER — token-level interaction the
    bi-encoder can't do. ~50-300ms for 30 pairs (illustrative); worth it."""
    pairs  = [(q, h["payload"]["text"]) for h in hits]
    scores = ce.predict(pairs)          # e.g. BAAI/bge-reranker-v2-m3, cohere rerank
    ranked = sorted(zip(hits, scores), key=lambda x: -x[1])
    return [h for h, s in ranked[:keep] if s > 0.2]        # drop confident junk

Worked example of why RRF, with real ranks: query "error E-4417 on the KX-220". Dense ranking puts the true chunk at rank 27 (alphanumeric soup embeds badly); BM25 puts it at rank 1. RRF (k=60): 1/(60+28) + 1/(60+2) ≈ 0.0114 + 0.0161 = 0.0275 — comfortably above a chunk that's rank 8 in dense only (1/69 ≈ 0.0145). One list's strong vote rescues the other's miss, with zero tuning.

Packing the context under a token budget

Reranked chunks still must fit the prompt without starving the answer. Naive truncation cuts mid-sentence in the middle of your best chunk; budget-aware packing keeps whole chunks in rank order:

pack.py — greedy packing with a hard token budget, dedup includedpython
def pack_context(hits: list[dict], tok, budget_tokens: int = 4000) -> tuple[str, list[dict]]:
    """Keep whole chunks in rerank order until the budget is spent.
    Never truncate a chunk mid-way: a half-fact is worse than no fact."""
    used, parts, kept, seen_docs = 0, [], [], defaultdict(int)
    for h in hits:
        p = h["payload"]
        if seen_docs[p["doc_id"]] >= 3:      # diversity: max 3 chunks per doc
continue
        t = len(tok.encode(p["text"]))
        if used + t > budget_tokens:
            continue # skip, try next (smaller) chunk
        n = len(kept) + 1
        parts.append(f"[{n}] ({p['title']} › {p['section']})\n{p['text']}")
        kept.append(h); used += t + 20 # +20: label overhead
        seen_docs[p["doc_id"]] += 1
return "\n\n".join(parts), kept

Worked budget (illustrative): 8k-token prompt target = 400 system + 4,000 sources + 100 question + headroom; at ~700 tokens/chunk that's 5–6 chunks. At an assumed $3/M input tokens, each query's context costs ~$0.013 — which is why "just stuff 50 chunks in a 200k window" is a cost and quality mistake: models attend less reliably to the middle of huge contexts ("lost in the middle"), and irrelevant chunks actively invite the model to answer from the wrong one.

Trust, but verify: citation checking

The prompt says "cite [n]"; models mostly comply and occasionally cite a source that doesn't support the sentence. A cheap post-hoc check catches the worst of it before the user sees it:

cite_check.py — verify every [n] exists and plausibly supports its sentencepython
import re

def check_citations(answer: str, kept: list[dict], embedder,
                    min_sim: float = 0.45) -> dict:
    """Two-tier check: (1) structural — every [n] must reference a real source;
    (2) semantic — each cited sentence should be similar to its cited chunk.
    Cheap screen; escalate flagged sentences to an LLM judge (next chapter)."""
    issues, n_src = [], len(kept)
    sents = re.split(r"(?<=[.!?])\s+", answer)
    for s in sents:
        refs = [int(m) for m in re.findall(r"\[(\d+)\]", s)]
        for r in refs:
            if not (1 <= r <= n_src):
                issues.append({"sentence": s, "ref": r, "kind": "dangling"})
                continue
            src = kept[r - 1]["payload"]["text"]
            sim = embedder.similarity(s, src)          # cosine of the two embeddings
if sim < min_sim:
                issues.append({"sentence": s, "ref": r, "kind": "weak_support",
                               "sim": round(float(sim), 2)})
    has_claims = any(len(s) > 40 for s in sents)
    cited      = any(re.search(r"\[\d+\]", s) for s in sents)
    if has_claims and not cited:
        issues.append({"kind": "no_citations_at_all"})
    return {"ok": not issues, "issues": issues}

# usage: if not ok → retry with a sterner instruction, or show the answer
# with flagged sentences marked "unverified" — never silently ship them.

Where fresh RAG pipelines actually fail

1. Garbage parsing: PDFs extracted as two interleaved columns, headers/footers repeated into every chunk, tables flattened to word soup — the DB happily embeds it all. Read 20 random chunks from your index; it's the highest-ROI debugging act in RAG. 2. Embedder mismatch: ingested with model A, querying with model B (or with/without the "query:" prefix) — everything "works," recall is silently terrible. Store the model name in the collection metadata and assert at query time. 3. Stale index: docs updated, vectors not; deterministic chunk IDs + re-ingest-on-change (and delete vectors of removed docs — orphans love to get retrieved). 4. The over-trusting prompt: without "if the sources don't contain it, say so," the model backfills from pretraining and your citations decorate a hallucination. 5. Top-K too small: K=3 with mediocre retrieval means the answer often simply isn't in the prompt — over-fetch then rerank, never trust raw top-3.

04 — Mini-scenario: "the bot ignores our docs"

You ship a support bot over 1,200 product PDFs. QA reports: "asked about the refund window, bot said 30 days, docs say 14." You check retrieval: the right chunk was retrieved — at position 7 of 8, after five chunks about shipping. The model, reading mostly-irrelevant context, answered from its pretraining instead. The fix was not the prompt: reranking moved the refund chunk to position 1, packing dropped the shipping noise, and the citation checker would have flagged the "30 days" sentence (cosine 0.21 against its cited chunk) regardless. Ship order: hybrid retrieval → rerank → pack → cite-check. Each stage exists because this exact ticket happens without it.

RAG vs fine-tuning

RAG adds knowledge/facts (fresh, private, citable). Fine-tuning changes behavior/style. For "know my docs," RAG wins — it's cheaper, updatable, and traceable. They're complementary, not rivals: fine-tune a model to follow your answer format, RAG to know this week's facts.
