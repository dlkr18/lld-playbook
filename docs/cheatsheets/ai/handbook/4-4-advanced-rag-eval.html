Making RAG actually good // 4.4

Basic RAG is easy; reliable RAG is where the work is. Most failures are retrieval failures.

Part 4 · Knowledge & RAGChapter 4.4

01 — The foundation levers (from the last chapter)

Chunking strategy

Too big → noisy matches; too small → lost context. Start ~600–1000 tokens with ~15% overlap. Better: split on structure (headings, sections), keep metadata.

Reranking

Retrieve 30 candidates with vectors (fast, fuzzy), then a cross-encoder reranker scores each (query, chunk) pair precisely and keeps the top 5. Biggest quality lever after chunking.

Hybrid search

Fuse vector similarity with keyword/BM25 so exact terms (product codes, names, acronyms) aren't missed by embeddings.

Query rewriting

Use an LLM to expand/clarify the query (or split a compound question) before retrieval — improves recall on messy user input.

Agentic RAG

Make retrieval a tool an agent calls iteratively — search, read, decide it needs more, search again. (Bridges to Part 6.)

GraphRAG

Build a knowledge graph from documents and retrieve over entities/relations for multi-hop questions.

02 — The advanced toolbox — mechanism, payoff, and when to reach for each

Parent-child retrieval (small-to-big). Mechanism: index small chunks (150–300 tokens — precise vectors, one idea each), but store on each a pointer to its parent (the full section, 1,500–3,000 tokens). Search over the children; feed the LLM the parents. Why it works: retrieval precision and generation context want opposite chunk sizes; this decouples them. When it pays: structured docs (manuals, contracts, policies) where the answer's evidence is one paragraph but understanding it needs the whole section — like the "see section 7.1" cross-reference from the handbook example last chapter. Cost: ~nothing at query time; slightly bigger index.

parent_child.py — search small, return bigpython
def ingest_parent_child(sections, db, embedder, child_tokens=250):
    for parent_id, section_text in sections:               # parent = whole section
        db.put_parent(parent_id, section_text)             # plain KV store is fine
for i, child in enumerate(split_tokens(section_text, child_tokens)):
            db.upsert("kb_children", [{
                "id": f"{parent_id}:{i}",
                "vector": embedder.embed([child])[0],
                "payload": {"text": child, "parent_id": parent_id}}])

def retrieve_parents(q, db, embedder, k=4):
    hits = db.search("kb_children", embedder.embed([q])[0], limit=20)
    seen, parents = set(), []
    for h in hits:                                          # dedup: siblings share a parent
        pid = h.payload["parent_id"]
        if pid not in seen:
            seen.add(pid); parents.append(db.get_parent(pid))
        if len(parents) == k: break
return parents

Multi-query retrieval. Mechanism: have an LLM rewrite the user's question into 3–5 variants (paraphrase, decomposition, vocabulary shift), retrieve for all of them in parallel, fuse with RRF (last chapter). Why it works: a single embedding of a vague query is one dart at the board; five phrasings are five darts, and RRF rewards chunks that multiple phrasings agree on. When it pays: messy real-user queries ("it's broken again after the update??") and compound questions; typically worth several points of recall (illustrative) for one cheap LLM call + parallel searches.

multi_query.py — rewrite, fan out, fusepython
def multi_query_retrieve(q, llm, db, embedder, n_variants=4, k=30):
    prompt = ("Rewrite the user question as {n} search queries that differ in wording "
"and angle. If it contains multiple sub-questions, split them. "
"One per line, no numbering.\n\nQ: {q}").format(n=n_variants, q=q)
    variants = [q] + [v.strip() for v in llm(prompt).splitlines() if v.strip()][:n_variants]
    rankings = []
    for v in variants:                                     # parallelize in production
        hits = db.search("kb", embedder.embed([v])[0], limit=k)
        rankings.append([h.id for h in hits])
    return rrf_fuse(rankings)[:k]                          # rrf_fuse from last chapter

HyDE (Hypothetical Document Embeddings). Mechanism: queries and documents live in slightly different regions of embedding space (questions don't look like answers). So: ask an LLM to hallucinate a plausible answer, embed that, and search with it — the fake answer's vector lands near real answer chunks. The hallucination is never shown to anyone; it's only a search probe. When it pays: short/underspecified queries over prose-heavy corpora, and zero-shot domains where you have no click data to tune on. Skip it when queries already resemble the docs (e.g. code search with code queries), and note it adds one LLM call of latency to every query.

hyde.py — search with a hallucinated answerpython
def hyde_retrieve(q, llm, db, embedder, k=30):
    fake = llm(f"Write a short factual paragraph that would answer:\n{q}",
               max_tokens=150)                             # wrong facts are OK —
    v = embedder.embed([fake])[0]                          # only its STYLE matters
return db.search("kb", v, limit=k)
# production: average embed(q) and embed(fake), or run both and RRF-fuse.

Query routing. Mechanism: a small classifier (often just an LLM call with a fixed label set) decides where a query should go: which collection (HR docs vs engineering wiki), which strategy (SQL over the orders table vs vector search over manuals), or "no retrieval needed" (chit-chat, math). When it pays: the moment you have more than one corpus or tool — searching everything for every query burns money and pollutes context with cross-domain noise. A misroute is catastrophic for that query, so keep a fallback ("search all") when the router is unsure.

Multi-hop retrieval. Mechanism: some questions can't be answered by any single chunk: "Which customers of the acquired company were affected by the March outage?" needs hop 1 (who was acquired) → hop 2 (their customers) → hop 3 (outage scope). Iterative retrieve→read→reformulate loops do this — which at the limit is exactly agentic RAG: retrieval as a tool in a loop, the agent deciding after each read whether it has enough (Part 6). When it pays: investigative and analytical questions; costs multiple sequential LLM+search rounds, so route only genuinely multi-hop queries into it.

GraphRAG. Mechanism: at ingest time, an LLM extracts entities and relations from every chunk into a knowledge graph (and pre-summarizes communities of related entities). At query time you retrieve subgraphs — entities, their relations, community summaries — instead of (or alongside) text chunks. When it pays: "global" questions no single chunk answers ("what are the main themes across all incident reports this year?") and relationship-hopping questions. Costs are real: one LLM pass over the whole corpus at ingest (often more expensive than embedding by 10–100×, illustrative) and a graph to keep fresh. Treat it as a heavy speciality tool, not a default.

Contextual compression. Mechanism: after retrieval, shrink what you pass on — either extractively (keep only sentences relevant to the query; a small LLM or even embedding-similarity-per-sentence works) or by summarizing each chunk w.r.t. the query. When it pays: long chunks with low signal density (meeting transcripts, email threads), or when you must fit many sources into a small budget. It's a latency/cost trade: you spend a cheap-model call to save expensive-model tokens — worth it roughly when compressed context is under half the original.

Order of operations

Do not start here. The sequence that pays: solid chunking → hybrid search → reranking → an eval set → and only then pick from this table the technique whose failure mode your eval actually shows. Every technique above adds latency, cost, or an ingest pipeline; adopted blind, they add all three and no measured quality.

03 — Evaluation: the harness that makes all of this tunable

Measure retrieval and generation separately

Recall@k: is the correct chunk in the top-k? (retrieval quality). Faithfulness: is the answer actually supported by the retrieved text? (generation quality). If recall@k is low, no prompt tweak helps — fix chunking/embedding/rerank first. Tools: Ragas, TruLens, or your own eval set — which is ~80 lines, below, and never surprises you with a framework upgrade.

You need 30–100 eval questions with known gold chunks. Build them from support tickets, or generate synthetically: sample chunks, ask an LLM "write a question this chunk answers" (have a human skim them — a bad eval set is worse than none, because you'll tune toward it).

rag_eval.py — recall@k + faithfulness judge, end to endpython
import json
from dataclasses import dataclass

@dataclass
class EvalCase:
    question: str
    gold_chunk_ids: set[str]        # chunk(s) that contain the answer
    reference_answer: str = "" # optional, for answer-quality checks
def recall_at_k(cases: list[EvalCase], retrieve_fn, k: int = 5) -> float:
    """retrieve_fn(question) -> ranked list of chunk ids."""
    hit = sum(1 for c in cases
              if set(retrieve_fn(c.question)[:k]) & c.gold_chunk_ids)
    return hit / len(cases)

def mrr(cases, retrieve_fn, k: int = 20) -> float:
    """Mean reciprocal rank: rewards putting gold at position 1, not just top-k."""
    total = 0.0
for c in cases:
        for rank, cid in enumerate(retrieve_fn(c.question)[:k], start=1):
            if cid in c.gold_chunk_ids:
                total += 1.0 / rank; break
return total / len(cases)

FAITH_PROMPT = """You are grading a RAG answer. For EACH claim in the answer,
decide if it is supported by the SOURCES. Reply as JSON:
{{"claims": [{{"claim": "...", "supported": true/false}}], "verdict": "pass"/"fail"}}
"fail" if ANY substantive claim is unsupported.
SOURCES:
{sources}
QUESTION: {q}
ANSWER: {a}"""
def faithfulness(q: str, answer: str, sources: list[str], judge_llm) -> dict:
    raw = judge_llm(FAITH_PROMPT.format(sources="\n---\n".join(sources), q=q, a=answer),
                    temperature=0)                     # judge must be deterministic-ish
try:
        return json.loads(raw)
    except json.JSONDecodeError:
        return {"verdict": "fail", "claims": [], "error": "judge_unparseable"}

def run_eval(cases, retrieve_fn, answer_fn, judge_llm, k=5):
    r_at_k = recall_at_k(cases, retrieve_fn, k)
    _mrr   = mrr(cases, retrieve_fn)
    faith_pass = 0
for c in cases:
        ids     = retrieve_fn(c.question)[:k]
        sources = [get_chunk_text(i) for i in ids]
        ans     = answer_fn(c.question, sources)
        if faithfulness(c.question, ans, sources, judge_llm)["verdict"] == "pass":
            faith_pass += 1
print(f"recall@{k}={r_at_k:.2f}  mrr={_mrr:.2f} "
f"faithfulness={faith_pass/len(cases):.2f}  n={len(cases)}")
    return r_at_k, _mrr, faith_pass / len(cases)
# Run on every pipeline change. 50 cases ≈ 100 LLM calls ≈ a dollar-ish
# (illustrative) — the cheapest regression insurance you will ever buy.

Judge caveats: use a different (and ideally stronger) model as judge than as generator — models grade their own style leniently; spot-check ~20 judge verdicts by hand once to calibrate; and keep the judge prompt frozen while you tune the pipeline, or your metric moves under you.

Walkthrough 1: "answers got worse after we re-ingested"

Support bot, previously fine; after a docs refresh, users report nonsense. You run the harness: recall@5 fell 0.82 → 0.31, faithfulness of what remains is unchanged. Retrieval broke, generation didn't — so you ignore prompts entirely. Bisect the retrieval side: same eval against the old collection still scores 0.82, so it's the new ingest, not the query path. You read 20 random chunks from the new collection: half begin mid-sentence with page-footer text ("Confidential — p. 14 of 88") — the docs team's new PDF export broke your parser, footers got interleaved, and chunk boundaries drifted. Fix the parser's footer stripping, re-ingest, recall@5 = 0.84. Elapsed: an afternoon, because the matrix told you which half of the system to open. Without split metrics you'd have spent that afternoon rewriting the prompt.

Walkthrough 2: "it retrieves the right doc but still answers wrong"

Internal policy bot: for "what's the expense limit for client dinners?", the gold chunk (limit table, $75/head) is retrieved at rank 4 — recall@5 = 1.0 for this case — yet the bot answers "$150," and faithfulness fails with the judge flagging the claim as unsupported. You print the packed context: ranks 1–3 are chunks about travel expenses, one containing "$150 hotel dinner allowance." The model conflated adjacent numbers — a context-noise failure, not retrieval. Fixes in cheapness order: (1) rerank — the cross-encoder puts the client-dinner table at rank 1 and demotes two travel chunks below the packing cutoff; (2) packing diversity cap already limits per-doc chunks; (3) the citation checker now shows the answer's cite pointing at the right chunk with sim 0.71. Faithfulness on the expense slice: 0.55 → 0.93 (illustrative). Note what you did not do: change the model, or the prompt.

Takeaway

"My RAG is dumb" almost always means "my retrieval is bad." Debug the pipeline in order: chunking → embedding model → filters → reranking → prompt. The LLM is usually the last suspect — and the eval harness is what tells you which stage to interrogate, in numbers, before you touch anything.

Exercises

  1. Build a 30-question eval set for a corpus you own (half hand-written from real questions, half LLM-generated and human-skimmed, each with gold chunk ids). Run run_eval() and record your baseline recall@5, MRR, and faithfulness.
  2. Implement parent-child retrieval on that corpus (children ~250 tokens, parents = sections). Compare recall@5 and faithfulness against flat chunking — parent-child often moves the second number more. Explain why in two sentences.
  3. Add multi-query (4 variants + RRF). Measure recall on your 5 vaguest eval questions before/after, and the added latency. Decide — with numbers — whether to enable it for all queries or route only low-confidence ones into it.
  4. Implement HyDE and A/B it against multi-query on the same eval set. Which wins on your corpus, and on which question types? (There is no universal answer; that's the point.)
  5. Break your pipeline on purpose: swap the query-time embedder to a different model, and separately corrupt 20% of chunks with boilerplate. For each sabotage, predict the metric signature from the debugging matrix, then run the harness and check the prediction.
