Deep learning — learned programs from differentiable blocks // 1.3

A neural network is a stack of matrix multiplies with nonlinearities between them, trained by gradient descent. Everything else is engineering to make that stack train stably and generalize.

Part 1 · Math & ML foundationsChapter 1.3

01 — The layer, the stack, the loop

one layer:   h = φ(Wx + b)     φ = nonlinearity (ReLU/GELU). Without φ, stacked layers
                                collapse into ONE linear map — depth would be pointless.
training:    batch → forward pass → loss → backward pass (gradients) → optimizer update → repeat

Why the collapse claim is true, in one line: W₂(W₁x) = (W₂W₁)x — two linear maps compose into one matrix, so a 100-layer purely-linear net has exactly the expressive power of a single layer. The nonlinearity between layers is the entire reason depth buys anything. With it, each layer can carve the space along different bends, and the stack composes them into arbitrarily intricate functions.

Vocabulary that must be reflex: tensors (n-dim arrays; always know your shapes), parameters vs activations (learned weights vs per-input values), batch/epoch, Adam/AdamW (adaptive-step SGD; the default), learning-rate schedules (warmup then decay), residual connections (add input to output → gradients flow through deep stacks), normalization (keep activation scales sane), dropout / weight decay (regularize), mixed precision (fp16/bf16 for speed/memory).

Here is the whole thing, runnable, in one file. Everything you'll ever do with PyTorch — including fine-tuning a 70B model — is a scaled-up version of these 60 lines. Read it until nothing in it is mysterious:

train.py — a complete training run: data, model, loop, evalpython
import torch
import torch.nn as nn
from torch.utils.data import Dataset, DataLoader

torch.manual_seed(0)
device = "cuda" if torch.cuda.is_available() else "cpu"
# ---------- 1. Data: a toy task the loop can actually learn ----------
class TwoMoons(Dataset):
    """Two noisy interleaved half-circles → binary classification."""
def __init__(self, n=2000):
        t = torch.rand(n) * torch.pi
        cls = torch.randint(0, 2, (n,))
        x = torch.stack([torch.cos(t), torch.sin(t)], dim=1)
        x[cls == 1] = -x[cls == 1] + torch.tensor([1.0, 0.5])
        self.x = x + 0.1 * torch.randn(n, 2)      # noise → not separable perfectly
self.y = cls.float()
    def __len__(self):            return len(self.x)
    def __getitem__(self, i):     return self.x[i], self.y[i]

train_ds, val_ds = TwoMoons(2000), TwoMoons(500)
train_dl = DataLoader(train_ds, batch_size=64, shuffle=True)   # shuffle=True: non-negotiable
val_dl   = DataLoader(val_ds, batch_size=256)

# ---------- 2. Model: two layers, one nonlinearity ----------
class MLP(nn.Module):
    def __init__(self, d_in=2, d_hidden=32):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(d_in, d_hidden), nn.ReLU(),
            nn.Linear(d_hidden, 1),            # logit; sigmoid lives in the loss
        )
    def forward(self, x):                      # x: [batch, 2] → [batch]
return self.net(x).squeeze(-1)

model = MLP().to(device)
opt = torch.optim.AdamW(model.parameters(), lr=3e-3, weight_decay=0.01)
loss_fn = nn.BCEWithLogitsLoss()               # numerically stable sigmoid+BCE
# ---------- 3. The loop ----------
def evaluate():
    model.eval()
    correct = total = 0
with torch.no_grad():                      # no graph → no memory bloat
for x, y in val_dl:
            x, y = x.to(device), y.to(device)
            correct += ((model(x) > 0) == y.bool()).sum().item()
            total += len(y)
    model.train()
    return correct / total

for epoch in range(20):
    for x, y in train_dl:
        x, y = x.to(device), y.to(device)
        loss = loss_fn(model(x), y)            # forward
        opt.zero_grad()                        # clear stale gradients (they ACCUMULATE)
        loss.backward()                        # backward: fills .grad on every param
        opt.step()                             # θ ← θ − η·(Adam-scaled) grad
print(f"epoch {epoch:2d}  train_loss {loss.item():.3f}  val_acc {evaluate():.3f}")
# expected shape of the run: loss ~0.69 (= ln 2, coin-flip) → ~0.15; val_acc → ~0.97

Three lines in that loop cause 90% of beginner bugs: forgetting opt.zero_grad() (gradients accumulate across steps by design — useful for gradient accumulation, silent corruption otherwise), calling the model in eval without torch.no_grad() (autograd builds a graph for every forward pass and memory climbs until OOM), and losses that already include the activation (BCEWithLogitsLoss wants raw logits — feed it sigmoid outputs and it still "works," just worse, forever).

02 — Debugging training — the ritual

  1. Overfit one tiny batch first. If the model can't memorize 32 examples, the code/loss/labels are broken — no point training for hours.
  2. Verify shapes and label ranges by hand once.
  3. Track train and validation loss separately; one number hides everything.
  4. Change one thing per experiment. Keep a journal: hypothesis → change → result.

Step 1 deserves code, because it's the highest-value ten lines in applied deep learning — a smoke test that separates "my code is broken" from "my model/data/hyperparameters need work" before you spend GPU-hours:

overfit_one_batch.py — the smoke test that saves GPU-dayspython
x, y = next(iter(train_dl))                    # ONE fixed batch, reused every step
x, y = x.to(device), y.to(device)

model = MLP().to(device)                       # fresh model
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)

for step in range(500):
    loss = loss_fn(model(x), y)
    opt.zero_grad(); loss.backward(); opt.step()
    if step % 100 == 0:
        print(step, f"{loss.item():.4f}")

# PASS: loss → ~0 (the model memorized 64 points; a net that can't is broken).
# FAIL modes and what they mean:
#   loss stuck at ln(2)=0.693  → outputs ignore inputs: detached graph, frozen
#                                params, or labels shuffled relative to inputs
#   loss = NaN                 → LR too high or bad numerics in your loss
#   loss drops then plateaus   → capacity too small for even 64 points, or
#                                duplicate inputs with conflicting labels
assert loss.item() < 0.01, "cannot overfit one batch — fix the code before training"

03 — Reading loss curves — the vital signs

You will spend more time looking at loss curves than at code. Learn the shapes (numbers illustrative):

Curve shapeReadingAction
Smooth fast drop, then long slow grind downhealthy runlet it cook; maybe extend the LR decay
Loss spikes to 10× then recovers (or NaNs)LR too high / bad batch / fp16 overflowlower LR, add warmup, grad clipping (clip_grad_norm_(…, 1.0))
Perfectly flat from step 0 at ln(vocab) or ln(2)model output independent of inputdetached graph, frozen params, LR≈0, label bug
Train ↓ steadily, val ↓ then ↑ (the V-shape)overfitting begins at the valleyearly-stop there; add data/regularization for the next run
Train and val both plateau high, togetherunderfitting (high bias)bigger model, better features, higher LR, longer training
Staircase: flat → cliff at each epoch boundarydata not shuffled; model rides orderingshuffle=True, check sampler
Sawtooth every N stepsperiodic bad slice of data or LR restart artifactinspect the batches at the teeth

One number worth memorizing: an untrained classifier's cross-entropy is ln(num_classes) — 0.693 for binary, ~10.8 for a 50K-token vocab. If your loss starts anywhere else, your initialization or loss wiring is off; if it never leaves that value, the model isn't seeing the inputs. This single check catches an absurd fraction of real bugs.

04 — Mixed precision — the free 2–3×

Modern GPUs execute fp16/bf16 matmuls 2–8× faster than fp32 and halve activation memory. The recipe is three lines around the loop you already have; bf16 (Ampere and newer) needs no loss scaling because its exponent range matches fp32:

amp.py — mixed-precision training, the standard recipepython
use_bf16 = torch.cuda.is_bf16_supported()
amp_dtype = torch.bfloat16 if use_bf16 else torch.float16
scaler = torch.amp.GradScaler("cuda", enabled=not use_bf16)  # fp16 only: scale loss
# so tiny grads don't
for x, y in train_dl:                                        # underflow to zero
    x, y = x.to(device), y.to(device)
    with torch.amp.autocast("cuda", dtype=amp_dtype):        # fwd in low precision
        loss = loss_fn(model(x), y)                          # (weights stay fp32)
    opt.zero_grad()
    scaler.scale(loss).backward()
    scaler.unscale_(opt)                                     # so clipping sees true grads
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(opt)                                         # skips step if inf/nan
    scaler.update()

Memory intuition you'll reuse in Part 9: training memory ≈ weights + gradients + optimizer state + activations. For Adam in fp32 that's roughly 16 bytes per parameter before activations (4 weights + 4 grads + 8 Adam moments) — a 1B-param model wants ~16 GB just to exist in the optimizer, which is why mixed precision, gradient checkpointing, and sharded optimizers exist.

05 — Mini-scenario: the 8-hour run that was CPU-bound

You fine-tune a small model on 4×A100s; the run crawls. nvidia-smi shows GPU utilization bouncing between 8% and 30% — the classic sign the GPUs are starving, not working. The model isn't slow; the data pipeline is: images decoded in Python inside __getitem__, num_workers=0, no prefetch. Fixes, in order of cheapness: DataLoader(num_workers=8, pin_memory=True, persistent_workers=True), move decode/augment to a compiled path or precompute, batch small files into shards. Utilization goes to 90%+, the 8-hour run finishes in 75 minutes (illustrative but typical magnitude). The general law: look at GPU utilization before touching the model — half of "training is slow" tickets are input pipelines.

SymptomUsual suspects
Loss = NaNlearning rate too high, bad numerics (log 0, div 0), corrupt input, fp16 overflow (try bf16)

Silent killers (no error, wrong results)

  • Forgetting model.eval() at inference: dropout keeps dropping and normalization uses batch stats — predictions become noisy and batch-size dependent.
  • Accumulated gradients from a missing zero_grad(): the effective update is a running sum; training "works" but corresponds to no optimizer you chose.
  • Loss reduction mismatch: reduction="sum" makes the gradient scale with batch size, so changing batch size silently changes the effective LR.
  • Non-determinism blamed on the model: forgot to seed, or nondeterministic CUDA kernels — fix seeds before comparing runs, or every A/B is noise.
  • Weight decay applied to norms/biases: standard AdamW recipes exclude them; regularizing LayerNorm gains hurts quietly.

Do it from scratch exactly once

Implement a 2-layer network + backprop in NumPy (or follow Karpathy's micrograd). One honest pass demystifies "the framework handles it" forever. Then use PyTorch and never look back — the point is exposure, not maintaining your own autograd.

Takeaway

DL = differentiable blocks + gradient descent + engineering for stability. The 60-line loop in this chapter is the loop that trains frontier models — bigger tensors, sharded across machines, same five steps. Overfit one batch before every serious run; read loss curves like vital signs; check GPU utilization before blaming the model. The Transformer (next chapter) is just a particular, spectacularly effective arrangement of these blocks.
