MLOps — version everything that changes behavior // 12.9

"It worked last week" is only debuggable if you can name exactly what changed. In an LLM system, far more things change behavior than in ordinary software.

Part 12 · Production architectureChapter 12.9

01 — Overview

The mini-scenario: Tuesday, support tickets spike — the bot is "giving weird answers about billing." You check deploys: nothing shipped. You check the provider status page: green. Three hours later you find it: a teammate re-ran the ingestion pipeline Monday night with a chunker fix, which changed chunk boundaries, which changed what retrieval returns for billing queries. No code deploy, no model change — and yet the system's behavior deployed. If your version manifest had included the index build ID, the first diff you ran would have found it in three minutes. That's the entire pitch for this chapter.

02 — The version manifest

Classic MLLLM apps add
code + environmentprovider + model identifier (models get silently updated!)
data snapshot + schemaprompts + tool schemas (a reworded prompt = a deploy)
features/preprocessingretrieval corpus + chunker + embedding model + index (one contract — change one, reindex all)
weights + hyperparams + seedsagent workflow, guardrail policies
eval resultsgraders + eval datasets (a changed judge changes every score)

Make it a file. One document, checked into git, that names every behavior-affecting component with an immutable reference. The rule of inclusion: if changing it could change an answer, it goes in the manifest.

release.yaml — the behavioral contract, pinnedyaml
release: support-bot-2026.03.2
created: 2026-03-14T09:20:00Z
owner: platform-team

models:
  primary:
    provider: anthropic
    id: claude-sonnet-4-5           # pinned snapshot id, never an alias
params: {temperature: 0.0, max_tokens: 1024}
  router:
    provider: anthropic
    id: claude-haiku-4-5
    escalation_threshold: -0.35      # tuned values are versioned too
prompts:                             # content-addressed: hash IS the version
system:        prompts/system.md        @ sha256:9f2c41…
  query_rewrite: prompts/rewrite.md       @ sha256:77ab02…
tool_schemas:    tools/schemas.json       @ sha256:c410de…

retrieval:                           # ONE contract — these move together
corpus_snapshot: s3://kb/snap-2026-03-13         # immutable copy
chunker:  {name: recursive_md, version: 1.4.0, size: 512, overlap: 64}
  embedding_model: text-embedding-x-2026-01        # pinned, not "latest"

reranker: {name: rerank-v3, top_k: 4}

guardrails:
  policy_pack: guardrails/policies.yaml @ sha256:5b7e90…
  injection_filter: v2.1

evals:                               # the ruler is versioned like the thing
suite: evals/support-v12           #   it measures
grader_model: claude-sonnet-4-5    # a changed judge changes every score
results: {resolution: 0.87, faithfulness: 0.94, run: eval_run_88123}

compat:
  cache_namespace: sb-2026.03.2      # response caches keyed per release
rollback_to: support-bot-2026.03.1 # tested, not aspirational

Three properties matter more than the exact schema. Immutability: every reference is a hash, snapshot, or build ID — prompts/system.md alone is useless because the file changes; the hash pins what was actually running. Completeness: the tuned threshold, the reranker's top_k, the grader model — the embarrassing incidents come from the fields people leave out. Diffability: "what changed between last week and now?" must be answerable by diff release-1.yaml release-2.yaml. When the pager goes off, that diff is your first move.

Where does it live?

Anywhere append-only and queryable: git (fine to start), MLflow's model registry, or a releases table in Postgres. What matters is that the running service logs its release ID on every trace (Part 12's tracing chapter), so any logged request can be mapped back to the exact manifest that produced it — that's the join that makes debugging and replay possible.

03 — Deployment discipline

  • Staged rollout: shadow (run silently next to prod) → canary (small %) → full; explicit rollback path rehearsed, not hoped.
  • Eval gates in CI: a prompt/model/index change ships only after the frozen eval suite passes; regressions block.
  • Immutable artifacts: the thing you tested is byte-for-byte the thing you deployed — prompts included (this also keeps prompt caches hot, Part 6).
  • Training–serving skew: preprocessing must be the same code path in training and serving; log serving inputs so you can replay them offline.

Not all changes are the same deploy — three runbooks

A prompt tweak, an index rebuild, and a model swap all "change behavior," but they differ in blast radius, rollback cost, and what can go subtly wrong. Teams that use one generic process either over-ceremony the small changes (so people route around the process) or under-ceremony the big ones (so the big ones cause incidents).

Shadow and canary, concretely

rollout.py — shadow + canary in one routerpython
import hashlib, asyncio, random

RELEASES = {"stable": load_release("support-bot-2026.03.1"),
            "candidate": load_release("support-bot-2026.03.2")}
CANARY_PCT = 0.05 # config, changeable without deploy
SHADOW_SAMPLE = 0.20 # shadow 20% of stable traffic (cost control)
def _bucket(user_id: str) -> float:
    """Sticky assignment: a user stays in one arm all session —
    flip-flopping between releases mid-conversation is its own bug."""
    h = hashlib.sha256(user_id.encode()).digest()
    return int.from_bytes(h[:4], "big") / 2**32
async def handle(request):
    arm = "candidate" if _bucket(request.user_id) < CANARY_PCT else "stable"
    resp = await run_pipeline(RELEASES[arm], request)
    log_trace(request, resp, release=RELEASES[arm].id, arm=arm)

    # SHADOW: candidate runs on a sample of stable traffic, result unused.
# Fire-and-forget; shadow failures must never touch the user path.
if arm == "stable" and random.random() < SHADOW_SAMPLE:
        asyncio.create_task(_shadow(request, resp))
    return resp

async def _shadow(request, live_resp):
    try:
        shadow_resp = await run_pipeline(RELEASES["candidate"], request,
                                         side_effects=False)  # READ-ONLY:
# tools that write (email, tickets, refunds) run in dry-run mode —
# shadowing a send_email tool for real is an incident, not a test.
        log_shadow_pair(request, live=live_resp, shadow=shadow_resp)
    except Exception as e:
        log_shadow_error(e)          # shadow errors are DATA (candidate is
# flaky!) — but never user-facing
# Canary judgment: compare arms on $/task, latency p95, error rate,
# eval-judge score on sampled pairs, and per-slice quality — a 5% canary
# with 40 intents has ~zero data per intent per day; size the canary
# window to the SLICE you care about, not the average.

Shadow answers "does the candidate crash, cost, or slow down?" for free, and — via judged comparison of logged pairs — "does it answer differently, and better?" Canary answers "do real users and real feedback like it?" with real stakes. You want both: shadow catches the 3am-obvious failures before any user sees them; canary catches what only user behavior reveals. The side_effects=False line is load-bearing — the classic shadow-mode incident is the candidate double-sending every email for a week.

Training–serving skew: detect it by replay

Skew is when offline and online disagree: your eval pipeline preprocesses one way, serving preprocesses another, and your beautiful offline scores describe a system you aren't actually running. The LLM-era version: eval harness renders prompts with template v2 while prod still ships v1; offline retrieval hits a fresher index than prod; the eval runs temperature 0 while prod runs 0.7. The detector is simple and brutal: replay logged production inputs through the offline pipeline and diff what each side produced.

skew_check.py — nightly replay of logged prod inputspython
async def skew_check(sample_size=200):
    """Pull last night's traces; re-run each through the OFFLINE pipeline
    at the SAME release id; diff the intermediate artifacts, not just
    final text (temperature makes final-text diffs noisy)."""
    traces = await fetch_traces(sample="random", n=sample_size,
                                window="24h", has="release_id")
    mismatches = []
    for t in traces:
        offline = await offline_pipeline.run(
            raw_input=t.raw_input,
            release=load_release(t.release_id))   # pin to what prod ran

        checks = {
            # 1. same rendered prompt? (template/version drift)
"prompt_hash": sha(offline.rendered_prompt) == sha(t.rendered_prompt),
            # 2. same retrieved chunk IDs? (index/filter drift)
"retrieval":   offline.chunk_ids == t.chunk_ids,
            # 3. same tool schemas presented? (schema drift)
"tools":       sha(offline.tool_schema_blob) == sha(t.tool_schema_blob),
            # 4. same params reaching the API? (config drift)
"params":      offline.model_params == t.model_params,
        }
        if not all(checks.values()):
            mismatches.append({"trace": t.id,
                "failed": [k for k, ok in checks.items() if not ok]})

    rate = len(mismatches) / sample_size
    emit_metric("skew.mismatch_rate", rate)
    if rate > 0.01:                    # ponytail: 1% flat threshold; move to
        page(f"train-serve skew {rate:.1%}",   # per-check thresholds if noisy
             examples=mismatches[:5])
    return mismatches

# Prerequisite (worth the storage): serving logs the RENDERED prompt,
# retrieved chunk ids, tool-schema hash, and model params on every trace —
# not just the user input. If you only log inputs, you can replay but
# you have nothing to diff against. Log the intermediates.

Diffing intermediates instead of outputs is the trick: rendered-prompt hash, chunk IDs, schema hash, params. Those are deterministic, so any mismatch is a true positive — a real divergence between what you evaluate and what you serve. When the nightly job pages you with "retrieval mismatch on 14% of traces," you've caught Tuesday's mystery index rebuild before the tickets spike.

04 — Cost accounting

cost per successful task =
  (model tokens + embeddings + reranking + tool calls + compute
   + retries + human review + observability) / successful tasks
— a cheaper model that triggers more retries and human fixes is a MORE expensive model.

Worked micro-example (illustrative): model A costs $0.09/task raw with a 4% human-escalation rate; model B costs $0.05/task raw with 9% escalation. At $2.50 per human touch: A = 0.09 + 0.04×2.50 = $0.19; B = 0.05 + 0.09×2.50 = $0.275. The "45% cheaper" model is 45% more expensive. This is why the manifest pins tuned thresholds and why eval gates measure $/successful-task, not $/token.

Versioning gotchas

  • The alias that moved: pinning latest or a dated alias that the provider re-points is not pinning. If a true snapshot id isn't available, your frozen eval suite run on a schedule is the only tripwire for silent upstream swaps — treat a score shift with no manifest diff as "the provider deployed."
  • Half-versioned retrieval: re-embedding with a new model while old vectors remain in the same index = two incompatible geometries in one ANN structure; similarity scores become meaningless quietly. The retrieval block moves as one unit — that's why it shares one index_build id.
  • The grader drifted: someone "improves" the judge prompt; every historical score is now in a different currency and your trend charts lie. Version graders and eval sets like prompts, and re-score a fixed anchor set when either changes so you can splice the trend.
  • Config outside the manifest: the env var someone flipped, the feature flag, the temperature override in a hotfix. Rule: the service refuses to start unless every behavior-affecting setting resolves from the manifest. Painful for a week, then it saves you quarterly.
  • Rollback rot: the rollback target references an index that was garbage-collected or a prompt file that moved. Rehearse rollback in staging on every release — "rollback_to" is only real if it's been executed.

Takeaway

The unit of deployment is not "the model" — it's the whole behavioral contract: model + prompts + index + tools + graders. Version it as one, gate it with evals, roll it out gradually.

Exercises

  1. Write the release.yaml for a system you know (or the support bot from this Part). Then audit it against the rule of inclusion: list three behavior-affecting settings you initially forgot (almost everyone forgets a tuned threshold, a grader version, or a reranker top_k).
  2. Take two versions of any prompt you've iterated on. Content-address both (sha256), run 50 identical inputs through each at temperature 0, and diff the outputs. How many changed in ways you didn't intend? That number is why prompt changes are deploys.
  3. Implement the shadow router from this chapter around a toy pipeline (even a single LLM call). Verify: shadow failures never surface to the caller, side-effecting tools run dry, and logged pairs land somewhere queryable. Then compute a judged win-rate between stable and candidate over 100 shadow pairs.
  4. Build the nightly skew check for one pipeline stage: log the rendered prompt hash at serving time, replay the raw input offline, compare. Introduce a deliberate skew (change the offline template's whitespace) and confirm the check catches it.
  5. Write the three runbooks (prompt change / index rebuild / model swap) for your own system as one-page checklists, including the rollback command for each. Then actually execute the index-rebuild rollback in staging and record how long it took — if the answer is "we couldn't," you've found this quarter's most valuable ticket.
