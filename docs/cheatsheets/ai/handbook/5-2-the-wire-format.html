What actually goes over the wire // 5.2

This request/response choreography is the protocol. Every framework hides it; understand it once and you can read them all — and debug the 400 errors they produce.

Part 5 · Tools & actionsChapter 5.2

01 — The two message shapes

Everything reduces to two shapes: the model requesting a call, and you returning a result. On the Anthropic API the request arrives as a tool_use content block in an assistant message, flagged by stop_reason: "tool_use":

the model asks for a tool (stop_reason: "tool_use")json
{ "role":"assistant", "content":[
  {"type":"text", "text":"Let me check that order."},
  {"type":"tool_use", "id":"toolu_01A",
   "name":"get_order", "input":{"order_id":"X-92"}}
]}
you run it, then send the result back as the next turnjson
{ "role":"user", "content":[
  {"type":"tool_result", "tool_use_id":"toolu_01A",
   "content":"{\"status\":\"shipped\"}", "is_error":false}
]}

Note the oddity that trips newcomers: the tool result travels in a user-role message. There is no "tool" role on this API — from the model's perspective, the environment answering is just the next inbound turn. The tool_use_id is what pairs a result to its request; the pairing, not the position, is load-bearing.

02 — A complete transcript: parallel calls and an error

Mini-scenario: a travel assistant with two tools, get_weather(city) and get_flight_price(origin, dest). User asks: "I'm in Berlin — compare the weather in Lisbon and Athens, and get me a flight price to whichever sounds warmer." Below is the entire messages array as it grows, exactly what crosses the wire. Five API calls' worth of state, one array.

full transcript — Anthropic format (comments mark each API round)json
[
  // ---- turn 1: the user ------------------------------------------------
  { "role": "user", "content":
      "I'm in Berlin — compare the weather in Lisbon and Athens, and get a flight price to whichever sounds warmer." },

  // ---- API round 1 returns: PARALLEL tool_use — two blocks, one turn ----
  { "role": "assistant", "content": [
      { "type": "text", "text": "I'll check both cities' weather." },
      { "type": "tool_use", "id": "toolu_01A",
        "name": "get_weather", "input": { "city": "Lisbon" } },
      { "type": "tool_use", "id": "toolu_01B",
        "name": "get_weather", "input": { "city": "Athens" } }
  ]},

  // ---- you ran BOTH; both results in ONE user turn, paired by id --------
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01A",
        "content": "{\"temp_c\": 19, \"sky\": \"cloudy\"}", "is_error": false },
      { "type": "tool_result", "tool_use_id": "toolu_01B",
        "content": "{\"temp_c\": 27, \"sky\": \"sunny\"}", "is_error": false }
  ]},

  // ---- API round 2: model picks Athens, asks for the flight -------------
  { "role": "assistant", "content": [
      { "type": "text", "text": "Athens is warmer (27°C). Checking flights." },
      { "type": "tool_use", "id": "toolu_01C",
        "name": "get_flight_price",
        "input": { "origin": "BER", "dest": "ATH" } }
  ]},

  // ---- the flight API timed out: is_error=true, message, DON'T throw ----
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01C",
        "content": "Upstream timeout after 5000ms. Safe to retry once.",
        "is_error": true }
  ]},

  // ---- API round 3: model reads the error and retries by itself ---------
  { "role": "assistant", "content": [
      { "type": "tool_use", "id": "toolu_01D",
        "name": "get_flight_price",
        "input": { "origin": "BER", "dest": "ATH" } }
  ]},

  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01D",
        "content": "{\"price_eur\": 142, \"airline\": \"A3\"}", "is_error": false }
  ]},

  // ---- API round 4: stop_reason "end_turn" — the final answer -----------
  { "role": "assistant", "content": [
      { "type": "text", "text":
        "Athens wins: 27°C and sunny vs Lisbon's cloudy 19°C. A flight BER→ATH is €142 on Aegean. Want me to look at dates?" }
  ]}
]

Read it once slowly — four things are worth noticing. (1) The two weather calls arrive as two tool_use blocks in a single assistant turn: parallel calls, which you may execute concurrently, but whose results must all come back in the single next user turn. (2) The timeout is returned as data (is_error: true), and the model's very next move is a sensible retry — no retry logic in your code. (3) Every API round resends the entire array; the API is stateless, the array is the state. (4) Token growth is the price: this conversation's final round carries ~7 messages of history — with tool definitions on top, each round's input grows by roughly the previous round's traffic, which is why prompt caching of the static prefix (Part 6) matters for agents.

03 — The same conversation, OpenAI format

Same dance, different field names. The model's requests live in a tool_calls array on the assistant message (arguments as a JSON string, not an object), and each result is its own role: "tool" message keyed by tool_call_id:

the parallel round + error round — OpenAI formatjson
[
  { "role": "user", "content": "I'm in Berlin — compare..." },

  // parallel calls: tool_calls array, arguments are a JSON *string*
  { "role": "assistant", "content": null, "tool_calls": [
      { "id": "call_A", "type": "function", "function":
          { "name": "get_weather", "arguments": "{\"city\": \"Lisbon\"}" } },
      { "id": "call_B", "type": "function", "function":
          { "name": "get_weather", "arguments": "{\"city\": \"Athens\"}" } }
  ]},

  // one role:"tool" message PER call — not one combined turn
  { "role": "tool", "tool_call_id": "call_A",
    "content": "{\"temp_c\": 19, \"sky\": \"cloudy\"}" },
  { "role": "tool", "tool_call_id": "call_B",
    "content": "{\"temp_c\": 27, \"sky\": \"sunny\"}" },

  // ...flight call round elided (same shape)...

  // no is_error flag exists — describe the failure in content instead
  { "role": "tool", "tool_call_id": "call_C",
    "content": "ERROR: upstream timeout after 5000ms. Safe to retry once." }
]

Learn one wire format and the other is a field-renaming exercise — which is exactly what every cross-provider framework (and MCP, chapter 4.4) does under the hood. The genuinely different bits are just three: where results live (user turn vs tool role), arguments as object vs string, and the presence/absence of a first-class error flag.

The rules that trip everyone up

  • Append the assistant turn (with the tool_use) before the tool_result, or the API errors — the request must precede its answer in history. This is the #1 first-week 400 error.
  • One turn can contain several tool_use blocks (parallel calls) — return a tool_result for each, in the single next user turn. A missing id → 400; results for all-but-one → 400.
  • tool_result.content must be a string — stringify your JSON. Passing a dict is the #2 first-week error.
  • On failure, return is_error: true with a message — don't throw; let the model read it and recover. Make the message actionable ("timeout, safe to retry") rather than a bare stack trace.
  • Never edit or drop earlier tool_use/tool_result pairs when trimming history for context length — orphaned ids are rejected. Trim in whole request/response pairs.
  • On the OpenAI side: function.arguments is a string that can, rarely, be malformed JSON — parse defensively; and under streaming, arguments arrive as concatenated deltas you must assemble before parsing.

OpenAI naming

Same dance, different words: the model returns tool_calls on the message; you reply with a role:"tool" message keyed by tool_call_id. Learn one wire format; read them all.

Takeaway

The protocol is a paired ledger: every tool request carries an id, every id gets exactly one string result, the whole ledger is resent every round. Frameworks add convenience, not semantics — when an agent framework misbehaves, print the raw messages array and check the ledger by hand.

Exercises

  1. Reconstruct the Berlin transcript with real API calls and two stub tools. Log the raw messages array after every round and diff it against the transcript above.
  2. Break it on purpose, three ways: (a) send a tool_result without appending the assistant turn first, (b) answer only one of two parallel calls, (c) pass a dict as content. Record each API error message — you'll recognize them for the rest of your career.
  3. Return the timeout error as is_error: true with the message "Upstream timeout" versus a raw 40-line stack trace. Compare the model's recovery behavior over 5 runs each.
  4. Write a 30-line translator that converts an Anthropic-format transcript into the OpenAI format (and back) using the table above. Round-trip the Berlin transcript and assert equality of the semantic content.
  5. Instrument each round's input token count for the Berlin conversation. Verify the growth is roughly linear in accumulated history, then estimate the savings if the system prompt + tool definitions (say 900 tokens) were cache-hits after round 1.
