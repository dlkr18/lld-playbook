Memory: making agents remember // 6.5

Models are stateless. "Memory" is a system you build. It exists because the context window is finite — memory decides what to keep and what to reload.

Part 6 · AgentsChapter 6.5

01 — Overview

Every "the agent remembered!" moment is plumbing: something wrote text to a store earlier, and something injected it into the context now. There is no third mechanism. Once you see memory as write policy + storage + read policy, the five classic types below stop being taxonomy trivia and become five different answers to "what do we write, where, and when do we read it back?"

02 — Working memory: a buffer that knows when to shrink

The messages list is working memory, and its failure mode is simply growing until it degrades quality and burns money. The fix is a buffer object that watches its own token count and summarizes the oldest turns past a threshold — the summarization trigger is the design decision, not the summary itself.

working_memory.py — buffer with a summarization triggerpython
class ConversationBuffer:
    """messages list that compresses itself past a token threshold."""
def __init__(self, count_tokens, llm, max_tokens=30_000, keep_recent=6):
        self.msgs, self.count, self.llm = [], count_tokens, llm
        self.max_tokens, self.keep_recent = max_tokens, keep_recent
        self.summary = "" # rolling summary of evicted turns
def append(self, msg):
        self.msgs.append(msg)
        if self._tokens() > self.max_tokens:   # TRIGGER: threshold, not every turn
self._compress()

    def _tokens(self):
        return sum(self.count(json.dumps(m)) for m in self.msgs)

    def _compress(self):
        old, self.msgs = self.msgs[:-self.keep_recent], self.msgs[-self.keep_recent:]
        self.summary = self.llm(
            f"Update the running summary with the new turns.\n"
f"PRESERVE: decisions made, facts stated, open tasks, IDs, file paths.\n"
f"Current summary:\n{self.summary}\n\nNew turns:\n{render(old)}")

    def view(self):                            # what actually goes to the API
        head = ([{"role": "user",
                  "content": f"[SUMMARY OF EARLIER CONVERSATION]\n{self.summary}"}]
                if self.summary else [])
        return head + self.msgs

Details that matter: the trigger fires on tokens, not message count (one message can be a 40k-token tool result); the last keep_recent turns stay verbatim because the model needs exact recent wording, not a paraphrase; and the summary is rolling — each compression folds new turns into the existing summary rather than re-summarizing from scratch, keeping compression cost O(evicted turns), not O(history). Worked numbers (illustrative): a 100-turn support session averaging 400 tokens/turn is 40k tokens raw. With max_tokens=30_000 this buffer compresses twice, and turn 100 is answered against ~2k of summary + ~2.4k of recent turns ≈ 4.4k instead of 40k — a ~9× input-cost cut, and (just as important) the model isn't wading through 90 stale turns to find the current question.

03 — Episodic memory: remember/recall over a vector store

Working memory dies with the session. Episodic memory is the cross-session store: embed notable moments, retrieve the relevant ones next time. The original sketch, now with the parts a real one needs — dedupe on write and score-thresholded, time-aware reads:

episodic.py — vector store of past events (qdrant-style API)python
class EpisodicMemory:
    def __init__(self, db, embed, col="memories"):
        self.db, self.embed, self.col = db, embed, col

    def remember(self, text, kind="event", user_id=None):
        vec = self.embed([text])[0]
        # dedupe: if a near-identical memory exists, skip the write
        near = self.db.search(self.col, vec, limit=1)
        if near and near[0].score > 0.95:
            return near[0].id                     # already known
        mid = str(uuid.uuid4())
        self.db.upsert(self.col, [{"id": mid, "vector": vec,
            "payload": {"text": text, "kind": kind, "user_id": user_id,
                        "ts": time.time()}}])
        return mid

    def recall(self, query, k=4, min_score=0.35, user_id=None):
        hits = self.db.search(self.col, self.embed([query])[0], limit=k * 3,
                              filter={"user_id": user_id} if user_id else None)
        good = [h for h in hits if h.score >= min_score][:k]   # relevance floor
return sorted(good, key=lambda h: h.payload["ts"])      # oldest→newest
def inject_memories(mem, user_msg, user_id):
    hits = mem.recall(user_msg, user_id=user_id)
    if not hits: return user_msg
    lines = "\n".join(f"- [{iso(h.payload['ts'])}] {h.payload['text']}" for h in hits)
    return (f"Relevant memories from past sessions (may be stale — verify "
f"anything critical):\n{lines}\n\n---\n{user_msg}")

Three non-obvious choices here. The relevance floor: vector search always returns something, and without min_score an unrelated question drags in four random memories that actively mislead. The dedupe check: agents restate the same fact constantly; without it, "user prefers Python" ends up stored 30 times and crowds out everything else in every recall. The staleness disclaimer in the injection: memories are claims about the past, and the model should treat them as evidence, not gospel — "may be stale" measurably reduces the model doubling down on outdated facts.

04 — Fact extraction: from transcripts to a profile

Episodic recall answers "what happened related to X?" But some knowledge should be always present, not retrieved-if-relevant: the user's name, plan tier, stack, standing preferences. That's a profile — a small structured document, built by running an extraction pass after each session, and injected into the system prompt whole (it's tiny).

profile.py — end-of-session fact extraction with mergepython
PROFILE_SCHEMA = {"name": None, "role": None, "stack": [], "preferences": [],
                  "constraints": [], "current_projects": []}

def update_profile(llm, profile: dict, transcript: str) -> dict:
    raw = llm(f"""Extract durable facts about the USER from this session.
Rules:
- Only facts stated by the user about themselves/their work. No inferences.
- Durable means: still true in a month. "It's raining" is NOT durable.
- If a new fact CONTRADICTS the profile, the new fact wins; drop the old.
Current profile:\n{json.dumps(profile)}
Transcript:\n{transcript[-20_000:]}
Return the FULL updated profile as JSON matching the same schema.""")
    try:
        new = json.loads(raw)
        assert set(new) <= set(PROFILE_SCHEMA)          # schema drift guard
return new
    except (json.JSONDecodeError, AssertionError):
        return profile                                   # bad extraction? keep old
# each session starts with:
# SYSTEM += f"\nWhat you know about this user:\n{json.dumps(profile, indent=1)}"

The contradiction rule is the whole game: profiles must be updatable, not append-only. "User is migrating to Postgres" (March) must replace "user runs MySQL" (January), or the agent gives confidently wrong advice forever. Note also the fail-safe: a botched extraction keeps the old profile rather than corrupting it — memory writes should never be able to make the system dumber than doing nothing.

05 — External memory: the file the agent keeps

The "write to a file" trick

A robust, inspectable pattern: the agent keeps a plan/notes file and re-reads it each turn. It survives context compaction, you can debug it, and it doubles as an audit log. Simple beats clever.

Concretely, this is just two tools plus a system-prompt contract:

scratchpad.py — file-based external memory as toolspython
PAD = pathlib.Path("workdir/scratchpad.md")

def read_scratchpad() -> str:
    return PAD.read_text() if PAD.exists() else "(empty)"
def write_scratchpad(content: str) -> str:
    if len(content) > 8_000:                       # keep it a scratchpad, not a dump
return "ERROR: scratchpad limit 8000 chars. Summarize before writing."
    PAD.write_text(content); return "saved"

SYSTEM += """
You have a persistent scratchpad file. At the START of a task, read it.
Keep it updated: your plan, checked-off steps, key findings, IDs and paths.
It is your only memory that survives interruptions — write anything you
cannot afford to re-derive."""

Why this humble pattern outperforms fancier memory for long tasks: the model chooses what's worth writing (it knows what it'll need better than your heuristics do), the file survives compaction and process restarts, and when the run goes sideways you open the file and read the agent's own account of what it thought it was doing. Coding agents in the wild lean heavily on exactly this — a plan/notes markdown file per task. The size cap matters: uncapped scratchpads become a second unbounded context window, re-ingested every turn.

Semantic memory (facts about the world → RAG, Parts 4–5) and procedural memory (instructions that update — really just the profile pattern applied to behavior: "user wants diffs, not full files" ends up as a standing instruction) complete the table; both reuse machinery you've already seen, which is the quiet point of this chapter — memory types differ in policy, barely in mechanism.

06 — The write policy: what NOT to store

Everyone designs the read path; the write path is where memory systems actually die. Store too little and the agent is a goldfish. Store too much and recall returns noise, the profile bloats, and you've built a privacy liability. Rules that hold up:

  • Don't store what you can re-derive. Tool outputs, retrieved documents, computed results — the source of truth already exists; store the pointer ("order data lives in orders_db, key = email"), not the copy that will silently go stale.
  • Don't store transient state as durable fact. "The build is broken" is true for an afternoon. Written to episodic memory, it resurfaces in a recall three weeks later as ambient falsehood. Tag event-memories with timestamps and let recall favor recency for anything state-like.
  • Don't store secrets or regulated data. API keys, passwords, payment details, health data pasted mid-session — a memory store is a new copy of that data with a new access path and (usually) no deletion story. Filter writes; if the user must be remembered as "has an API key configured," store that, never the key.
  • Don't store the model's own speculation as fact. "The user probably works in fintech" written today is retrieved tomorrow as "the user works in fintech." Extraction prompts must demand stated facts only (see the No inferences rule above) — memory laundering turns guesses into ground truth.
  • Do store: explicit user corrections ("no, staging is eu-west-1"), decisions and their reasons, stable preferences, open commitments ("promised a follow-up on the refund"), and hard-won findings that cost many steps to derive.
  • Give memory a deletion story. TTLs on event-type memories, a user-visible "what do you know about me" view, and a delete path. This is a compliance requirement in most jurisdictions and a trust feature everywhere.

Memory failure modes that only show up later

(1) Poisoning: one wrong stored "fact" (a typo'd hostname, a sarcastic user message taken literally) gets recalled, restated by the model, re-extracted, and re-stored — now it has three copies and citation-like authority. Mitigate: dedupe on write, provenance in payloads ("stated by user 2026-03-14"), and periodic pruning passes. (2) Cross-user leakage: forget the user_id filter once and user A's "prefers aggressive refunds" surfaces in user B's session — always filter at the store layer, never trust the prompt to ignore it. (3) Recall crowding: 30 duplicates of one preference fill all k slots, so nothing else is ever recalled — this looks exactly like "memory stopped working." (4) Summary-then-need: working-memory compression drops the one order ID you need 30 turns later — the preserve-list in the compression prompt (IDs, paths, decisions) is load-bearing, not decoration (next chapter goes deep).

Mini-scenario: the assistant that "forgot" a promise

Your support agent tells a customer "I'll flag this for a refund review — we'll follow up within 48 h." Session ends. The follow-up never happens: the promise lived only in working memory, which evaporated. The fix isn't more retrieval — it's recognizing that commitments are writes. You add one rule to the extraction pass: open commitments go to a followups table with a due date, and a cron job re-opens sessions that owe one. Memory design is mostly noticing which utterances are actually state changes.

Takeaway

Memory = write policy + store + read policy, per type: buffer (always write, threshold-compress, always read), episodic (write selectively with dedupe, read by similarity with a floor), profile (extract stated facts, replace on contradiction, always inject), scratchpad (agent-directed, capped, re-read each task). The write policy — especially what you refuse to store — determines whether the system still works in month three.
