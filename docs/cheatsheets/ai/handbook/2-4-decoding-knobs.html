The knobs you can turn // 2.4

You can't easily change the model's brain, but you control how it picks each next token. These are the settings you'll actually use.

Part 2 · LLM foundationsChapter 2.4

01 — The four knobs

Recall from the "What an LLM really is" chapter: at every step the model hands you a probability distribution over its whole vocabulary. Decoding parameters decide how a single token gets drawn from it. There are only four you'll touch routinely:

KnobWhat it doesUse when
temperature (0–~1)Randomness. 0 = always pick the most likely token (deterministic, repeatable). Higher = more varied/creative. Mechanically: logits are divided by T before softmax, so low T sharpens the distribution, high T flattens it.0 for extraction, code, classification, caching · 0.7+ for brainstorming, writing.
top_p (0–1)"Nucleus sampling" — only consider the smallest set of tokens whose probability sums to p, renormalize, sample from that. top_p=0.9 = "sample only from the credible candidates."An alternative to temperature; usually tune one, not both.
max_tokensHard cap on output length. Not a target — the model doesn't know it exists; generation just gets cut off there.Always set it — controls cost & runaway generation. Size it ~2× your expected longest valid answer.
stop sequencesStrings that force generation to halt the moment they're emitted (the stop string itself is not returned).Structured formats; ending at a delimiter; single-item generation from list-happy models.

02 — See it, don't trust it: sweeping temperature and top_p

The fastest way to build intuition is to sweep the knobs on one prompt and read the outputs side by side:

sweep.py — same prompt, different decoding settingspython
import anthropic
client = anthropic.Anthropic()
PROMPT = "Suggest a name for a coffee shop run by robots. Reply with the name only."
def sample(temperature=None, top_p=None, n=4):
    kwargs = dict(model="claude-sonnet-4-5", max_tokens=20,
                  messages=[{"role": "user", "content": PROMPT}])
    if temperature is not None: kwargs["temperature"] = temperature
    if top_p is not None:       kwargs["top_p"] = top_p          # set one OR the other
    outs = [client.messages.create(**kwargs).content[0].text.strip() for _ in range(n)]
    label = f"T={temperature}" if temperature is not None else f"top_p={top_p}"
print(f"{label:>10}: {outs}")

sample(temperature=0)
sample(temperature=0.4)
sample(temperature=1.0)
sample(top_p=0.5)
sample(top_p=0.95)

Typical output (illustrative — your run will differ, which is rather the point):

       T=0: ['Brew Bot', 'Brew Bot', 'Brew Bot', 'Brew Bot']            ← same every time
     T=0.4: ['Brew Bot', 'Roast Protocol', 'Brew Bot', 'Gear & Grind']  ← mild variety
     T=1.0: ['Perk-a-Tron', 'The Soldered Bean', 'Circuit Grounds',
             'Steam.exe']                                               ← every call different
  top_p=0.5: ['Brew Bot', 'Brew Bot', 'Roast Lab', 'Brew Bot']          ← tail chopped off
 top_p=0.95: ['Caffeine Circuit', 'Mecha Mocha', 'Brew Bot', 'Volt & Bean']

Reading the sweep: temperature reshapes the whole distribution smoothly (even weird tokens keep a sliver of probability at T=1), while top_p makes a hard cut — the tail is simply gone, then the survivors are sampled normally. That's why very high temperature occasionally produces something incoherent (a genuinely rare token got lucky), while top_p keeps outputs on-distribution even when varied. In practice: leave top_p at its default and drive temperature, unless you specifically want "varied but never unhinged," which is temperature≈1, top_p≈0.9.

03 — Stop sequences: ending exactly where you want

Stop sequences shine when you want one item from a model that loves to elaborate, or when you're generating into a structured format and want to halt at a delimiter instead of paying for (and then trimming) trailing prose:

stop_sequences.py — halt generation at a delimiterpython
# Use case 1: force exactly one list item. Without the stop, you'd get 10 bullets.
resp = client.messages.create(
    model="claude-sonnet-4-5", max_tokens=100, temperature=0,
    stop_sequences=["\n"],                       # halt at the first newline
    messages=[{"role": "user",
               "content": "List startup name ideas for a plant-care app, one per line."}],
)
print(repr(resp.content[0].text))   # → 'Sproutly'   (no newline, no second item)
print(resp.stop_reason)             # → 'stop_sequence'
print(resp.stop_sequence)           # → '\n'  (which one fired)
# Use case 2: generate until the end of one XML-ish block, not beyond.
resp = client.messages.create(
    model="claude-sonnet-4-5", max_tokens=500, temperature=0,
    stop_sequences=["</summary>"],
    messages=[{"role": "user",
               "content": "Summarize the following in a <summary> tag:\n" + document}],
)
summary = resp.content[0].text.split("<summary>")[-1].strip()  # stop string not included
# Use case 3: guard rails for a Q&A bot that must answer one question at a time —
# stop before it starts inventing the user's next question:
resp = client.messages.create(
    model="claude-sonnet-4-5", max_tokens=400,
    stop_sequences=["\nUser:", "\nQ:"],
    messages=[{"role": "user", "content": "Q: What is DNS?\nA:"}],
)

Two details worth knowing: the matched stop string is not included in the returned text (budget your parser accordingly), and stop_reason/stop_sequence tell you whether you halted on a stop, ran to completion, or hit max_tokens — three very different situations for downstream code.

Mini-scenario: the flaky eval suite

Your team ships a prompt change and the eval pass-rate moves from 84% to 79%. Panic, revert, re-run: 83%. Re-run again: 86%. Two hours of archaeology later, the cause: someone left temperature unset in the eval harness (provider default is typically ~1.0), so every run sampled different outputs — the "regression" was sampling noise. The fix is one line (temperature=0 in the harness) plus one habit: any number you intend to compare across runs must come from pinned decoding settings. Keep a second eval lane at production temperature if you want to measure real-world variance — but label it as such.

The one to remember

temperature. Set it to 0 when you want the same answer every time (and to make response-caching valid). Turn it up only when you want variety. If you remember one config habit from this chapter: extraction/classification/evals at 0, creative work at 0.7+, and never tune temperature and top_p at the same time — you won't be able to tell which knob did what.

Knob gotchas

  • Unset ≠ zero. Most providers default temperature to ~1.0. If you never set it, your "deterministic" pipeline has been sampling all along.
  • max_tokens is a guillotine, not a request. The model doesn't plan around it; it just stops mid-token-stream. Truncated JSON that almost parses is the classic symptom — always check stop_reason == "max_tokens" before parsing.
  • Stop sequences match anywhere, including inside content you wanted. stop_sequences=["\n"] on a task whose valid answer contains newlines silently truncates it.
  • Reasoning/extended-thinking modes often ignore or restrict these knobs (temperature may be forced to 1, or the parameter rejected). Check the model's docs before assuming your settings apply.
  • Temperature 0 doesn't fix wrongness. It makes the model consistently pick its favorite token — if the favorite is a hallucination, you now get the same hallucination every time. Determinism ≠ correctness.

Determinism caveat

Even at temperature=0, outputs aren't guaranteed identical (floating-point non-associativity under different batch shapes, hardware differences, silent model updates). Treat "deterministic" as "very stable," not "cryptographically fixed" — and design tests to tolerate benign variation (compare parsed fields, not raw strings).

Takeaways

  • Decoding knobs control how a token is drawn from the model's distribution — temperature reshapes it, top_p truncates its tail.
  • Tune temperature or top_p, not both; 0 for repeatability, 0.7+ for variety.
  • max_tokens is a cost/runaway guard that cuts mid-sentence — always check stop_reason.
  • Stop sequences end generation exactly at your delimiter and save you the tokens you didn't want.

Exercises

  1. Run sweep.py with n=10 at T ∈ {0, 0.3, 0.7, 1.0}. Count distinct outputs at each setting and sketch the curve. At what T does your prompt stop being "stable enough" for caching?
  2. Build a classifier call (sentiment: positive/negative/neutral) with temperature=0, max_tokens=5, stop_sequences=["\n"]. Measure cost per 1,000 calls vs. the same prompt with no caps (assume illustrative prices). How much did the knobs alone save?
  3. Deliberately break JSON with max_tokens: ask for a 10-field JSON object with max_tokens=40. Write the guard that detects stop_reason=="max_tokens" and retries with a doubled cap.
  4. Reproduce the flaky-eval story: run a 20-question eval twice at default temperature and twice at 0. Report the pass-rate spread in each mode.
  5. Find a prompt where temperature=1, top_p=0.9 gives clearly better results than temperature=1 alone (hint: long creative generation, watch for the occasional derailment without top_p).
