Part 5 · Tools & actions

4

5.1 Why tools / function calling

So far the model can only emit text. Tools (a.k.a. function calling) let it do things — query a DB, hit an API, run code, search the web. This is the leap from "chatbot" to "system that acts."

5.2 The wire format

This request/response choreography is the protocol. Every framework hides it; understand it once and you can read them all — and debug the 400 errors they produce.

5.3 Schemas, validation & design

The model picks a tool and fills its arguments entirely from the schema you write. The schema is a prompt. Most "the agent is dumb" bugs are bad schemas or bad error messages.

5.4 MCP & tool ecosystems

As tools proliferated, every app reinvented how to expose them. The Model Context Protocol (MCP) standardizes it.

Part 8 · Model adaptation

3

8.1 Fine-tuning in practice

You've exhausted prompting and RAG, and you need consistent behavior — a format, a style, a narrow skill — baked in. Now, and only now, you fine-tune.

8.2 RLHF & reward modeling

SFT teaches format ("answer the request"). It cannot teach "of these two valid answers, this one is better." Preference optimization does — it's why chat models feel helpful rather than merely fluent.

8.3 DPO & modern preference optimization

DPO's insight: under RLHF's own assumptions, the optimal policy can be written in closed form — so you can skip the reward model and the RL loop, and train directly on preference pairs with a supervised loss.

Part 12 · Production architecture

10

12.1 Reference architecture

Demos are one file. Production is a system. Here's the full-stack reference architecture, the concrete decisions hiding inside every layer, two request walkthroughs (sync chat and async job), and the capacity arithmetic for a real-sized deployment.

12.2 Reliability engineering

LLM APIs rate-limit, time out, and occasionally return garbage. Agents compound small errors: a 2% failure rate per step is an 18% failure rate over a 10-step trajectory (0.98¹⁰ ≈ 0.82). Engineer for it — this chapter is the module you drop into the thin harness from the build-vs-buy chapter.

12.3 Evaluation

Agents are non-deterministic; a prompt tweak can shift a whole trajectory. Evals are how you know a change helped, not hurt. This chapter builds the complete harness: a dataset format, a runner, deterministic and judge graders, a CI gate, and the statistics that stop you from shipping noise. Three levels of eval, then the machinery.

12.4 Observability

You cannot debug a non-deterministic, multi-step, tool-calling system from print statements. Trace everything — with OpenTelemetry-shaped spans so the data outlives your current vendor — then aggregate the spans into metrics with alert thresholds you've actually chosen.

12.5 Security

An agent + powerful tools + untrusted input is a new class of risk. Design assuming it will be attacked.
