Framework, thin harness, or raw? // 11.3

The build-vs-buy question for agents isn't ideological. It's a function of how hot the path is, how weird the control flow is, and how much of the framework you're actively fighting. Here's the decision, a real-shaped story of outgrowing a framework, and the ~50 lines that replace one.

Part 11 · FrameworksChapter 11.3

01 — Overview

Use a framework when

Prototyping fast · standard patterns (RAG, manager-worker) · you want batteries (memory, tracing, HITL) included · small team.

Build a thin harness when

Hot paths needing tight cost/latency control · unusual control flow · you've outgrown the framework's abstractions and are fighting them.

Go fully raw when

Learning the fundamentals · a tiny, well-scoped agent · maximum control & minimal dependencies matter.

02 — Case study: outgrowing the framework

A composite of real teams, with illustrative numbers. A three-engineer team ships a document-processing agent on a crew-style framework: ingest a contract, extract terms, cross-check against policy, draft a summary. The prototype takes four days. Volume grows to ~40k documents/month. Then the pain arrives, in the order it usually does:

  1. Month 2 — cost. Tracing shows 31k tokens per document; a hand-count of the useful work says ~11k should suffice. The other 20k is role preambles re-sent every turn, manager deliberation, and two silent JSON-repair retries. At (assume) $3/Mtok blended and 40k docs, that's ~$2.4k/month of pure overhead. The framework has no knob for "stop resending the preamble."
  2. Month 3 — latency. p95 hits 90s because the manager agent "thinks" between every worker turn. The SLA is 30s. The only fix the framework offers is fewer agents — which is an architecture change, not a tuning knob.
  3. Month 3 — a 3am page. A malformed PDF makes the extractor agent return prose instead of JSON; the manager retries it in a loop for 22 minutes before a global timeout fires. The retry policy lives inside the framework and isn't configurable per-task.
  4. Month 4 — the monkey-patch era. The team now maintains: a patched prompt template (to cut preamble), a wrapped executor (to cap retries), and a forked memory class (to truncate history). A framework minor-version bump breaks two of the three. This is the tell: you are already maintaining a harness — it's just splattered across patches.
  5. Month 5 — the rewrite. Two engineers, nine days. The flow was never actually dynamic — it's extract → check → draft, a fixed pipeline with one LLM decision point. The eval suite (180 cases, kept framework-independent) passes within 1.5 points of baseline on day 7. Results: 31k → 12k tokens/doc, p95 90s → 24s, and every retry/timeout/truncation policy is now a line of code they own.

The moral isn't "frameworks bad." The framework was the right call for months 0–2: it made the demo exist. The mistake teams make is not the adoption — it's missing the tell in month 4 and patching for another two quarters.

The rewrite trap on the other side

Teams that rewrite too early hit the opposite failure: they rebuild the loop in a weekend, then spend a quarter rediscovering everything the framework had quietly handled — checkpoint serialization, streaming tool-call deltas, context-window truncation, provider quirks (one provider's tool_use blocks vs another's tool_calls arrays), token counting per model family. Budget the harness honestly: the loop is 50 lines; the operational 20% around it is where the real week goes. If you can't name three of those quiet features off the top of your head, you're not ready to leave the framework.

03 — The thin harness: ~50 lines that replace a framework

This is the skeleton the case-study team ended up with. Four pieces: a provider interface (so models are swappable), a tool registry (so tools are data, not wiring), the loop, and a tracing hook (so Part 12's observability chapter has somewhere to plug in). Everything else — retries, budgets, memory policy — attaches to these seams.

harness.py — provider interface, tool registry, loop, tracing hookpython
import json, time, uuid
from dataclasses import dataclass, field
from typing import Protocol, Callable, Any

# ---- 1 · provider interface: the ONLY place a vendor SDK is touched ----------
@dataclass
class ModelReply:
    text: str | None
    tool_calls: list[dict]            # [{"id","name","args"}] — normalized shape
    usage: dict # {"in": int, "out": int}
class Provider(Protocol):
    def chat(self, messages: list[dict], tools: list[dict],
             timeout_s: float) -> ModelReply: ...
# anthropic_provider.py / openai_provider.py each implement chat() in ~30 lines,
# normalizing their native tool-call format into ModelReply. Swap = one import.
# ---- 2 · tool registry: tools are data + a callable ---------------------------
@dataclass
class Tool:
    name: str; description: str; schema: dict; fn: Callable[..., Any]

class Registry:
    def __init__(self): self._t: dict[str, Tool] = {}
    def add(self, t: Tool): self._t[t.name] = t
    def specs(self): return [{"name": t.name, "description": t.description,
                              "input_schema": t.schema} for t in self._t.values()]
    def run(self, name: str, args: dict) -> str:
        if name not in self._t: return f"ERROR: unknown tool {name}"
try: return json.dumps(self._t[name].fn(**args))[:8000]  # cap output size
except Exception as e: return f"ERROR: {e}" # errors go BACK to the model
# ---- 3 · tracing hook: one callable, no vendor coupling (see Part 12) --------
def null_trace(event: str, **kw): pass
# ---- 4 · the loop -------------------------------------------------------------
def run_agent(provider: Provider, registry: Registry, messages: list[dict],
              max_iters: int = 8, budget_tokens: int = 60_000,
              trace=null_trace) -> str:
    run_id, spent = str(uuid.uuid4()), 0
for i in range(max_iters):
        t0 = time.monotonic()
        reply = provider.chat(messages, registry.specs(), timeout_s=45)
        spent += reply.usage["in"] + reply.usage["out"]
        trace("llm_call", run=run_id, iter=i, usage=reply.usage,
              ms=int((time.monotonic() - t0) * 1000))
        if spent > budget_tokens:
            trace("budget_exceeded", run=run_id, spent=spent)
            return "Sorry — I hit my processing budget on this request."
if not reply.tool_calls:
            trace("done", run=run_id, iters=i); return reply.text or ""
        messages.append({"role": "assistant", "tool_calls": reply.tool_calls,
                         "content": reply.text})
        for call in reply.tool_calls:
            out = registry.run(call["name"], call["args"])
            trace("tool", run=run_id, name=call["name"], ok=not out.startswith("ERROR"))
            messages.append({"role": "tool", "tool_call_id": call["id"], "content": out})
    trace("max_iters", run=run_id)
    return "I couldn't finish within my step limit; here's where I got: ..."

Notes on the seams: tool errors are returned to the model as text, not raised — the model often self-corrects (bad args, wrong id) and that's one recovery loop you get for free. The token budget and iteration cap are the two levers that make the harness safe to expose to users. The trace callable is deliberately a bare function: Part 12's observability chapter replaces null_trace with an OpenTelemetry-shaped one without touching this file.

What you still have to add (the honest bill)

  • Retry/backoff and fallback inside each provider's chat() — the reliability chapter's module drops in here.
  • Context management: truncate/summarize messages when they approach the window; the harness above will happily grow forever.
  • Streaming, if the UX needs it — roughly doubles the provider adapter's size.
  • Checkpointing, only if you have long jobs or HITL: persist messages + iteration index per run_id; that's a table, not a framework.

What top teams actually do

Often a hybrid: a thin custom harness on the raw SDK for the performance-critical core, with a framework for glue and less-critical flows. Because they know the agent-loop chapter loop, they can drop down to raw whenever an abstraction gets in the way. Learn the loop; frameworks become optional. The harness above is that option made concrete — 50 lines you fully own, with seams for everything Part 12 adds.

Exercises

  1. Implement Provider.chat() for one real vendor SDK (normalize its tool-call format into ModelReply). Run the harness end-to-end with two tools.
  2. Add a second provider adapter and swap providers with a one-line change. Verify your eval cases pass on both.
  3. Break a tool on purpose (raise inside fn) and confirm the model recovers by reading the ERROR text. Then make the error message uninformative ("ERROR: 1") and watch recovery quality drop.
  4. Add message-list truncation: when the running token estimate exceeds 80% of the window, summarize all but the last 4 messages into one system note. Measure quality on your eval set before/after.
  5. Take the month-2 cost numbers from the case study (31k vs 12k tokens/doc, 40k docs/month) and compute the monthly savings at your provider's current prices. At what volume would the 9-day rewrite have paid for itself in under a quarter?
