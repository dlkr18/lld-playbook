The lesson

03 — The question

Inference internals explains what one GPU does with one batch. Serving is the next layer up: turning a traffic forecast and a latency target into a number of GPUs, a way to spread requests across them, a rule for adding and removing them, and a benchmark you can trust. It is classic capacity planning, with two twists: the unit of work is the token rather than the request, and each request occupies memory for its whole lifetime.

The questions interviewers ask:

  1. Given a traffic forecast and a latency target, how many GPUs do you need, and how do you justify the number?
  2. When do you add replicas and when do you split one model across GPUs?
  3. How do you route and autoscale LLM traffic, and why is CPU or GPU utilisation the wrong signal?
  4. How do you benchmark a serving setup so the numbers mean something?

Running example. An internal assistant runs the 8B model from Inference internals (16 GB of BF16 weights, 128 KiB of KV cache per token) on H100 80 GB GPUs. At the daily peak it receives 12 requests per second; an average request has a 1,500-token prompt and a 250-token answer. The SLO is p95 TTFT under 1 s and p95 TPOT under 40 ms. Off-peak traffic averages 4 requests per second. As before, hardware figures are datasheet values (989 TFLOP/s BF16, 3.35 TB/s) and every result is a napkin estimate to be confirmed by load testing.

04 — Step 1: the parts of a serving system

A request passes through four layers, each with one job:

client ──► gateway ──────► router ──────────► engine replica (GPU)
           auth, quotas,   picks a replica:   scheduler: who runs this step
           rate limits,    load, prefix,      KV manager: blocks per sequence
           request logs    model / adapter    model runner: the forward pass
                                              └─ streams tokens back (SSE)
  • The gateway handles everything that is about the caller: authentication, per-tenant token quotas, request size limits, logging.
  • The router picks which replica serves the request. For LLMs this is not a plain round-robin balancer, for reasons in Step 6.
  • The engine runs the continuous-batching loop: each iteration the scheduler decides which sequences decode and which prefills (or prefill chunks) run, the KV manager allocates blocks, and the runner executes one forward pass.

The engine is where performance is won or lost, but the layers around it decide whether the system survives real traffic. Treat the engine as a stateful service: in-flight generations die with the process, so deploys must drain replicas before restarting them.

05 — Step 2: from requests to tokens and concurrency

Requests per second is the wrong unit, because two requests can differ in cost by a factor of a hundred. Convert to tokens:

  • Prefill load: 12 × 1,500 = 18,000 prompt tokens/s, which costs compute.
  • Decode load: 12 × 250 = 3,000 output tokens/s, which costs bandwidth and KV memory.

Then convert to concurrency with Little's law: the average number of requests in the system \(L\) equals the arrival rate \(\lambda\) times the average time each spends inside, \(W\):

\[ L = \lambda W \]

If TTFT is about 0.2 s and TPOT about 20 ms, one request lives for \(W \approx 0.2 + 249 \times 0.02 \approx 5.2\) s, so at 12 requests per second about \(12 \times 5.2 \approx 62\) requests are in flight at any moment. That is the batch the GPUs must hold, and it is why memory, not request rate, is often the binding constraint: 62 sequences each need their own KV cache for five seconds.

Little's law also shows a feedback loop. If the server slows down, \(W\) grows, so more requests are in flight, so the batch is bigger, so each step is slower. Overloaded LLM servers do not degrade gently; they spiral until memory runs out and the scheduler starts preempting.

06 — Step 3: what one replica can carry

One replica has a fixed budget of GPU time per second, shared by two kinds of work:

  • Prefill costs \(2 \times 8.03\times10^{9} \times 1{,}500\) FLOPs per request; at half of peak compute, about 48.7 ms of GPU time. At \(\lambda\) requests per second it occupies a fraction \(\rho_{\text{pre}} = \lambda \times 0.0487\) of the GPU.
  • Decode gets the rest. A decode step at batch \(B\) takes about \((W + B \times \text{KV}_{\text{seq}}) / \text{bandwidth}\), and since prefill chunks are interleaved with decode steps, the time between a user's tokens is stretched to roughly \(\text{step} / (1 - \rho_{\text{pre}})\).

Combine that with Little's law (the batch \(B\) equals \(\lambda\) times time in system, which itself depends on TPOT) and solve for the steady state. The code at the end does it; the results for our 12 requests per second split across \(n\) replicas:

Three things to read off. First, with a 1,500-token prompt, prefill is the larger consumer: one replica spends 58% of its time on prompts. Long-prompt workloads (RAG, agents with big tool schemas) are compute-heavy even though people think of LLM serving as bandwidth-bound. Second, a single replica technically meets the TPOT target at peak, at 21.5 ms against 40. Third, memory is nowhere near full, so this workload is limited by compute, not KV capacity. A workload with 30,000-token prompts or long answers would flip that.

The model is optimistic (real kernels rarely sustain 50% of peak, and it ignores queueing), which is exactly why the next step matters.

07 — Step 4: the latency curve and the operating point

Averages hide queues. Requests do not arrive evenly; they arrive in random bursts, and a burst that lands while the GPU is busy waits. Queueing theory gives the shape: for a single busy resource, the expected wait grows like

\[ \text{wait} \propto \frac{\rho}{1 - \rho} \]

At \(\rho = 0.5\) the factor is 1; at 0.9 it is 9; at 0.95 it is 19. Simulating random (Poisson) arrivals into the prefill queue of one replica, assuming waiting prefills run ahead of decode steps (decode absorbs whatever time is left, as Step 3 modelled), gives p95 TTFT of:

LoadPrefill busyp95 TTFT
6 req/s29%100 ms
12 req/s58%180 ms

Latency is nearly flat up to about 60% busy, then climbs steeply: the "knee". The last 10% of capacity is bought with a tenfold rise in tail latency. This is the reason capacity plans target 60 to 70% utilisation at peak instead of 100%, and why the number that matters is goodput, the rate the system sustains while meeting the SLO, not its maximum throughput. A benchmark that reports "9,000 tokens/s" without the latency at which it was measured is reporting the far side of the knee.

08 — Step 5: scaling out, replicas versus tensor parallelism

There are two ways to add GPUs, and they buy different things.

More replicas (data parallelism for serving) multiply throughput. Each replica is independent, so there is no communication cost, failures are isolated, and capacity grows linearly. They do nothing for single-request latency: a replica serving one user is as fast as it was.

Tensor parallelism splits each layer across \(t\) GPUs. Each GPU holds and reads \(1/t\) of the weights per step, so decode steps get faster, and the combined memory can hold a model too big for one GPU. The price is two all-reduce operations per layer per step, which is fast over NVLink inside one server and slow across servers, so TP normally stays within a node.

For a model that does not fit, TP is mandatory. A 70B model in BF16 is 140 GB, and its KV cache (80 layers, 8 KV heads, head dimension 128) is 320 KiB per token:

  • TP = 2 on two 80 GB GPUs: 70 GB of weights each, leaving about 12 GB of KV room in total, roughly 22 of our requests. It fits, but barely serves anyone.
  • TP = 4: 35 GB of weights each, about 164 GB of KV room, roughly 308 requests. This is the practical minimum for real traffic in BF16.
  • FP8 weights on TP = 2: 70 GB of weights, 35 GB per GPU as with BF16 on TP = 4, leaving about 82 GB of KV room, roughly 154 requests, on half the GPUs. Quantization (Quantization & compression) and TP are alternative ways to buy memory.

The rule: use the smallest TP degree that fits the model with healthy KV room and meets the TPOT target, then scale throughput with replicas of that unit. For our 8B model the unit is one GPU. Spreading it over two GPUs would cut TPOT a little but waste a second GPU's worth of capacity on communication.

09 — Step 6: routing

A plain load balancer distributes requests evenly by count. For LLMs that is a poor proxy for load: one request may carry a 20,000-token prompt and ask for 2,000 tokens, the next 200 and 20. Two routing signals work better:

  • Least outstanding work. Route to the replica with the fewest queued plus running tokens (or the lowest KV-cache usage), read from each engine's metrics. This keeps one replica from collecting all the heavy requests by chance.
  • Prefix affinity. A multi-turn conversation resends its whole history each turn. If turn 5 lands on the replica that served turn 4, prefix caching can reuse the history's KV blocks; on any other replica it is recomputed. With three replicas and random routing, a conversation's next turn finds its cache only one time in three. Routing by a hash of the conversation or of the shared prefix sends it home nearly every time, which saves both prefill compute and TTFT.

The two signals conflict: affinity concentrates load, balancing spreads it. Production routers use affinity until the preferred replica is noticeably busier than the others, then spill over. The router is also where model and adapter selection happen when one fleet serves several models.

10 — Step 7: autoscaling and cold starts

Traffic for our assistant swings from 4 requests per second off-peak to 12 at peak. Sizing for peak all day leaves two-thirds of the fleet idle whenever traffic is at its off-peak level, so the fleet should scale. Two problems make LLM autoscaling different from scaling a web service.

The signal. CPU utilisation is meaningless (the work is on the GPU), and GPU compute utilisation is misleading (decode is memory-bound, so it looks low even under heavy load). Scale on the quantities that predict SLO violations: the number of waiting requests in each engine's queue, KV-cache usage, and measured p95 TTFT. A replica with requests waiting and KV usage near 90% is full regardless of what the utilisation gauge says.

The delay. A new replica must start a machine, pull a container, load 16 GB of weights (at an illustrative 1 GB/s from network storage, 16 s; a 140 GB model takes minutes), allocate the KV pool and warm up kernels. A minute or more from decision to serving is common. Traffic that doubles in thirty seconds outruns that. The consequences:

  • Keep a minimum fleet that absorbs normal bursts: here, two replicas, which also gives N+1 redundancy, since one replica alone still meets the TPOT target at peak (Step 3).
  • Scale up early, on a leading signal such as queue growth, and scale down slowly, to avoid oscillation.
  • Make cold starts shorter where it is cheap: weights cached on local disk, pre-built images, snapshots of an initialised engine.
  • Shed load deliberately when scaling cannot keep up: reject or queue low-priority traffic at the gateway rather than letting every request miss the SLO.

11 — Step 8: benchmarking honestly

Most published serving numbers cannot be compared with each other, because the benchmark decided the answer. The rules that make a benchmark mean something:

  1. Use open-loop load for capacity questions. A closed-loop tester with 32 virtual users sends a new request only when one finishes. If the server slows down, the tester slows down with it, so queues never build and tail latency looks fine. Real users do not wait for each other. An open-loop tester sends requests at a set rate (ideally random, Poisson-distributed gaps) and so reproduces the knee from Step 4. Closed-loop numbers are useful for "how fast is one request" and misleading for "how many users can we serve".
  2. Use the real length distribution. Fixed 512-in/128-out prompts hide the long-prompt stalls and long-answer memory pressure that dominate real tails. Sample prompt and output lengths from production logs, including the long tail.
  3. Match cache behaviour. Random prompts get no prefix-cache hits and understate a chat workload; replaying one prompt gets 100% and overstates it.
  4. Pin everything else: model build, precision, engine version, max batch, sampling parameters (temperature changes answer length), and warm the server up before measuring.
  5. Report the curve, not a point: p50, p95 and p99 of TTFT and TPOT at several request rates, and the goodput at your SLO.

12 — Step 9: disaggregation, adapters, and choosing an engine

Disaggregated prefill and decode. Step 3 showed prefill and decode competing for the same GPU, and chunked prefill only softens that. Disaggregated serving runs them on separate pools: prefill GPUs process prompts and hand the KV cache to decode GPUs, which only generate. Each pool can be sized and tuned for its own bottleneck, and long prompts never stall anyone's stream. The cost is moving the cache: 1,500 tokens × 128 KiB ≈ 197 MB per request, about 2.4 GB/s at our peak, which needs a fast interconnect. It pays off at large scale with strict TPOT targets, not for a two-GPU fleet.

Multi-LoRA serving. If ten teams each fine-tune the model with LoRA, ten separate deployments would need ten sets of 16 GB weights. A rank-16 adapter on the attention projections of this model is about 13.6 million parameters, roughly 27 MB. Engines that support multi-LoRA keep one base model and many adapters in memory and batch requests for different adapters together, so ten fine-tunes cost little more than one deployment. See Fine-tuning, LoRA & QLoRA for the adapter maths.

Engines. vLLM and SGLang are the general-purpose open-source choices (paged KV cache, continuous batching, prefix caching, an OpenAI-compatible API); TensorRT-LLM trades setup effort for peak performance on NVIDIA hardware; llama.cpp and Ollama target laptops and single users. Pick on the features your workload needs and on your own benchmark, run as in Step 8, not on someone else's chart.

13 — A worked plan you can defend

"Serve the internal assistant: 12 req/s at peak, 1,500 in / 250 out, p95 TTFT < 1 s, p95 TPOT < 40 ms."

  1. Load in tokens: 18,000 prompt and 3,000 output tokens per second at peak; about 62 requests in flight by Little's law.
  2. Unit: one H100 per replica. The 8B model fits with over 60 GB of KV room; TP would waste capacity.
  3. Per-replica capacity (napkin): about 12 req/s with 58% of time on prefill and TPOT around 21 ms. Discount by half for real-kernel efficiency and keep peak utilisation near 60%: plan on about 5 to 6 req/s per replica until a load test says otherwise.
  4. Fleet: 2 replicas minimum (off-peak plus redundancy), autoscaling to 3 or 4 at peak on queue depth and KV usage.
  5. Routing: least outstanding tokens, with conversation affinity for prefix-cache hits; prefix caching on, since every request starts with the same system prompt.
  6. Verification: open-loop load test with production length distributions at 4, 8, 12 and 16 req/s; confirm goodput at the SLO and find the knee.
  7. Cost check (illustrative prices): three GPUs around the clock at $2.50 per hour is about $5,500 a month. If the day averages about 6 requests per second (4 off-peak, 12 at peak), the month is about 15.6 million requests; through an API priced at $0.25 per million input and $1.25 per million output tokens that is about $10,700. Self-hosting is roughly half the bill at this volume, but the gap is about one engineer's part-time attention, so operations effort, quality and data-handling rules decide it; at a third of the traffic the API (about $3,560) already costs less than even the two-GPU minimum fleet (about $3,650). 14 — In code: a capacity model, a queue, and a launch

The steady-state model behind Step 3. It solves the loop "batch depends on TPOT, TPOT depends on batch" by iteration.

P, W = 8.03e9, 16.06e9 # params, weight bytes (BF16)
KV_TOK = 131_072 # bytes per token (32 layers, 8 KV heads, dim 128, BF16)
FLOPS, MFU, BW = 989e12, 0.5, 3.35e12
PROMPT, OUT = 1500, 250
def replica(lam):
    """Steady state of one replica at lam requests/s (continuous batching)."""
    t_prefill = 2 * P * PROMPT / (FLOPS * MFU)          # GPU-seconds of prefill per request
    rho_pre = lam * t_prefill                            # share of GPU time spent in prefill
if rho_pre >= 1:
        return None
    kv_seq = KV_TOK * (PROMPT + OUT / 2)                 # average cache per running sequence
    B = 1.0
for _ in range(200):                                 # fixed point: B = lam * time-in-system
        step = max((W + B * kv_seq) / BW, 2 * P * B / FLOPS)
        tpot = step / (1 - rho_pre)                      # decode only gets the time prefill leaves
        B = lam * (t_prefill + OUT * tpot)
    mem = (W + B * KV_TOK * (PROMPT + OUT)) / 1e9
return rho_pre, B, tpot, mem

for n in (1, 2, 3, 4):
    r = replica(12 / n)
    if r is None:
        print(f"{n} replica(s): prefill alone saturates the GPU")
        continue
    rho, B, tpot, mem = r
    print(f"{n} replica(s): {12/n:4.1f} req/s each | prefill {rho:4.0%} of GPU | "
f"~{B:3.0f} in flight | TPOT {tpot*1e3:4.1f} ms | KV+weights {mem:4.1f} GB")

The queueing simulation behind Step 4: Poisson arrivals into one replica's prefill queue, using Lindley's recursion (each request waits for whatever work is still ahead of it).

import random

def p95_ttft(rate, service=0.0487, n=200_000, seed=0):
    """Open-loop arrivals (Poisson) into a prefill queue; Lindley's recursion for the wait."""
    rng = random.Random(seed)
    wait, ttfts = 0.0, []
    for _ in range(n):
        ttfts.append(wait + service)
        gap = rng.expovariate(rate)                  # time until the next arrival
        wait = max(0.0, wait + service - gap)        # next request's queueing delay
    ttfts.sort()
    return ttfts[int(0.95 * n)]

for rate in (6, 12, 16, 18, 19.5):
    rho = rate * 0.0487
print(f"{rate:5.1f} req/s  prefill busy {rho:4.0%}  p95 TTFT {p95_ttft(rate)*1e3:6.0f} ms")

15 — What & Why

Self-host Llama, Mistral, Qwen when data residency, cost at scale, or predictable latency beat closed APIs. vLLM is the production inference engine; Ollama is the developer UX layer for local iteration. Both expose OpenAI-shaped APIs so LangChain/LangGraph code swaps with a base_url change.

Functional requirements

  • Chat completions with streaming tokens
  • Concurrent requests with batching (not one-at-a-time)
  • Tool calling / JSON mode for agent graphs
  • Configurable context length and temperature per model
  • Embeddings served separately via TEI (not vLLM)

Non-functional requirements

  • Throughput: maximize tokens/sec per GPU via continuous batching
  • Memory: fit model weights + KV cache in VRAM (quantization helps)
  • Latency: TTFT < 500 ms; streaming for UX
  • Availability: health checks, rolling deploy, queue depth autoscale
Not for embeddings: use TEI for Choosing an embedding model. vLLM is LLM generation only.

20 — vLLM Deep Dive

PagedAttention: KV cache split into fixed-size blocks with block table (like OS virtual memory); continuous batching scheduler adds new requests without waiting for batch completion.

Key flags for production The RAG pipeline:

--enable-prefix-caching     # shared system prompts
--max-model-len 8192        # cap KV RAM; lower if OOM
--gpu-memory-utilization 0.9
--tensor-parallel-size 2    # 70B across 2 GPUs
--quantization awq          # 4-bit weights
  • Prefix caching: identical RAG system prompt + tool defs cached across users
  • Speculative decoding: draft model + verify (advanced latency win)
  • Structured output: guided JSON for tool calls

30 — Measure it yourself — a TTFT/TPOT benchmark client

Any OpenAI-compatible endpoint (vLLM included) can be benchmarked with ~60 lines of asyncio. The essential trick: stream, and timestamp the first chunk (TTFT) separately from the rest (TPOT). This is the tool you rerun for every "one factor changed" experiment:

bench.py — TTFT/TPOT under concurrency against any OpenAI-compatible serverpython
import asyncio, time, statistics, argparse, random
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="x")
MODEL = "meta-llama/Llama-3.1-8B-Instruct"
async def one_request(prompt: str, max_tokens: int) -> dict:
    t0 = time.perf_counter()
    ttft, n_chunks, last = None, 0, t0
    stream = await client.chat.completions.create(
        model=MODEL, stream=True, max_tokens=max_tokens, temperature=0.7,
        messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if not chunk.choices or chunk.choices[0].delta.content is None:
            continue
        now = time.perf_counter()
        if ttft is None:
            ttft = now - t0            # first token: queue + prefill
        n_chunks += 1
        last = now
    # TPOT = generation time / tokens AFTER the first (chunk≈token for vLLM)
    tpot = (last - (t0 + ttft)) / max(n_chunks - 1, 1)
    return {"ttft": ttft, "tpot": tpot, "toks": n_chunks, "total": last - t0}

async def run(concurrency: int, n_requests: int):
    # workload realism: mixed prompt lengths, like production. Pin the seed.
    random.seed(0)
    prompts = [("Summarize: " + "lorem ipsum " * random.choice([50, 200, 800]))
               for _ in range(n_requests)]
    sem = asyncio.Semaphore(concurrency)          # closed-loop load model
async def guarded(p):
        async with sem:
            try:
                return await one_request(p, max_tokens=256)
            except Exception as e:                # count failures — don't hide them
return {"error": str(e)}
    t0 = time.perf_counter()
    results = await asyncio.gather(*[guarded(p) for p in prompts])
    wall = time.perf_counter() - t0
    ok = [r for r in results if "error" not in r]

    def pct(xs, p): return statistics.quantiles(xs, n=100)[p - 1]
    ttfts = [r["ttft"] for r in ok]; tpots = [r["tpot"] for r in ok]
    print(f"concurrency={concurrency} ok={len(ok)}/{n_requests}")
    print(f"  TTFT  p50={pct(ttfts,50)*1e3:6.0f}ms  p99={pct(ttfts,99)*1e3:6.0f}ms")
    print(f"  TPOT  p50={pct(tpots,50)*1e3:6.1f}ms  p99={pct(tpots,99)*1e3:6.1f}ms")
    print(f"  throughput = {sum(r['toks'] for r in ok)/wall:,.0f} out-tok/s")

if __name__ == "__main__":
    a = argparse.ArgumentParser()
    a.add_argument("--concurrency", type=int, default=16)
    a.add_argument("--n", type=int, default=200)
    args = a.parse_args()
    asyncio.run(run(args.concurrency, args.n))

33 — Diagnosing "inference is slow"

  1. Separate queue time vs prefill vs decode — three different diseases. High TTFT + normal TPOT = queue/prefill (add replicas, chunk prefill, cache prefixes). Normal TTFT + high TPOT = decode pressure (batch too big, KV-bound — quantize KV, shed load).
  2. Check prompt/output length distribution (one 30K-token prompt stalls a batch; enable chunked prefill).
  3. Check GPU memory pressure — KV cache eviction/recompute thrashing shows up as preemption counts and sawtooth throughput.
  4. Confirm p95/p99, not a warm single request — and confirm with bench.py at production-shaped concurrency, not a curl.

Benchmarking gotchas that produce fake numbers

  • Cold-start contamination: first requests pay CUDA-graph capture and an empty prefix cache. Warm up, then measure.
  • Uniform prompts: benchmarking with one fixed prompt makes the prefix cache absorb all prefills — TTFT looks 10× better than production. Use mixed, realistic lengths (or disable the cache and say so).
  • Unbounded max_tokens with EOS-stopping: output-length distribution silently differs between runs; pin max_tokens or report the achieved distribution.
  • Closed-loop-only load: a semaphore client (like bench.py) self-throttles when the server slows — it understates queueing vs real open-loop arrivals. Fine for comparisons; for capacity planning, also test fixed request-rate arrivals.
  • Comparing across changed sampling params (temperature changes length changes batch pressure) or across different tokenizers ("tokens/s" from two tokenizers aren't the same unit).

Takeaways

Default to hosted; self-host on data boundaries, adapters, or big steady volume. A vLLM deployment is ~8 flags, each mapping to an internals concept — max-model-len and KV dtype set concurrency, prefix cache sets TTFT, chunked prefill protects TPOT. Benchmark with a streaming client at swept concurrency, report throughput at your SLO, change one factor per run, and re-run the hosted-vs-self-host arithmetic with your own measured tok/s — never someone else's marketing number.

35 — Recap

Chat is sync and short; agents can run for minutes. Your serving design must handle both.

The mini-scenario that motivates everything here: your coding agent works beautifully in the demo — one user, one request, a websocket held open for four minutes. Then you launch. A deploy restarts the pods mid-run and thirty users' agents vanish silently. A burst of traffic hits the provider rate limit and every request — including the ones already 3 minutes into their run — starts failing on step 9 of 10. Nothing here is an LLM problem; it's a distributed-systems problem you inherited the moment a "request" stopped fitting inside an HTTP timeout.

Short / interactive

Synchronous request → stream the response. Keep tool calls fast; enforce a per-request timeout + step cap.

Long-running jobs

Don't hold an HTTP connection for a 5-minute agent. Enqueue the job → async workers run the loop → client polls / gets a webhook / streams via SSE. Persist checkpoints so a crashed job resumes (LangGraph/Temporal-style durability).

Scaling the fleet

Agent workers are mostly I/O-bound (waiting on the LLM). Scale horizontally; the real ceiling is usually your LLM provider rate limits / quota, not CPU. Add a quota limiter + queue.

State & sessions

Externalize state (Redis/Postgres) so any worker can handle any turn. Keep conversation/session memory out of process memory.

import json, asyncio, socket

WORKER_ID = socket.gethostname()
MAX_STEPS, LEASE_S = 15, 120 # lease > slowest single step
async def worker_loop():
    while True:
        _, job_id = await rds.brpop("agent:queue", timeout=5) or (None, None)
        if job_id: await run_job(job_id.decode())

async def run_job(job_id: str):
    # claim with a lease so a dead worker's job gets re-queued, and a
# slow-but-alive worker isn't double-run (heartbeat extends the lease)
    claimed = await db.fetchrow(
        """UPDATE agent_jobs SET status='running', worker=$2,
                  lease_until=now() + interval '120 seconds'
           WHERE id=$1 AND (status='queued' OR
                 (status='running' AND lease_until < now()))
           RETURNING input, step""", job_id, WORKER_ID)
    if not claimed: return # someone else has it
# ---- RESUME: rebuild agent state from the last checkpoint ----
    ckpt = await db.fetchrow(
        """SELECT state FROM agent_checkpoints
           WHERE job_id=$1 ORDER BY step DESC LIMIT 1""", job_id)
    state = AgentState.from_json(ckpt["state"]) if ckpt \
            else AgentState.initial(json.loads(claimed["input"]))

    try:
        while not state.done and state.step < MAX_STEPS:
            state = await agent_step(state)          # ONE llm call + tools
async with db.transaction():             # atomic: step + heartbeat
await db.execute(
                    """INSERT INTO agent_checkpoints (job_id, step, state)
                       VALUES ($1, $2, $3)""",       # append-only = audit trail
                    job_id, state.step, state.to_json())
                await db.execute(
                    """UPDATE agent_jobs SET step=$2,
                              lease_until=now() + interval '120 seconds'
                       WHERE id=$1""", job_id, state.step)
            await publish_event(job_id, state.last_event)  # feeds SSE (below)
        final = "done" if state.done else "failed" # step cap exhausted
await db.execute(
            "UPDATE agent_jobs SET status=$2, result=$3 WHERE id=$1",
            job_id, final, state.result_json())
    except Exception as e:                   # crash → job re-queued by lease
await db.execute(                    # expiry; resume picks up at the
"UPDATE agent_jobs SET status='queued', error=$2 WHERE id=$1",
            job_id, repr(e))                 # last checkpoint, not step 0
await rds.lpush("agent:queue", job_id)

# but BEFORE the checkpoint means the tool may run twice on resume. Reads
# are fine; writes (send email, create ticket) need an idempotency key:
#   tool_call_id = f"{job_id}:{step}:{tool_name}"  → dedupe at the tool layer.

38 — The real ceiling: provider quota, and a token bucket for it

Your provider limits you in requests/min and tokens/min. Uncoordinated workers discover the limit by getting 429s — and naive per-worker retries synchronize into stampedes. Put one shared limiter in front of every call, denominated in tokens, because that's the scarcer unit for agent workloads.

token_bucket.py — shared, token-denominated rate limiter (Redis Lua = atomic)python
LUA = """
local key, now = KEYS[1], tonumber(ARGV[1])
local rate, burst, want = tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local b = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(b[1]) or burst
local ts     = tonumber(b[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)   -- refill
if tokens >= want then
  redis.call('HMSET', key, 'tokens', tokens - want, 'ts', now)
  redis.call('EXPIRE', key, 120)
  return -1                                             -- granted
end
return math.ceil((want - tokens) / rate)                -- seconds to wait
"""
class SharedTokenBucket:
    """One bucket across ALL workers. rate/burst in provider tokens/sec."""
def __init__(self, rds, key="llm:tpm", rate=8000.0, burst=480_000):
        self.rds, self.key, self.rate, self.burst = rds, key, rate, burst
        self._script = rds.register_script(LUA)

    async def acquire(self, est_tokens: int, max_wait_s=60):
        import time, random
        waited = 0.0
while True:
            delay = await self._script(
                keys=[self.key],
                args=[time.time(), self.rate, self.burst, est_tokens])
            if int(delay) < 0: return
            sleep = min(int(delay), 5) + random.random()   # jitter: don't
            waited += sleep                                # re-synchronize
if waited > max_wait_s:
                raise QuotaSaturated(f"waited {waited:.0f}s for quota")
            await asyncio.sleep(sleep)

# usage inside agent_step():
#   await bucket.acquire(est_tokens=count_tokens(prompt) + max_tokens)
#   resp = await client.messages.create(...)
# est_tokens can be rough; reconcile with resp.usage and adjust if you
# consistently under-estimate (that's how buckets quietly overshoot TPM).

QuotaSaturated is a feature, not a failure: it's the backpressure signal. Catch it in the worker, put the job back on the queue with a delay, and let queue depth grow — visible, bounded degradation instead of a 429-retry storm that burns quota on failures.

39 — Capacity math: a worked example

Illustrative numbers, but do this arithmetic for your own system — it takes ten minutes and prevents a launch-day incident. Target: 1,200 agent jobs/hour at peak; a job averages 8 LLM steps, ~7,000 input + 400 output tokens per step, provider latency ~6s/step, tool time ~2s/step.

  • Throughput per job: 8 × (6s + 2s) = ~64s of wall-clock, nearly all of it awaiting I/O.
  • Concurrency needed: 1,200 jobs/hr = 0.33 jobs/s × 64s = ~22 jobs in flight (Little's Law). With async workers running ~30 concurrent jobs per process comfortably (I/O-bound), that's one worker pod, two for redundancy. CPU is irrelevant; don't autoscale on it.
  • Provider quota — the real constraint: 1,200 jobs/hr × 8 steps × 7.4k tokens ≈ 71M tokens/hour ≈ 1.18M tokens/min. If your tier allows 400k TPM, you are 3× over: peak-hour jobs will queue for ~2 hours no matter how many pods you add. Options: raise the tier, shrink the prefix (Cost & latency — cached reads often don't count against TPM the same way, check your provider), route steps to a second model/region pool, or shed load.
  • Queue sizing: at 3× over quota for a 1-hour peak, backlog grows at ~0.66 jobs/s → ~2,400 jobs deep. At ~2KB of queue payload each that's trivial for Redis — the problem isn't memory, it's the 2-hour p99 completion time. Decide now what you'll shed or defer.

Autoscaling signals that actually work

Scale workers on queue depth / oldest-job age (KEDA-style), cap the fleet at quota ÷ per-worker token burn, and alert on bucket wait time — that's your leading indicator of saturation. CPU-based autoscaling on I/O-bound agent workers does nothing until it does harm: more pods, same quota, deeper 429s. The bottleneck is tokens/min, so the scaler must be denominated in tokens/min.

Durable execution

For complex long-running multi-step agents, durable workflow engines (Temporal, or LangGraph's checkpointer) let a job survive crashes/deploys and resume mid-flight — critical when a single run spans many tool calls and minutes. The worker above is the minimal homegrown version: once you need sub-workflows, signals ("user replied mid-run"), scheduled retries with backoff policies per activity, or exactly-once semantics across services, buy the engine instead of growing the 60 lines into 6,000.

Serving gotchas

  • The double-fired tool: crash between tool execution and checkpoint → resume re-runs the step → the customer gets two refund emails. Any side-effecting tool needs an idempotency key derived from (job_id, step); this is the single most common durable-agent bug.
  • Graceful shutdown that isn't: deploys SIGTERM your workers mid-step. Trap it, finish the current step, checkpoint, re-queue — and set terminationGracePeriodSeconds longer than your slowest step, or Kubernetes SIGKILLs you anyway.
  • Buffered "streaming": nginx/ALB/CDN default to buffering; your SSE arrives as one lump after 60s. X-Accel-Buffering: no, disable proxy buffering, send keepalive comments.
  • Sticky sessions as state management: pinning a conversation to a pod works until that pod dies. Externalized state + any-worker routing is barely more code and removes the whole failure class.
  • Retry amplification across layers: client retries × API retries × worker retries × SDK retries = one flaky provider minute becomes 16× traffic. Retry in one layer (the worker), make everything else fail fast.
  • One tenant eats the bucket: a single customer's batch job starves interactive traffic. Two buckets — per-tenant and global — and a priority queue (interactive ahead of batch) is the 80/20 fix.

42 — Where people get lost

  • Ollama in prod multi-tenant — no SLO, queue, or HA story
  • OOM from max-model-len too high — lower len or reduce concurrent requests
  • No batching / single-thread HF — 5–20× throughput left on table
  • vLLM for embeddings — use TEI instead
  • Skip quant eval — deploy AWQ without task benchmark
  • Cold start on scale-to-zero — first request 60s+ model load
  • "Plan capacity in requests per second." Requests differ in cost by orders of magnitude. Plan in prompt tokens and output tokens per second, and in concurrent sequences.
  • "Run the GPUs at 95% to save money." Tail latency explodes past the knee (Step 4). Plan for 60 to 70% at peak and buy the rest with autoscaling.
  • "Tensor parallelism is how you scale." TP is how you fit a model and lower per-token latency. Throughput scales with replicas; use the smallest TP degree that works.
  • "Autoscale on GPU utilisation." Decode looks underutilised even when full. Scale on waiting requests, KV-cache usage and measured TTFT.
  • "Our benchmark shows 32 users are fine." A closed-loop benchmark hides queueing. Test open-loop at target arrival rates with real length distributions.
  • "Round-robin is good enough." It ignores request size and throws away prefix-cache hits. Route on outstanding tokens with affinity.
  • "Restarting a replica is harmless." In-flight generations die with it. Drain before restart, and have clients retry idempotently.

44 — Check yourself

Traffic is 30 req/s with an average time in system of 8 s. How many sequences are in flight, and why does that number matter more than the request rate?
Little's law: \(30 \times 8 = 240\). Each in-flight sequence holds its own KV cache, so this concurrency sets the memory requirement and the batch size, and through them TPOT.
Why does p95 TTFT go from 335 ms to 1.5 s when load rises from 78% to 95% busy, even though throughput rose only 22%?
Queueing delay grows roughly like \(\rho/(1-\rho)\): 3.5 at 78%, 19 at 95%. Random bursts that arrive while the GPU is busy wait for all the work ahead of them, and near saturation that backlog rarely clears.
A 70B model in BF16 must serve about 200 concurrent 1,600-token conversations. TP=2 or TP=4 on 80 GB GPUs?
KV per conversation is about \(327{,}680 \times 1{,}600 \approx 0.52\) GB, so 200 need about 105 GB. TP=2 leaves only about 12 GB after 140 GB of weights and overhead; TP=4 leaves about 164 GB. TP=4 (or quantized weights on fewer GPUs).
Your load test with 64 virtual users shows p95 TTFT of 300 ms, yet production at the same average throughput sees 2 s. What is the likely cause?
The test was closed-loop: users waited for responses before sending more, so bursts never formed. Production arrivals are open-loop and bursty. Re-test with open-loop Poisson arrivals and production length distributions.
Should an 8B model that fits on one GPU be served with TP=2 to handle more traffic?
No. TP=2 adds per-layer communication and halves the number of independent replicas you get from the same GPUs. Two TP=1 replicas give more throughput and isolation; use TP only to fit a model or to meet a TPOT target one GPU cannot.
Name three signals you would autoscale on and one you would not, with reasons.
Scale on waiting-request count, KV-cache usage and p95 TTFT, because each directly predicts SLO misses. Not on GPU compute utilisation, because memory-bound decode keeps it low even when the replica is full.
Three replicas serve multi-turn chats behind a round-robin balancer. What does switching to conversation-affinity routing change, in numbers?
With round-robin, a follow-up turn lands on the replica holding its history about one time in three, so roughly two-thirds of follow-ups recompute the whole history in prefill. With affinity nearly all of them reuse the cached prefix, cutting prefill work and TTFT for follow-ups. Watch for hot replicas and spill over when one gets much busier.
vLLM vs HuggingFace generate?
vLLM adds PagedAttention + continuous batching for 5–20× throughput on concurrent requests. HF generate is fine for single-request notebooks, not prod serving.
What is PagedAttention?
KV cache stored in non-contiguous fixed blocks with a block table, like OS virtual memory. Reduces fragmentation so more concurrent requests fit in GPU RAM.
When use Ollama vs vLLM?
Ollama: laptop dev, demos, Modelfile experiments. vLLM: production K8s GPU pool with autoscale, prefix caching, and OpenAI gateway routing.
Why OpenAI-compatible API?
Point LangChain/LangGraph/OpenAI SDK at vLLM with base_url — zero application code change for self-host migration or hybrid routing.
Quantization trade-offs?
AWQ/GPTQ 4-bit: ~4× memory savings, ~1–3% quality drop on tasks. Benchmark on your RAG/agent eval before prod.
GPU for Llama-3-8B?
1× A10/L4 24GB FP16; or 1× T4 16GB with AWQ. Reserve headroom for KV cache at target concurrent users.
Tensor parallel when?
When single GPU VRAM insufficient for model weights + KV — e.g. 70B AWQ on 2× A100 with tensor-parallel-size 2.
Prefix caching for RAG?
vLLM reuses KV blocks for identical prompt prefixes. Shared system prompt + tool definitions across users saves compute on every request.
When still use OpenAI cloud?
Frontier reasoning, zero ops, burst beyond GPU capacity. Hybrid router sends easy queries to local 8B, hard to GPT-4o.
Embed serving stack?
Text Embeddings Inference (TEI) for BGE/E5 batch GPU — not vLLM. See Choosing an embedding model.
Autoscale vLLM on K8s?
HPA on custom metric queue_depth or tokens/sec backlog; min replicas >0 to avoid cold start; GPU node pool separate from CPU.
SDE3: private LLM platform?
vLLM on K8s GPU pool; model registry (Llama/Mistral/Qwen versions); OpenAI-compatible gateway with auth; quant pipeline AWQ; A/B model versions; cost per token chargeback; fallback to cloud API; LangSmith tracing; prefix cache for RAG system prompts.
Why does 4-bit weight-only quantization speed up decode when the matmul still runs in fp16?
Decode is bound by reading weights from HBM; 4-bit cuts bytes ~4×, dequantization in registers is cheap.
Why does continuous batching beat static batching?
Sequences end at different times; static batches idle finished slots until the longest finishes. Iteration-level scheduling refills slots every step.
What problem does PagedAttention solve?
KV-cache fragmentation and over-reservation; paging lets memory be allocated on demand and shared, raising concurrency.
Why multiply the distillation KL term by T²?
Softening by T scales its gradients by 1/T²; multiplying keeps them comparable to the hard-label term.
Does speculative decoding change the output distribution?
No; the accept/reject rule preserves the target model's distribution exactly.
TTFT is fine but tokens stream slowly under load.
Decode is bandwidth/KV-bound: quantize weights and KV, enable chunked prefill, cap batch size for TPOT SLO, or add replicas/tensor parallelism.
