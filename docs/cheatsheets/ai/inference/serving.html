Serving & scaling // Inference & serving

vLLM and Ollama, benchmarking honestly, a production serving setup and scaling it.

01 — At a glance

Serve open-weight LLMs locally: vLLM for production GPU throughput (PagedAttention, continuous batching, OpenAI-compatible API), Ollama for laptop dev and quick pulls, quantization (AWQ/GPTQ), GPU sizing, and hybrid routing with cloud APIs.

vLLM serving: OpenAI-compatible /v1/chat/completions → scheduler → PagedAttention KV cache → GPU workers. 5–20× throughput vs naive HuggingFace generate on same hardware for The RAG pipeline and agent workloads.

Quick reference

02 — What & Why

Self-host Llama, Mistral, Qwen when data residency, cost at scale, or predictable latency beat closed APIs. vLLM is the production inference engine; Ollama is the developer UX layer for local iteration. Both expose OpenAI-shaped APIs so LangChain/LangGraph code swaps with a base_url change.

Functional requirements

  • Chat completions with streaming tokens
  • Concurrent requests with batching (not one-at-a-time)
  • Tool calling / JSON mode for agent graphs
  • Configurable context length and temperature per model
  • Embeddings served separately via TEI (not vLLM)

Non-functional requirements

  • Throughput: maximize tokens/sec per GPU via continuous batching
  • Memory: fit model weights + KV cache in VRAM (quantization helps)
  • Latency: TTFT < 500 ms; streaming for UX
  • Availability: health checks, rolling deploy, queue depth autoscale
Not for embeddings: use TEI for Choosing an embedding model. vLLM is LLM generation only.

07 — vLLM Deep Dive

PagedAttention: KV cache split into fixed-size blocks with block table (like OS virtual memory); continuous batching scheduler adds new requests without waiting for batch completion.

Key flags for production The RAG pipeline:

--enable-prefix-caching     # shared system prompts
--max-model-len 8192        # cap KV RAM; lower if OOM
--gpu-memory-utilization 0.9
--tensor-parallel-size 2    # 70B across 2 GPUs
--quantization awq          # 4-bit weights
  • Prefix caching: identical RAG system prompt + tool defs cached across users
  • Speculative decoding: draft model + verify (advanced latency win)
  • Structured output: guided JSON for tool calls

13 — Serving open models & benchmarking honestly

Hosted API vs self-hosted is a real decision; and every serving claim is meaningless without its workload. Here's the vocabulary and the method.

Self-hosting earns its keep in roughly four cases: data can't leave your boundary; you fine-tuned and the adapter is the product; token volume is huge and steady (the arithmetic below); or you need latency/behavior guarantees a shared API won't sign. Otherwise the hosted default stands — you are not going to out-ops a provider on their own model.

15 — A real vLLM deployment, flag by flag

The one-liner from the quickstart hides every decision that matters. Here's a production-shaped launch with each flag annotated — these flags are Inference & serving (Inference internals) turned into switches:

serve.sh — vLLM in production shape, every flag a decisionbash
pip install vllm

vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --max-model-len 8192 \
 # ^ context ceiling. Directly sets worst-case KV per sequence — the smaller
 #   you can honestly make this, the more concurrency you get. Don't default
 #   to the model's max (128K) "just in case": one flag, 16× the KV budget.
  --gpu-memory-utilization 0.90 \
 # ^ fraction of VRAM vLLM pre-allocates (weights + KV pool). Higher = more
 #   concurrent sequences; too high risks OOM from CUDA graph/overhead spikes.
  --max-num-seqs 128 \
 # ^ scheduler cap on simultaneously-running sequences. Raise for throughput,
 #   lower to protect inter-token latency under load.
  --enable-prefix-caching \
 # ^ shared-prefix KV reuse (system prompts, few-shot preambles). Near-free
 #   TTFT win when traffic shares prefixes — chat apps almost always do.
  --enable-chunked-prefill \
 # ^ big prompts prefill in slices interleaved with decode steps — protects
 #   everyone's TPOT from one 30K-token tenant (on by default in recent vLLM).
  --kv-cache-dtype fp8 \
 # ^ 8-bit KV: ~2× concurrency from the same pool. Eval quality on YOUR task.
  --quantization awq_marlin \
 # ^ only if serving a quantized checkpoint — 4-bit weights ≈ 4× less
 #   bandwidth per decode step (see the quantization table, Inference & serving).
  --tensor-parallel-size 1 \
 # ^ GPUs to shard across. 1 for an 8B on a modern card; 70B bf16 needs 4×80GB.
  --enable-lora --max-loras 8 \
 # ^ serve fine-tuned adapters (Fine-tuning & alignment) on the shared base — one deployment,
 #   many tenants/tasks, adapters hot-swapped per request by name.
  --api-key "$VLLM_API_KEY" --port 8000
# then point ANY OpenAI SDK at http://localhost:8000/v1 — same client code as LLM fundamentals

Operationally, treat it like any stateful service: scrape /metrics (Prometheus format — queue depth, KV-cache usage %, preemption count, TTFT/TPOT histograms), one model per GPU pool, a plain HTTP load balancer in front of replicas, and drain-before-restart since in-flight generations are lost on kill. The metrics to alert on: KV utilization pinned at ~100% and preemptions > 0 — that's the memory cliff from Inference internals, and p99 will have noticed before your users tell you.

The benchmarking law

Never report throughput without: concurrency, prompt/output length distribution, hardware, model, precision, and the latency constraint. "X tokens/sec" alone is marketing, not measurement. Change one factor per run (precision, max batch, prefix cache on/off) and explain the delta.

17 — Measure it yourself — a TTFT/TPOT benchmark client

Any OpenAI-compatible endpoint (vLLM included) can be benchmarked with ~60 lines of asyncio. The essential trick: stream, and timestamp the first chunk (TTFT) separately from the rest (TPOT). This is the tool you rerun for every "one factor changed" experiment:

bench.py — TTFT/TPOT under concurrency against any OpenAI-compatible serverpython
import asyncio, time, statistics, argparse, random
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="x")
MODEL = "meta-llama/Llama-3.1-8B-Instruct"
async def one_request(prompt: str, max_tokens: int) -> dict:
    t0 = time.perf_counter()
    ttft, n_chunks, last = None, 0, t0
    stream = await client.chat.completions.create(
        model=MODEL, stream=True, max_tokens=max_tokens, temperature=0.7,
        messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if not chunk.choices or chunk.choices[0].delta.content is None:
            continue
        now = time.perf_counter()
        if ttft is None:
            ttft = now - t0            # first token: queue + prefill
        n_chunks += 1
        last = now
    # TPOT = generation time / tokens AFTER the first (chunk≈token for vLLM)
    tpot = (last - (t0 + ttft)) / max(n_chunks - 1, 1)
    return {"ttft": ttft, "tpot": tpot, "toks": n_chunks, "total": last - t0}

async def run(concurrency: int, n_requests: int):
    # workload realism: mixed prompt lengths, like production. Pin the seed.
    random.seed(0)
    prompts = [("Summarize: " + "lorem ipsum " * random.choice([50, 200, 800]))
               for _ in range(n_requests)]
    sem = asyncio.Semaphore(concurrency)          # closed-loop load model
async def guarded(p):
        async with sem:
            try:
                return await one_request(p, max_tokens=256)
            except Exception as e:                # count failures — don't hide them
return {"error": str(e)}
    t0 = time.perf_counter()
    results = await asyncio.gather(*[guarded(p) for p in prompts])
    wall = time.perf_counter() - t0
    ok = [r for r in results if "error" not in r]

    def pct(xs, p): return statistics.quantiles(xs, n=100)[p - 1]
    ttfts = [r["ttft"] for r in ok]; tpots = [r["tpot"] for r in ok]
    print(f"concurrency={concurrency} ok={len(ok)}/{n_requests}")
    print(f"  TTFT  p50={pct(ttfts,50)*1e3:6.0f}ms  p99={pct(ttfts,99)*1e3:6.0f}ms")
    print(f"  TPOT  p50={pct(tpots,50)*1e3:6.1f}ms  p99={pct(tpots,99)*1e3:6.1f}ms")
    print(f"  throughput = {sum(r['toks'] for r in ok)/wall:,.0f} out-tok/s")

if __name__ == "__main__":
    a = argparse.ArgumentParser()
    a.add_argument("--concurrency", type=int, default=16)
    a.add_argument("--n", type=int, default=200)
    args = a.parse_args()
    asyncio.run(run(args.concurrency, args.n))
# sweep it:  for c in 1 4 16 64 128; do python bench.py --concurrency $c; done
# and always: warm up the server first (one throwaway run) — cold CUDA graphs
# and an empty prefix cache make run #1 lie to you.

18 — Reading a benchmark sweep

An illustrative sweep of the setup above (8B, one 80 GB GPU, mixed prompts, 256 output tokens — numbers invented for teaching, shapes realistic):

ConcurrencyTTFT p50TTFT p99TPOT p50TPOT p99Throughput (out-tok/s)
190 ms180 ms6 ms7 ms160
4100 ms220 ms7 ms9 ms580
16140 ms400 ms9 ms14 ms1,900
64310 ms1,200 ms16 ms28 ms4,800
128900 ms6,500 ms29 ms70 ms6,100
2564,200 ms21,000 ms31 ms160 ms6,300

How to read it — four observations that generalize:

  1. 1→16: near-free scaling. Throughput grows ~12× while TPOT rises only 50% — that's continuous batching amortizing weight reads (decode was bandwidth-bound and mostly idle at batch 1).
  2. 64→128: the knee. Throughput gains flatten (4,800→6,100) while p99s explode — the batch is saturating compute/KV, and new arrivals queue. Past the knee you're buying tokens/s with user pain.
  3. 128→256: pure queueing. Throughput is flat (~6,300 is this box's ceiling) and TTFT p99 is 21 s — every extra request just waits. If you see this in prod, you need replicas, not tuning.
  4. The operating point is an SLO decision, not a max. If your product needs TTFT p99 < 1 s and TPOT p99 < 30 ms, this box is a "concurrency ≈ 64, ~4,800 tok/s" machine. That — throughput at the SLO — is the number that goes in the capacity plan and the cost model below.

19 — Hosted vs self-host: the arithmetic, worked twice

Assume (all illustrative): hosted small-tier model at $0.25/M input + $1.25/M output tokens; an 80 GB GPU instance at $2.50/hr on-demand (~$1,825/month); the benchmarked ~4,800 out-tok/s at SLO from above; one engineer-day ≈ $1,000 loaded.

SCENARIO A — internal tool: 5M input + 1M output tokens/day
  hosted:    5 × $0.25 + 1 × $1.25            = $2.50/day  ≈ $75/month
  self-host: 1 GPU can't be fractional         ≥ $1,825/month
             + ops (upgrades, on-call, evals)  ≥ 2 eng-days/mo ≈ $2,000
             ────────────────────────────────────────────────
             ≈ $3,800/month vs $75  →  hosted wins by ~50×. Not close.
  break-even volume ≈ $3,800 / blended $/M ≈ 4.6 B mixed tokens/month —
  ~60× this workload. Rule of thumb: under ~1B tokens/month, don't even
  run the spreadsheet.

SCENARIO B — consumer feature: 2B input + 400M output tokens/day
  hosted:    2,000 × $0.25 + 400 × $1.25      = $1,000/day ≈ $30K/month
  self-host capacity: 400M out-tok/day ≈ 4,630 tok/s AVERAGE
             traffic peaks ~2.5× average       → 11,600 tok/s peak
             ÷ 4,800 tok/s per GPU at SLO      → 3 GPUs peak
             + N+1 redundancy + input-heavy prefill load → 5 GPUs
             5 × $1,825                        = $9,125/month
             + 0.25 engineer ongoing           ≈ $5,000/month
             ────────────────────────────────────────────────
             ≈ $14K/month vs $30K  →  self-host wins ~2×, IF:
               · utilization stays high (idle GPUs still bill)
               · the open 8B actually matches the hosted model on YOUR evals
               · you wanted the fine-tuned adapter/data-boundary anyway
  and note the counterfactual: reserved/committed hosted pricing and batch
  APIs typically claw back 30–50% — rerun the numbers before deciding.

The honest summary: self-hosting is a volume × utilization × quality-parity bet. Scenario B flips back to hosted if traffic is spiky (utilization drops), if you need the frontier model's quality (no parity), or if eng time is your scarcest resource. Run the arithmetic with your numbers quarterly; the answer changes as prices and open-model quality move.

20 — Diagnosing "inference is slow"

  1. Separate queue time vs prefill vs decode — three different diseases. High TTFT + normal TPOT = queue/prefill (add replicas, chunk prefill, cache prefixes). Normal TTFT + high TPOT = decode pressure (batch too big, KV-bound — quantize KV, shed load).
  2. Check prompt/output length distribution (one 30K-token prompt stalls a batch; enable chunked prefill).
  3. Check GPU memory pressure — KV cache eviction/recompute thrashing shows up as preemption counts and sawtooth throughput.
  4. Confirm p95/p99, not a warm single request — and confirm with bench.py at production-shaped concurrency, not a curl.

Benchmarking gotchas that produce fake numbers

  • Cold-start contamination: first requests pay CUDA-graph capture and an empty prefix cache. Warm up, then measure.
  • Uniform prompts: benchmarking with one fixed prompt makes the prefix cache absorb all prefills — TTFT looks 10× better than production. Use mixed, realistic lengths (or disable the cache and say so).
  • Unbounded max_tokens with EOS-stopping: output-length distribution silently differs between runs; pin max_tokens or report the achieved distribution.
  • Closed-loop-only load: a semaphore client (like bench.py) self-throttles when the server slows — it understates queueing vs real open-loop arrivals. Fine for comparisons; for capacity planning, also test fixed request-rate arrivals.
  • Comparing across changed sampling params (temperature changes length changes batch pressure) or across different tokenizers ("tokens/s" from two tokenizers aren't the same unit).

Takeaways

Default to hosted; self-host on data boundaries, adapters, or big steady volume. A vLLM deployment is ~8 flags, each mapping to an internals concept — max-model-len and KV dtype set concurrency, prefix cache sets TTFT, chunked prefill protects TPOT. Benchmark with a streaming client at swept concurrency, report throughput at your SLO, change one factor per run, and re-run the hosted-vs-self-host arithmetic with your own measured tok/s — never someone else's marketing number.

21 — A production serving setup

  • API layer (FastAPI) handles auth, rate limits, request validation, streaming tokens to clients via SSE.
  • Inference server (vLLM) on GPU nodes behind a load balancer; prefix-aware routing to maximize cache hits.
  • Autoscale on queue depth or KV-cache utilization, not CPU.
  • Structured output via JSON-schema constrained decoding; timeouts and max-token caps.
  • Log prompts, outputs, latency and user feedback to Postgres for evals and future fine-tuning data.

This maps neatly onto your ad-serving instincts: tail latency, caching, admission control, and per-request cost.

22 — Recap

Chat is sync and short; agents can run for minutes. Your serving design must handle both.

The mini-scenario that motivates everything here: your coding agent works beautifully in the demo — one user, one request, a websocket held open for four minutes. Then you launch. A deploy restarts the pods mid-run and thirty users' agents vanish silently. A burst of traffic hits the provider rate limit and every request — including the ones already 3 minutes into their run — starts failing on step 9 of 10. Nothing here is an LLM problem; it's a distributed-systems problem you inherited the moment a "request" stopped fitting inside an HTTP timeout.

Short / interactive

Synchronous request → stream the response. Keep tool calls fast; enforce a per-request timeout + step cap.

Long-running jobs

Don't hold an HTTP connection for a 5-minute agent. Enqueue the job → async workers run the loop → client polls / gets a webhook / streams via SSE. Persist checkpoints so a crashed job resumes (LangGraph/Temporal-style durability).

Scaling the fleet

Agent workers are mostly I/O-bound (waiting on the LLM). Scale horizontally; the real ceiling is usually your LLM provider rate limits / quota, not CPU. Add a quota limiter + queue.

State & sessions

Externalize state (Redis/Postgres) so any worker can handle any turn. Keep conversation/session memory out of process memory.

23 — The async job architecture, in code

The shape is always the same: an API that accepts and returns immediately, a queue, workers that run the agent loop and checkpoint after every step, and a results channel back to the client. Here it is with Redis as the queue and Postgres as the checkpoint store — swap in SQS/Celery/Temporal without changing the shape.

jobs_api.py — accept fast, run elsewherepython
import json, uuid, redis.asyncio as aioredis
from fastapi import FastAPI, HTTPException

app = FastAPI()
rds = aioredis.from_url("redis://queue:6379")

@app.post("/v1/agent/jobs", status_code=202)
async def submit(req: AgentRequest):
    job_id = f"job_{uuid.uuid4().hex[:12]}"
await db.execute(                       # source of truth: Postgres row
"""INSERT INTO agent_jobs (id, tenant, status, input, step, created_at)
           VALUES ($1, $2, 'queued', $3, 0, now())""",
        job_id, req.tenant, json.dumps(req.model_dump()))
    await rds.lpush("agent:queue", job_id)  # queue carries only the ID —
return {"job_id": job_id,               # payloads live in the DB
"status_url": f"/v1/agent/jobs/{job_id}",
            "stream_url": f"/v1/agent/jobs/{job_id}/events"}

@app.get("/v1/agent/jobs/{job_id}")
async def status(job_id: str):
    row = await db.fetchrow(
        "SELECT status, step, result, error FROM agent_jobs WHERE id=$1", job_id)
    if not row: raise HTTPException(404)
    return dict(row)                        # queued|running|done|failed + step
worker.py — checkpoint every step; resume from the last onepython
import json, asyncio, socket

WORKER_ID = socket.gethostname()
MAX_STEPS, LEASE_S = 15, 120 # lease > slowest single step
async def worker_loop():
    while True:
        _, job_id = await rds.brpop("agent:queue", timeout=5) or (None, None)
        if job_id: await run_job(job_id.decode())

async def run_job(job_id: str):
    # claim with a lease so a dead worker's job gets re-queued, and a
# slow-but-alive worker isn't double-run (heartbeat extends the lease)
    claimed = await db.fetchrow(
        """UPDATE agent_jobs SET status='running', worker=$2,
                  lease_until=now() + interval '120 seconds'
           WHERE id=$1 AND (status='queued' OR
                 (status='running' AND lease_until < now()))
           RETURNING input, step""", job_id, WORKER_ID)
    if not claimed: return # someone else has it
# ---- RESUME: rebuild agent state from the last checkpoint ----
    ckpt = await db.fetchrow(
        """SELECT state FROM agent_checkpoints
           WHERE job_id=$1 ORDER BY step DESC LIMIT 1""", job_id)
    state = AgentState.from_json(ckpt["state"]) if ckpt \
            else AgentState.initial(json.loads(claimed["input"]))

    try:
        while not state.done and state.step < MAX_STEPS:
            state = await agent_step(state)          # ONE llm call + tools
async with db.transaction():             # atomic: step + heartbeat
await db.execute(
                    """INSERT INTO agent_checkpoints (job_id, step, state)
                       VALUES ($1, $2, $3)""",       # append-only = audit trail
                    job_id, state.step, state.to_json())
                await db.execute(
                    """UPDATE agent_jobs SET step=$2,
                              lease_until=now() + interval '120 seconds'
                       WHERE id=$1""", job_id, state.step)
            await publish_event(job_id, state.last_event)  # feeds SSE (below)
        final = "done" if state.done else "failed" # step cap exhausted
await db.execute(
            "UPDATE agent_jobs SET status=$2, result=$3 WHERE id=$1",
            job_id, final, state.result_json())
    except Exception as e:                   # crash → job re-queued by lease
await db.execute(                    # expiry; resume picks up at the
"UPDATE agent_jobs SET status='queued', error=$2 WHERE id=$1",
            job_id, repr(e))                 # last checkpoint, not step 0
await rds.lpush("agent:queue", job_id)

# CRITICAL: agent_step must be idempotent-ish. A crash AFTER a tool call
# but BEFORE the checkpoint means the tool may run twice on resume. Reads
# are fine; writes (send email, create ticket) need an idempotency key:
#   tool_call_id = f"{job_id}:{step}:{tool_name}"  → dedupe at the tool layer.

The two lines that earn their keep in production: the lease (a worker OOM-killed mid-run doesn't strand the job; a competing worker re-claims it after 120s) and the append-only checkpoint table (resume-on-crash and a free step-by-step audit log for debugging "what did the agent do?"). This is exactly what Temporal or a LangGraph checkpointer gives you packaged; build the 60-line version to understand it, adopt the engine when your workflows outgrow it.

24 — Streaming progress to the client: SSE

Polling wastes requests and feels dead; websockets are overkill for one-way progress. Server-Sent Events are plain HTTP, survive proxies, and auto-reconnect in the browser with a Last-Event-ID header — which pairs perfectly with the checkpoint log you already have.

sse.py — resumable event stream over the checkpoint logpython
from fastapi import Request
from fastapi.responses import StreamingResponse

@app.get("/v1/agent/jobs/{job_id}/events")
async def events(job_id: str, request: Request):
    last_id = int(request.headers.get("last-event-id", 0))  # reconnect support
async def gen():
        # 1. replay history the client missed (from checkpoints, not memory)
        rows = await db.fetch(
            """SELECT step, state->>'last_event' AS ev FROM agent_checkpoints
               WHERE job_id=$1 AND step > $2 ORDER BY step""", job_id, last_id)
        for r in rows:
            yield f"id: {r['step']}\nevent: step\ndata: {r['ev']}\n\n"
# 2. then follow live events via pub/sub
async with rds.pubsub() as ps:
            await ps.subscribe(f"events:{job_id}")
            while not await request.is_disconnected():
                msg = await ps.get_message(ignore_subscribe_messages=True,
                                           timeout=15.0)
                if msg:
                    yield f"id: {msg['data'].decode()}\n\n"
else:
                    yield ": keepalive\n\n" # comment frame defeats
# idle-timeout proxies
return StreamingResponse(gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
        # X-Accel-Buffering: nginx will otherwise buffer your "stream"
# into one big flush at the end — the classic SSE gotcha.

25 — The real ceiling: provider quota, and a token bucket for it

Your provider limits you in requests/min and tokens/min. Uncoordinated workers discover the limit by getting 429s — and naive per-worker retries synchronize into stampedes. Put one shared limiter in front of every call, denominated in tokens, because that's the scarcer unit for agent workloads.

token_bucket.py — shared, token-denominated rate limiter (Redis Lua = atomic)python
LUA = """
local key, now = KEYS[1], tonumber(ARGV[1])
local rate, burst, want = tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local b = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(b[1]) or burst
local ts     = tonumber(b[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)   -- refill
if tokens >= want then
  redis.call('HMSET', key, 'tokens', tokens - want, 'ts', now)
  redis.call('EXPIRE', key, 120)
  return -1                                             -- granted
end
return math.ceil((want - tokens) / rate)                -- seconds to wait
"""
class SharedTokenBucket:
    """One bucket across ALL workers. rate/burst in provider tokens/sec."""
def __init__(self, rds, key="llm:tpm", rate=8000.0, burst=480_000):
        self.rds, self.key, self.rate, self.burst = rds, key, rate, burst
        self._script = rds.register_script(LUA)

    async def acquire(self, est_tokens: int, max_wait_s=60):
        import time, random
        waited = 0.0
while True:
            delay = await self._script(
                keys=[self.key],
                args=[time.time(), self.rate, self.burst, est_tokens])
            if int(delay) < 0: return
            sleep = min(int(delay), 5) + random.random()   # jitter: don't
            waited += sleep                                # re-synchronize
if waited > max_wait_s:
                raise QuotaSaturated(f"waited {waited:.0f}s for quota")
            await asyncio.sleep(sleep)

# usage inside agent_step():
#   await bucket.acquire(est_tokens=count_tokens(prompt) + max_tokens)
#   resp = await client.messages.create(...)
# est_tokens can be rough; reconcile with resp.usage and adjust if you
# consistently under-estimate (that's how buckets quietly overshoot TPM).

QuotaSaturated is a feature, not a failure: it's the backpressure signal. Catch it in the worker, put the job back on the queue with a delay, and let queue depth grow — visible, bounded degradation instead of a 429-retry storm that burns quota on failures.

26 — Capacity math: a worked example

Illustrative numbers, but do this arithmetic for your own system — it takes ten minutes and prevents a launch-day incident. Target: 1,200 agent jobs/hour at peak; a job averages 8 LLM steps, ~7,000 input + 400 output tokens per step, provider latency ~6s/step, tool time ~2s/step.

  • Throughput per job: 8 × (6s + 2s) = ~64s of wall-clock, nearly all of it awaiting I/O.
  • Concurrency needed: 1,200 jobs/hr = 0.33 jobs/s × 64s = ~22 jobs in flight (Little's Law). With async workers running ~30 concurrent jobs per process comfortably (I/O-bound), that's one worker pod, two for redundancy. CPU is irrelevant; don't autoscale on it.
  • Provider quota — the real constraint: 1,200 jobs/hr × 8 steps × 7.4k tokens ≈ 71M tokens/hour ≈ 1.18M tokens/min. If your tier allows 400k TPM, you are 3× over: peak-hour jobs will queue for ~2 hours no matter how many pods you add. Options: raise the tier, shrink the prefix (Cost & latency — cached reads often don't count against TPM the same way, check your provider), route steps to a second model/region pool, or shed load.
  • Queue sizing: at 3× over quota for a 1-hour peak, backlog grows at ~0.66 jobs/s → ~2,400 jobs deep. At ~2KB of queue payload each that's trivial for Redis — the problem isn't memory, it's the 2-hour p99 completion time. Decide now what you'll shed or defer.

Autoscaling signals that actually work

Scale workers on queue depth / oldest-job age (KEDA-style), cap the fleet at quota ÷ per-worker token burn, and alert on bucket wait time — that's your leading indicator of saturation. CPU-based autoscaling on I/O-bound agent workers does nothing until it does harm: more pods, same quota, deeper 429s. The bottleneck is tokens/min, so the scaler must be denominated in tokens/min.

Durable execution

For complex long-running multi-step agents, durable workflow engines (Temporal, or LangGraph's checkpointer) let a job survive crashes/deploys and resume mid-flight — critical when a single run spans many tool calls and minutes. The worker above is the minimal homegrown version: once you need sub-workflows, signals ("user replied mid-run"), scheduled retries with backoff policies per activity, or exactly-once semantics across services, buy the engine instead of growing the 60 lines into 6,000.

Serving gotchas

  • The double-fired tool: crash between tool execution and checkpoint → resume re-runs the step → the customer gets two refund emails. Any side-effecting tool needs an idempotency key derived from (job_id, step); this is the single most common durable-agent bug.
  • Graceful shutdown that isn't: deploys SIGTERM your workers mid-step. Trap it, finish the current step, checkpoint, re-queue — and set terminationGracePeriodSeconds longer than your slowest step, or Kubernetes SIGKILLs you anyway.
  • Buffered "streaming": nginx/ALB/CDN default to buffering; your SSE arrives as one lump after 60s. X-Accel-Buffering: no, disable proxy buffering, send keepalive comments.
  • Sticky sessions as state management: pinning a conversation to a pod works until that pod dies. Externalized state + any-worker routing is barely more code and removes the whole failure class.
  • Retry amplification across layers: client retries × API retries × worker retries × SDK retries = one flaky provider minute becomes 16× traffic. Retry in one layer (the worker), make everything else fail fast.
  • One tenant eats the bucket: a single customer's batch job starves interactive traffic. Two buckets — per-tenant and global — and a priority queue (interactive ahead of batch) is the 80/20 fix.

30 — Check yourself

vLLM vs HuggingFace generate?
vLLM adds PagedAttention + continuous batching for 5–20× throughput on concurrent requests. HF generate is fine for single-request notebooks, not prod serving.
What is PagedAttention?
KV cache stored in non-contiguous fixed blocks with a block table, like OS virtual memory. Reduces fragmentation so more concurrent requests fit in GPU RAM.
When use Ollama vs vLLM?
Ollama: laptop dev, demos, Modelfile experiments. vLLM: production K8s GPU pool with autoscale, prefix caching, and OpenAI gateway routing.
Why OpenAI-compatible API?
Point LangChain/LangGraph/OpenAI SDK at vLLM with base_url — zero application code change for self-host migration or hybrid routing.
Quantization trade-offs?
AWQ/GPTQ 4-bit: ~4× memory savings, ~1–3% quality drop on tasks. Benchmark on your RAG/agent eval before prod.
GPU for Llama-3-8B?
1× A10/L4 24GB FP16; or 1× T4 16GB with AWQ. Reserve headroom for KV cache at target concurrent users.
Tensor parallel when?
When single GPU VRAM insufficient for model weights + KV — e.g. 70B AWQ on 2× A100 with tensor-parallel-size 2.
Prefix caching for RAG?
vLLM reuses KV blocks for identical prompt prefixes. Shared system prompt + tool definitions across users saves compute on every request.
When still use OpenAI cloud?
Frontier reasoning, zero ops, burst beyond GPU capacity. Hybrid router sends easy queries to local 8B, hard to GPT-4o.
Embed serving stack?
Text Embeddings Inference (TEI) for BGE/E5 batch GPU — not vLLM. See Choosing an embedding model.
Autoscale vLLM on K8s?
HPA on custom metric queue_depth or tokens/sec backlog; min replicas >0 to avoid cold start; GPU node pool separate from CPU.
SDE3: private LLM platform?
vLLM on K8s GPU pool; model registry (Llama/Mistral/Qwen versions); OpenAI-compatible gateway with auth; quant pipeline AWQ; A/B model versions; cost per token chargeback; fallback to cloud API; LangSmith tracing; prefix cache for RAG system prompts.
Why does 4-bit weight-only quantization speed up decode when the matmul still runs in fp16?
Decode is bound by reading weights from HBM; 4-bit cuts bytes ~4×, dequantization in registers is cheap.
Why does continuous batching beat static batching?
Sequences end at different times; static batches idle finished slots until the longest finishes. Iteration-level scheduling refills slots every step.
What problem does PagedAttention solve?
KV-cache fragmentation and over-reservation; paging lets memory be allocated on demand and shared, raising concurrency.
Why multiply the distillation KL term by T²?
Softening by T scales its gradients by 1/T²; multiplying keeps them comparable to the hard-label term.
Does speculative decoding change the output distribution?
No; the accept/reject rule preserves the target model's distribution exactly.
TTFT is fine but tokens stream slowly under load.
Decode is bandwidth/KV-bound: quantize weights and KV, enable chunked prefill, cap batch size for TPOT SLO, or add replicas/tensor parallelism.
