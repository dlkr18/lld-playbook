Vector search & databases // Knowledge & RAG

Exact and approximate nearest neighbours, HNSW and IVF, and choosing a vector database.

39 min read3 diagrams

01 — At a glance

Specialized stores for approximate nearest-neighbor (ANN) search over high-dimensional embeddings. This overview covers index algorithms (HNSW, IVF), metadata pre-filtering, hybrid BM25+vector retrieval, and how to choose between Pinecone, pgvector, Weaviate, and Chroma for your RAG stack.

End-to-end retrieval: chunk documents, embed with the same model at ingest and query time, upsert vectors + metadata into an ANN index (HNSW/IVF), apply metadata pre-filters, optionally fuse BM25 + vector scores, rerank, then pass top chunks to the LLM. Typical p99 query latency: 15–40 ms at 1–10M vectors with tuned ef_search.

Quick reference

03 — What & Why

A vector database stores dense embedding vectors and answers “which vectors are closest to this query vector?” in sub-linear time via approximate indexes. It is the retrieval layer in most The RAG pipeline systems — not a replacement for Postgres (transactions, joins) or Elasticsearch (full-text analytics), but the right tool for semantic similarity at scale.

Functional requirements

  • Upsert vectors with stable IDs, optional metadata JSON, and namespace/collection isolation
  • Query by vector (and sometimes by raw text if the DB embeds server-side)
  • Filter on metadata before or during ANN search (tenant, ACL, date range, doc type)
  • Delete / update by ID; re-index after embedding model change
  • Hybrid keyword + vector fusion when exact token matches matter (SKUs, names, error codes)

Non-functional requirements

  • Latency: p99 query < 50 ms for top-k=20 at millions of vectors (with HNSW + warm index)
  • Recall: ANN recall@10 ≥ 0.90 vs brute-force gold (tune ef_search / nprobe)
  • Freshness: near-real-time upsert for doc updates; full re-embed on model swap
  • Cost: RAM for HNSW graphs dominates; disk-backed IVF cheaper at 100M+ scale
  • Multi-tenancy: namespaces, partition keys, or row-level metadata filters
Prerequisite: vectors only work if you understand Embeddings — same model, same dimension, cosine vs dot-product metric must match training.

05 — API / Interface Surface

Most vector DBs expose a similar REST/gRPC/SDK contract. Examples below are representative patterns (Pinecone / Weaviate / pgvector / Chroma all map to this shape).

Upsert (ingest)

POST /vectors/upsert
{
  "namespace": "tenant_acme_v2",
  "vectors": [
    {
      "id": "doc-42-chunk-3",
      "values": [0.012, -0.034, ...],   // dim=1536
      "metadata": {
        "source": "handbook.pdf",
        "page": 12,
        "tenant_id": "acme",
        "doc_type": "policy"
      }
    }
  ]
}
# Batch 100-500 vectors per request; backoff on 429

Query (retrieve)

POST /vectors/query
{
  "namespace": "tenant_acme_v2",
  "vector": query_embedding,          // from same embed model
  "top_k": 20,
  "include_metadata": true,
  "filter": {
    "tenant_id": {"$eq": "acme"},
    "doc_type": {"$in": ["policy", "faq"]}
  }
}
# Returns ranked hits: id, score, metadata

pgvector (SQL-native)

SELECT id, content, metadata,
       embedding <=> $1::vector AS distance
FROM document_chunks
WHERE tenant_id = 'acme'
  AND doc_type IN ('policy', 'faq')
ORDER BY embedding <=> $1::vector
LIMIT 20;
-- Index: CREATE INDEX ON document_chunks
--   USING hnsw (embedding vector_cosine_ops);
Contract to nail in interviews: idempotent upsert by chunk ID, filter applied before returning top-k to the LLM, and scores exposed for reranker / logging. Never silently change embedding model without a new namespace.

The vector DB is not the system of record for documents — keep source text in object storage or Postgres; store only embeddings + pointers (chunk_id, source URI) in the vector index.

08 — HNSW (Hierarchical Navigable Small World)

HNSW is the default ANN algorithm in Pinecone, pgvector, Weaviate, Qdrant, and Milvus. It builds a multi-layer graph: sparse long-range links on top layers for fast coarse navigation, dense links on layer 0 for fine-grained neighbors.

ParameterMeaningTypical starting point
MMax edges per node (build-time)16–32 (higher = better recall, more RAM)
ef_constructionBuild-time search width128–256 (index build quality)
ef_searchQuery-time beam width64–200 (tune for recall@k vs latency)
  • Query flow: enter at top layer → greedy walk to local minimum → drop to next layer → repeat until layer 0 → expand neighbor list → return top-k.
  • Complexity: roughly O(log N) per query in practice; build is O(N log N) with high constant factor.
  • When to pick: default for production RAG up to tens of millions of vectors when RAM budget exists.

HNSW search: long jumps on sparse upper layers, then dense neighbor expansion on layer 0. Increase ef_search when eval shows recall gaps on tail queries.

09 — IVF / IVFFlat

IVF (Inverted File Index) partitions the vector space into nlist clusters (k-means centroids at index build). At query time, only the nprobe closest centroids are searched — dramatically fewer distance computations than flat scan.

VariantHow it worksTrade-off
IVFFlatIVF buckets + exact scan within each probed bucketpgvector default before HNSW; lower RAM than HNSW
IVF-PQProduct quantization compresses vectors in bucketsVery large scale (100M+); recall loss from compression
IVF + HNSWHNSW on bucket centroids or per-bucket graphsHybrid used in Milvus/Faiss for billion-scale

Build requirements

  • Train centroids on a representative sample of your embedding distribution — not random noise.
  • Rule of thumb: nlist = sqrt(N) for N vectors; nprobe start at 8–32 and increase until recall target met.
  • After major corpus drift (new product line, new language), retrain IVF centroids.
HNSW vs IVF interview answer: HNSW = higher RAM, simpler ops, best recall/latency for most RAG sizes. IVF = better when N is huge and RAM is constrained, but needs careful centroid training and nprobe tuning.

10 — Metadata Filtering

Production RAG rarely does pure global ANN — you filter by tenant, ACL, date, product, or document type before returning chunks to the LLM.

Partition by namespaceSeparate index per tenant/model versionStrong isolation; more ops overhead
# Pinecone-style filter DSL
filter = {
    "tenant_id": {"$eq": "acme"},
    "created_at": {"$gte": "2025-01-01"},
    "allowed_roles": {"$in": ["employee", "manager"]}

# pgvector: push filter into SQL WHERE (preferred)

Interview tip: post-filter with small k is a common bug — you retrieve 20 globally relevant chunks, filter to 2, miss the true answer. Fix: pre-filter, namespace per tenant, or retrieve k′ = 5×k then filter.

11 — Hybrid Search Overview

Hybrid search fuses dense vector similarity with sparse lexical matching (BM25, SPLADE, or inverted indexes). Use when users query exact IDs, error codes, or rare tokens that embeddings miss.

StageWhat happens
1. Dual retrievalBM25 top-50 + vector top-50 in parallel
2. FusionRRF: score = Σ 1/(k + rank_i) or linear: α·dense + (1-α)·sparse
3. RerankCross-encoder on top 20 → final 5 to LLM (+30–80 ms)
  • Weaviate has native hybrid (BM25 + vector) in one GraphQL query.
  • pgvector + Postgres tsvector / ParadeDB / external ES for sparse leg.
  • Pinecone sparse-dense vectors (if enabled) or dual-index in application layer.
See also: The RAG pipeline for where hybrid fits in the full pipeline, and dedicated Hybrid search & query understanding when published.

The full explanation

13 — The question

Once text is embedded, retrieval is a geometry problem: given a query vector, find the stored vectors nearest to it. With 30,000 vectors you just compare against all of them. With 10 million, comparing against all of them takes over a second per query, and the system needs answers in tens of milliseconds. Vector search is the set of index structures that make that possible by looking at a tiny fraction of the data, and vector databases are the systems that wrap those indexes with storage, filtering, updates and scaling.

Interviewers ask:

  1. How does HNSW (or IVF) work, and what do its parameters trade?
  2. Why is it approximate, and how do you measure and tune how approximate?
  3. How do metadata filters interact with vector search, and why do small tenants get bad results?
  4. How much memory does a given collection need, and how would you choose a vector database?

The running example: the course's support assistant has become a product sold to 2,000 business customers (tenants), each with its own help centre. The index holds 10 million chunks of 768-dimension embeddings. Every query must search only the asking tenant's chunks, return the top 10, and finish within 50 ms at the 99th percentile, at 200 queries per second at peak. The smallest tenants have about 5,000 chunks, 0.05% of the index.

14 — Step 1: what exact search costs

Exact search computes the query's similarity with every stored vector and keeps the best \(k\). For our index that is \(10^7 \times 768 = 7.68\) billion multiply-adds per query, reading \(10^7 \times 768 \times 4\) bytes \(= 30.7\) GB of 32-bit floats.

Search over vectors is mostly limited by how fast memory can be read, not by arithmetic. At an order-of-magnitude 20 GB/s of memory bandwidth per server, one scan takes about 1.5 seconds. At 200 queries per second we would need the equivalent of 300 servers scanning in parallel. Exact search is out.

The same arithmetic tells you when exact search is fine: 100,000 vectors of 768 dimensions is 307 MB, about 15 ms to scan. Below roughly that size, a flat index (or a plain matrix multiply) is simpler, has perfect recall, and needs no tuning. Many RAG prototypes, including the single-tenant version of this assistant at 30,000 chunks, never need an ANN index.

15 — Step 2: trading a little accuracy for a lot of speed

Approximate nearest neighbour indexes give up the guarantee of finding the true top \(k\) in exchange for examining a few percent of the vectors, or fewer. Their accuracy is measured against exact search:

\[ \text{recall@}k = \frac{|\text{ANN top } k \ \cap\ \text{exact top } k|}{k} \]

A recall@10 of 0.95 means that, on average, 9.5 of the 10 true nearest neighbours were returned. The missing half-neighbour is usually replaced by something almost as close, which matters much less to a RAG system than it sounds: the embedding model's own errors are larger than this. Every ANN index has a knob that moves along a recall-versus-latency curve, and choosing a point on that curve is the main tuning job.

Note this is a different recall from the retrieval recall in choosing an embedding model. That one asks "did we find the relevant chunk?"; this one asks "did the index find what exact search would have found?". An index at 0.95 recall in front of a model at 0.80 retrieval recall gives a system at about 0.76 to 0.80.

16 — Step 3: IVF, scan only the nearby clusters

The inverted file index partitions the space. At build time, run k-means on the vectors to find nlist centroids, and put each vector in the list of its nearest centroid. At query time, compare the query with all centroids, pick the nprobe nearest, and scan only the vectors in those lists exactly.

For our index, a common starting point is nlist of a few times \(\sqrt{N}\); with nlist = 16,384 clusters (about 610 vectors each) and nprobe = 32, a query computes 16,384 centroid similarities plus about \(32/16{,}384 \times 10^7 \approx 19{,}500\) vector similarities: roughly 0.36% of the work of exact search.

Why is it approximate? A true neighbour can sit just across a cluster boundary, in a list we did not probe. Raising nprobe fixes that at a linear cost. On a synthetic test (10,000 unit vectors in 64 dimensions, 100 topics, 64 clusters; the code is at the end):

IVF's strengths are simplicity, low memory overhead (one list ID per vector) and easy partitioning across machines. Its weaknesses: it needs representative data to train the centroids, and as data drifts after the build, clusters become unbalanced and recall drops until you retrain.

17 — Step 4: product quantization, a vector in a few bytes

IVF reduces how many vectors you touch; product quantization reduces how many bytes each one costs. Split each 768-dimension vector into \(m = 96\) sub-vectors of 8 dimensions. For each of the 96 positions, run k-means with 256 centroids on that slice of the data. Now store each vector as 96 one-byte centroid IDs: 96 bytes instead of 3,072, a 32-times reduction. Our 10 million vectors drop from 30.7 GB to 0.96 GB.

Searching compressed vectors is cheap too. For a query, compute its similarity with all 256 centroids in each of the 96 positions once: a 96 × 256 lookup table. A stored vector's approximate score is then 96 table lookups and additions, with no multiplication over the full dimensions.

The cost is accuracy: each vector is replaced by its nearest point on a coarse grid. In the synthetic test, a 16-byte PQ code for 64-dimension vectors (16 times smaller) gives recall@10 of 0.679 on its own. Fetching the top 100 by PQ score and rescoring those with the full vectors lifts it to 0.998. That is the standard pattern, the same as binary quantization in choosing an embedding model: compressed codes find a shortlist, full vectors order it. In practice IVF and PQ are combined (IVF-PQ): probe a few clusters, score their PQ codes, rescore the best.

18 — Step 5: HNSW, walking a graph toward the query

Graph indexes take a different approach: connect each vector to its near neighbours, then search by walking. Start at some node, look at its neighbours, move to whichever is closest to the query, repeat until no neighbour is closer. Because neighbours of neighbours tend to be closer still, the walk converges on the query's region after visiting a small number of nodes.

A plain greedy walk gets stuck in local optima, so the search keeps a beam: a list of the best ef nodes found so far, always expanding the closest unexplored one, stopping when the closest unexplored candidate is worse than the worst node in the beam. A wider beam explores more and misses less.

HNSW adds two ideas:

  • Layers. Every node is in the bottom layer; a random, exponentially shrinking subset is also in higher layers (roughly 1 in \(M\) nodes per layer up). The search starts at the sparse top layer, where links are long and a few hops cross the whole space, then descends layer by layer to the dense bottom, where links are short. It is the same idea as a skip list, and it makes the number of hops grow roughly logarithmically with \(N\).
  • Diverse neighbours. When linking a new node, it keeps neighbours that point in different directions rather than the \(M\) absolutely nearest (which tend to cluster on one side). That keeps the graph navigable across cluster boundaries.

The parameters:

ParameterTypicalRaising it
M (links per node; the bottom layer usually gets \(2M\))16 to 32Better recall and robustness; more memory and slower builds.
efConstruction (beam while inserting)100 to 400Better graph quality; slower builds. Set once.
efSearch (beam while querying, at least \(k\))40 to 400Higher recall, higher latency. The per-query knob you tune.

On the synthetic set, a single-layer version (each node linked to its 16 nearest neighbours, a fixed entry point, no hierarchy) already shows the curve:

Compare with IVF: to pass 0.92 recall, IVF scanned 24% of the vectors and the graph about 6%. That gap is why HNSW became the default in most vector databases: it reaches high recall with very few distance computations. Its costs are memory (the links, plus the full vectors, which it needs in RAM for its random-access walk) and slow, memory-hungry builds.

19 — Step 6: sizing the index

For our 10 million × 768 collection with HNSW at \(M = 16\):

  • Vectors: 30.7 GB in float32, 15.4 GB in float16.
  • Bottom-layer links: \(10^7 \times 2M \times 4\) bytes \(= 1.28\) GB; upper layers add a few percent.
  • Metadata (tenant ID, document ID, language) and the ID mapping: a few hundred MB.

So roughly 17 GB with float16 vectors, or 33 GB with float32, per full copy. With IVF-PQ the same collection fits in about 1 GB of codes plus the centroids, with full vectors on SSD for rescoring: far cheaper, somewhat lower recall at a given latency, and more tuning.

Throughput is a separate question from memory. One HNSW query at a recall of about 0.95 typically computes a few thousand distances; a server core handles hundreds to about a thousand such queries per second at this size (order of magnitude; measure your own). Our 200 QPS fits on one well-provisioned node; replicas are for availability and growth. When one copy no longer fits in a machine's RAM, shard: split the vectors across nodes, send each query to every shard, take each shard's top \(k\) and merge. Sharding adds a network hop and makes latency the slowest shard's latency.

20 — Step 7: metadata filters and the small-tenant problem

Every query in our product carries a filter: tenant_id = 'acme'. How the filter meets the index decides whether small tenants get answers at all.

Post-filtering searches the whole index, takes the top 100, then drops chunks from other tenants. For a tenant with 0.05% of the data, the expected number of their chunks in a random top 100 is \(100 \times 0.0005 = 0.05\). Their nearest neighbours are spread among everyone else's; the filter throws almost everything away and the tenant gets zero or one result. To expect 10 survivors you would need a top-20,000 search, which destroys latency.

Pre-filtering first finds every chunk passing the filter, then searches only those. For this tenant that is 5,000 vectors, and an exact scan of 5,000 × 768 is under a millisecond. Pre-filtering is ideal for selective filters and terrible for broad ones (a filter matching 60% of the index turns into a near-full exact scan).

Filtering inside the walk (what most HNSW-based databases do) traverses the graph normally but only admits passing nodes into the results. It works when many nodes pass. When few pass, the walk must wander through huge numbers of non-matching nodes, and the graph may not connect the passing ones at all, so recall collapses. Good engines detect low selectivity and switch to pre-filtering with exact search automatically; check that yours does.

When the filter is always the same field (a tenant), the structural answer is to partition: one index or namespace per tenant, or per group of small tenants. Every query then searches a small, homogeneous index, small tenants get exact search, deleting a tenant is dropping an index, and noisy neighbours cannot crowd each other out.

Test with your smallest tenant. Aggregate recall dominated by large tenants can look excellent while small tenants receive empty or irrelevant results. Measure recall per filter value, especially the most selective ones.

21 — Step 8: writes, deletes and freshness

Indexes are easiest to build in one batch; production data changes continuously.

  • Inserts. HNSW supports incremental inserts (each new node runs a search to find its neighbours), at a cost of milliseconds per insert and some lock contention. IVF inserts are cheap (append to the nearest list) but the centroids were trained on old data, so lists grow unbalanced.
  • Deletes. Removing a node from a graph would break the paths through it, so most engines mark it with a tombstone and filter it from results. Tombstones still cost memory and still get visited. After heavy churn (say 20% deleted), recall and latency degrade until a compaction or rebuild.
  • Updates are a delete plus an insert. Editing a help article means removing its old chunks and adding new ones; see document ingestion for doing that incrementally.

Many databases borrow the log-structured design: new writes go to a small, fresh segment (searched exactly or with a quick index), segments are periodically merged into larger optimised ones, and a query searches all segments and merges the results. That is why a just-written vector is usually searchable within a second or so, but not necessarily instantly; read the engine's consistency guarantees before promising "upload and ask immediately".

22 — Step 9: choosing where the vectors live

The index algorithms above are nearly universal; the systems differ in everything around them. Four broad options:

  • A library in your process (FAISS, hnswlib). Fastest and free, but you build persistence, filtering, updates and replication yourself. Right for offline jobs, research, or a read-only index rebuilt nightly.
  • A vector index inside your existing database: pgvector in Postgres. Vectors sit next to the rows they describe, filters are SQL, transactions and backups come free. Right up to tens of millions of vectors for most teams, especially when you already run Postgres.
  • A managed vector database: Pinecone and others. No operations, namespaces for tenants, scaling handled for you; you pay per usage and accept vendor limits.
  • A self-hosted vector database: Weaviate, Qdrant, Milvus, or Chroma for local development. Native hybrid search, filtering and multi-tenancy, with the operations on you.

The questions that actually decide it: Do you already run Postgres? How many vectors in three years? How selective are your filters, and does the engine handle selective filters well? Do you need keyword search in the same engine? Can data leave your network? What is the update rate? Benchmark the finalists on your own vectors and filters at your target recall; published benchmarks use filter-free workloads that may not resemble yours.

23 — A worked plan for the multi-tenant assistant

  1. Partition by tenant. Large tenants (over about 100,000 chunks) get their own HNSW index; small tenants share partitions but are always searched with a pre-filter, which turns into exact search over a few thousand vectors.
  2. Index settings. HNSW, \(M = 16\), efConstruction = 200, cosine on normalised float16 vectors. Total memory about 17 GB per copy, so two replicas on 32 to 64 GB machines.
  3. Tune efSearch on a sample of 500 real queries per large tenant against exact search: pick the smallest value reaching recall@10 of 0.95. Record p50 and p99 latency at 200 QPS.
  4. Freshness. Incremental inserts as articles change; nightly compaction where tombstones exceed 10%.
  5. Guardrails. Per-tenant recall checks in the nightly evaluation, an alert on empty-result rates by tenant, and the embedding model version stored with every index.

N, d, k = 10_000, 64, 10
centers = rng.normal(size=(100, d))                                   # 100 topics
X = centers[rng.integers(0, 100, N)] + 1.5 * rng.normal(size=(N, d))
X = (X / np.linalg.norm(X, axis=1, keepdims=True)).astype(np.float32)
Q = X[rng.integers(0, N, 100)] + 0.05 * rng.normal(size=(100, d)).astype(np.float32)
Q = (Q / np.linalg.norm(Q, axis=1, keepdims=True)).astype(np.float32)
truth = np.argsort(-(Q @ X.T), axis=1)[:, :k]                         # exact top 10
recall = lambda found: np.mean([len(set(f) & set(t)) / k for f, t in zip(found, truth)])

# --- IVF: cluster once, then scan only the nprobe nearest clusters ---
nlist = 64
km = KMeans(nlist, n_init=1, random_state=0).fit(X)
lists = [np.where(km.labels_ == c)[0] for c in range(nlist)]
for nprobe in (1, 4, 8, 16):
    found, scanned = [], 0
for q in Q:
        ids = np.concatenate([lists[c] for c in np.argsort(-(km.cluster_centers_ @ q))[:nprobe]])
        scanned += len(ids)
        found.append(ids[np.argsort(-(X[ids] @ q))[:k]])
    print(f"IVF   nprobe={nprobe:2d}  recall@10={recall(found):.3f}  scanned {scanned / len(Q) / N:.1%}")

# --- graph search: each node links to its M nearest; best-first walk with a beam of ef ---
M = 16
S = X @ X.T
np.fill_diagonal(S, -np.inf)
nbrs = np.argpartition(-S, M, axis=1)[:, :M]
del S

def graph_search(q, ef, entry=0):
    seen, evals = {entry}, 1
    s0 = float(X[entry] @ q)
    frontier = [(-s0, entry)]            # max-heap on similarity (negated)
    best = [(s0, entry)]                 # min-heap holding the ef best so far
while frontier:
        neg_s, node = heapq.heappop(frontier)
        if len(best) >= ef and -neg_s < best[0][0]:
            break # closest unexplored node is worse than our worst kept
for n in nbrs[node]:
            if n in seen:
                continue
            seen.add(n); evals += 1
            s = float(X[n] @ q)
            if len(best) < ef or s > best[0][0]:
                heapq.heappush(frontier, (-s, n)); heapq.heappush(best, (s, n))
                if len(best) > ef:
                    heapq.heappop(best)
    return [i for _, i in sorted(best, reverse=True)[:k]], evals

for ef in (10, 20, 40, 80):
    res = [graph_search(q, ef) for q in Q]
    ev = np.mean([e for _, e in res])
    print(f"graph ef={ef:3d}  recall@10={recall([r for r, _ in res]):.3f}  computed {ev:.0f} distances ({ev / N:.1%})")

# --- PQ: 16 sub-vectors of 4 dims, 256 centroids each -> 16 bytes instead of 256 ---
m, sub = 16, d // 16
books, codes = [], np.zeros((N, m), np.uint8)
for j in range(m):
    kmj = KMeans(256, n_init=1, random_state=0).fit(X[:, j * sub:(j + 1) * sub])
    books.append(kmj.cluster_centers_); codes[:, j] = kmj.labels_
pq_found, pq_rescored = [], []
for q in Q:
    table = np.stack([books[j] @ q[j * sub:(j + 1) * sub] for j in range(m)])   # 16 x 256 lookups
    approx = table[np.arange(m), codes].sum(1)                                    # score every vector
    short = np.argsort(-approx)[:100]
    pq_found.append(short[:k]); pq_rescored.append(short[np.argsort(-(X[short] @ q))[:k]])
print(f"PQ 16 bytes/vector  recall@10={recall(pq_found):.3f}  with exact rescoring of 100: {recall(pq_rescored):.3f}")

25 — Vector databases: search by meaning at scale

Once everything is a vector, you need to store millions of them and instantly find the nearest to a query. That's a vector database.

26 — What it does

  • Upsert records: { id, vector, payload } — the vector + metadata (the original text, source, tags, dates).
  • Search: give it a query vector + top-K (how many neighbors) + optional filters on the payload ("only English, only this user").
  • Returns the nearest records with similarity scores — in milliseconds, even over millions of vectors.

Why milliseconds is remarkable: brute-force ("flat") search over 10M vectors of 1024 dims is 10M dot products of 1024 mults each ≈ 10 billion multiply-adds per query — tens to hundreds of ms of pure compute, per query, before you've served the second user. The whole field of vector databases is about not doing that.

TermMeaning
Collection / indexA named set of vectors (like a table).
Point / recordOne row: id + vector + payload.
Metadata filterRestrict search by payload fields before/while matching.
Hybrid searchCombine vector similarity with keyword (BM25) search.
Recall@kFraction of the true k nearest neighbors your (approximate) search actually returned. The honesty metric of every ANN index.

27 — HNSW: the index that runs the industry

Exact nearest-neighbor over millions of vectors is too slow, so vector DBs use Approximate Nearest Neighbor (ANN) indexes that trade a sliver of recall for orders-of-magnitude speed. The dominant one is HNSW — Hierarchical Navigable Small World graphs. Here's the actual mechanism, not the hand-wave:

The structure. Every vector becomes a node in a graph, connected to its ~M nearest neighbors ("small world" links). On top of this base layer, HNSW stacks sparser layers: each node is promoted to layer 1 with probability ~1/e, to layer 2 with ~1/e², and so on. The top layer has a handful of nodes with long-range links — an express-lane network. Think of it as: top layer = flights between continents, middle = highways, bottom layer = streets to the exact door.

layer 2:   A ───────────────────── F              (few nodes, long hops)
                │                    │
layer 1:   A ──── C ─────── E ───── F ── H        (more nodes)
                │      │        │        │
layer 0:  A─B─C─D─E─F─G─H─I─J─K─L─M─N─O─P        (ALL nodes, short links)

query: enter at top, greedy-hop toward target, drop a layer, repeat.
     ≈ O(log N) hops instead of O(N) comparisons.

The search. Start at the top layer's entry point. Greedily hop to whichever neighbor is closest to the query; when no neighbor improves, drop one layer and repeat. At layer 0, switch from single-minded greed to a beam search: keep a candidate list of the best ef nodes seen, keep expanding until the list stops improving, return the top-K. That candidate list is the accuracy dial.

The three knobs and what they actually do:

ParameterWhat it isRaise it →Typical values
MMax links per node (build-time)Better recall & robustness, ~linear growth in index RAM, slower build16–48 (64 for high-dim/high-recall)
ef_constructionBeam width while buildingHigher-quality graph, slower ingestion; one-time cost100–400
ef_searchBeam width while queryingRecall climbs toward ~1.0, latency climbs ~linearly. The per-query speed/accuracy dial50–400; must be ≥ K

Illustrative shape of the trade-off on 1M×768-dim vectors (single node): ef_search=16 → recall@10 ≈ 0.85 at ~0.6 ms; ef_search=64 → ≈ 0.97 at ~1.5 ms; ef_search=256 → ≈ 0.995 at ~5 ms. Recall buys are cheap until ~0.98, then the curve goes vertical — the last 1% of recall can cost as much latency as the first 97%.

Why "approximate" is fine

Missing a true neighbor 3% of the time sounds scary until you remember what's downstream: RAG fetches 20–50 candidates and reranks them anyway. A 97%-recall index behind a reranker is indistinguishable from exact search in end-to-end answer quality — at 50–500× the throughput.

28 — The other two families: IVF and PQ

IVF (inverted file index): cluster all vectors into nlist buckets with k-means (e.g. 4,096 centroids for 10M vectors). At query time, find the nprobe closest centroids and brute-force only their buckets. With nlist=4096, nprobe=32 you scan ~32/4096 ≈ 0.8% of the corpus — a ~128× reduction. Weakness: a true neighbor sitting just across a cluster boundary is invisible unless nprobe is high enough. IVF builds much faster than HNSW and suits batch-rebuilt, memory-tight, or GPU (FAISS) setups; HNSW usually wins on the recall/latency frontier for online serving.

PQ (product quantization) — compression, not search: chop each 1024-dim vector into e.g. 64 sub-vectors of 16 dims; replace each sub-vector with the id of its nearest centroid from a learned 256-entry codebook. Each vector becomes 64 bytes instead of 4,096 — a 64× compression. Distances are approximated via codebook lookup tables. Combined as IVF-PQ (or HNSW+PQ), this is how billion-vector search fits in RAM: 1B×1024-dim float32 = ~4 TB raw, but ~64 GB as 64-byte PQ codes. The catch: quantization error costs recall, so serious systems re-rank PQ candidates against full-precision vectors kept on disk. Cheaper sibling: scalar/binary quantization (float32→int8 = 4×, →1 bit = 32×) with less machinery, now a one-flag option in most engines.

29 — pgvector: the "just use Postgres" option

If your data already lives in Postgres and you're under ~5–20M vectors, pgvector means no new infrastructure, real transactions, joins, and one backup story. Complete working schema:

schema.sql — pgvector table, HNSW index, filtered similarity querysql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    id         bigserial PRIMARY KEY,
    doc_id     text        NOT NULL,
    lang       text        NOT NULL DEFAULT 'en',
    tenant_id  text        NOT NULL,           -- multi-tenant isolation
    content    text        NOT NULL,           -- ALWAYS keep the raw text
    created_at timestamptz NOT NULL DEFAULT now(),
    embedding  vector(1024) NOT NULL           -- dims fixed at table creation
);

-- HNSW index. vector_cosine_ops → use the <=> operator in queries.
CREATE INDEX chunks_embedding_hnsw
    ON chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 200);

-- B-tree for the filter columns (the planner combines them)
CREATE INDEX chunks_tenant_lang ON chunks (tenant_id, lang);

-- Query: top-10 for one tenant. <=> is cosine DISTANCE (0=identical),
-- so ORDER BY ascending and similarity = 1 - distance.
SET hnsw.ef_search = 100;   -- per-session recall/latency dial

SELECT id, doc_id, content, 1 - (embedding <=> $1) AS similarity
FROM   chunks
WHERE  tenant_id = $2 AND lang = 'en'
ORDER  BY embedding <=> $1
LIMIT  10;

The metadata-filter trap

Filters and ANN indexes interact badly, in every engine. The ANN index knows geometry, not your WHERE clause. Two strategies exist: post-filter — fetch top-K by vector, then discard non-matching rows; if your filter matches only 1% of rows, top-10 becomes top-0.1 and you return almost nothing (the classic "search works except for small tenants" bug). Pre-filter / integrated filter — restrict candidates first; exact and fine when the filtered set is small, but degrades toward brute force on mid-size sets. pgvector historically post-filtered (its iterative scans option keeps searching until the LIMIT is honestly filled — turn it on); Qdrant/Weaviate filter inside graph traversal, which handles this well but can still thin the graph until it fragments under very selective filters. Test recall with your real filters, not just without — and if one filter (like tenant_id) is always present and highly selective, consider partitioning or one collection per tenant instead of a filter.

30 — Benchmark it yourself (the only numbers that matter)

Vendor benchmarks use their favorite dataset and their favorite knobs. The method below is ~40 lines and gives you the two numbers that matter — recall@k and latency — on your vectors, your filters:

bench.py — ground truth by brute force, then recall@k vs latency per configpython
import numpy as np, time

def ground_truth(corpus: np.ndarray, queries: np.ndarray, k: int) -> np.ndarray:
    """Exact top-k by brute force. Slow and that's fine: run once, cache it.
    corpus (N,d) and queries (Q,d) must be L2-normalized."""
    sims = queries @ corpus.T                        # (Q, N)
return np.argsort(-sims, axis=1)[:, :k]          # true neighbor ids
def evaluate(search_fn, queries, truth, k=10):
    """search_fn(vec, k) -> list[int]. Returns (mean recall@k, p50 ms, p95 ms)."""
    recalls, lats = [], []
    for q, true_ids in zip(queries, truth):
        t0 = time.perf_counter()
        got = search_fn(q, k)
        lats.append((time.perf_counter() - t0) * 1000)
        recalls.append(len(set(got) & set(true_ids)) / k)
    lats = np.sort(lats)
    return (float(np.mean(recalls)),
            float(lats[len(lats)//2]), float(lats[int(len(lats)*0.95)]))

# --- sweep the accuracy dial and print the trade-off curve ---
truth = ground_truth(corpus, queries, k=10)          # cache this to disk!
for ef in (16, 32, 64, 128, 256):
    client.update_search_params(ef=ef)               # engine-specific call
    r, p50, p95 = evaluate(lambda q, k: client.search(q, k), queries, truth)
    print(f"ef={ef:4d}  recall@10={r:.3f}  p50={p50:.1f}ms  p95={p95:.1f}ms")

Method notes: use ≥1,000 held-out queries (real user queries if you have them — their distribution differs from random corpus vectors); report p95, not mean (ANN latencies are long-tailed); and rerun the whole sweep with your production filters applied — that's where engines diverge most.

32 — Mini-scenario: the invisible small tenant

You run a docs-search product on one shared collection, 8M chunks, tenant_id in the payload. Big tenants are happy. Then a 300-chunk pilot customer reports "search returns nothing." Nothing is down. The cause: their filter matches 300 of 8M vectors (0.004%); the engine fetched top-50 by geometry and post-filtered — and the odds that any of the global top-50 belonged to that tenant were near zero. Recall@10 for them: 0.02. The fixes, in ascending effort: enable integrated/iterative filtering; raise the candidate pool when the filter is selective; or give small tenants their own collections. The lesson is the gotcha box above, paid for in a churned pilot: benchmark with filters on.

  2. Stand up pgvector with the schema above; insert 50K chunks across 10 tenants where one tenant has only 100 rows. Measure recall@10 for that tenant with and without iterative scans (or with exact search as reference). Reproduce the invisible-tenant bug, then fix it.

  4. Apply scalar (int8) quantization in your engine of choice. Measure the storage saved and the recall drop at fixed ef_search; then add full-precision re-ranking of the top-100 and show the recall recovering.
  5. Write down, for your own product: expected vector count in 12 months, always-on filters, and required p95. Use those three numbers to justify one engine from the table — in three sentences.

33 — Vector search: exact and approximate

Exact k-NN compares the query to every vector: O(N·d), fine to ~1M vectors on a GPU, too slow beyond. Approximate nearest neighbor (ANN) trades a little recall for big speed:

  • HNSW: a multi-layer proximity graph; greedy-walk from a sparse top layer down to dense lower layers. Excellent recall/latency, memory-heavy. Tunables: M (links per node), ef_search.
  • IVF: k-means cluster the vectors; search only the nprobe nearest clusters.
  • PQ (product quantization): split vectors into chunks, encode each chunk as a codebook id; compresses 10–50× for huge corpora.

Tools: FAISS (library), pgvector (Postgres extension with HNSW and IVFFlat indexes), Qdrant, Milvus, Weaviate. For many products, pgvector next to your existing Postgres is enough.

36 — Where people get lost

  • Model mismatch: ingest with v1, query with v2 — similarity scores meaningless.
  • Post-filter starvation: top-k globally then filter → 0–2 results; use pre-filter or over-fetch.
  • Chunk too large/small: 4K-token chunks dilute semantics; 50-token chunks lose context.
  • No eval set: tuning ef_search by gut feel; recall cliffs on legal/medical tail queries.
  • Vectors without source text: index stores embedding only; debugging and citations break.
  • Ignoring hybrid: pure vector misses exact product SKUs and error codes users paste verbatim.
  • One namespace for prod + staging: test upserts pollute prod retrieval.
  • "We need a vector database" at 50,000 vectors. Exact search over that is milliseconds. Add an ANN index when measurements say so.
  • Tuning for speed without measuring recall. Every ANN setting trades recall; compute it against exact search on real queries before choosing efSearch or nprobe.
  • Post-filtering with selective filters. A tenant with 0.05% of the data expects 0.05 matches in a top 100. Use pre-filtering, partitions, or an engine that switches strategy by selectivity.
  • Reporting aggregate recall only. Large tenants dominate the average; small or rare filter values are where filtered search breaks.
  • Forgetting that HNSW needs the vectors in RAM. Size memory as vectors plus links plus metadata, per replica; use float16 or PQ with rescoring when it does not fit.
  • Assuming deletes free space. Tombstoned vectors stay until compaction, and heavy churn degrades recall and latency.
  • Trusting published benchmarks. They rarely use your dimension, filters or update rate. Benchmark finalists on your data at your target recall.

38 — Check yourself

How much memory does an HNSW index over 4 million 1,024-dimension float32 vectors with \(M = 32\) need, roughly?
Vectors: \(4 \times 10^6 \times 1{,}024 \times 4 = 16.4\) GB. Bottom-layer links: \(4 \times 10^6 \times 64 \times 4 = 1.02\) GB. Plus metadata and upper layers: about 18 GB per copy. Storing vectors as float16 brings it to about 9.5 GB.
A tenant owns 0.2% of a shared index. With post-filtering on a top-50 search, how many of their chunks do you expect, and what would you do?
\(50 \times 0.002 = 0.1\). Almost always zero. Pre-filter (their chunks are few enough to search exactly), move them into a per-tenant partition or namespace, or use an engine that switches to pre-filtering at low selectivity.
Why is a graph walk with a wider beam (higher efSearch) more accurate, and what does it cost?
The beam keeps more candidate nodes and expands more of them, so the walk is less likely to stop in a local region that is not the true neighbourhood. It costs more distance computations per query, so latency rises roughly in proportion.
Explain in two sentences why PQ codes are paired with rescoring.
PQ replaces each vector with its nearest point on a coarse grid, so approximate scores mis-order close neighbours. The true neighbours are nearly always in the PQ shortlist, so rescoring the top 100 or so with full vectors restores almost exact ordering cheaply.
Your index is 12 million vectors and one replica needs 70 GB of RAM. Your machines have 64 GB. Name three options.
Store vectors as float16 (roughly halves memory); switch to IVF-PQ with full vectors on SSD for rescoring; or shard the index across two machines and merge each shard's top \(k\). Also consider whether a smaller embedding dimension (Matryoshka truncation) loses acceptable recall.
After a month of heavy edits, p99 latency has crept up and recall has dropped, with no config change. What is the likely cause?
Accumulated tombstones and incremental inserts have degraded the graph (or, for IVF, unbalanced the clusters). Compact or rebuild the index, and schedule it based on the deleted fraction.
What is a vector database and how is it different from a regular database?
A vector DB optimizes approximate nearest-neighbor search in high-dimensional space (typically 384–3072 dims). Relational DBs excel at exact matches, joins, and transactions; they degrade on brute-force cosine scan at millions of rows. Vector DBs trade exactness for sub-50ms ANN via HNSW/IVF. Many teams use both: Postgres for users/docs, vector index for semantic retrieval.
Explain HNSW in 60 seconds for a whiteboard.
Build a hierarchy of proximity graphs: top layers are sparse with long jumps; bottom layer connects all points densely. Query starts at the top, greedily walks to the nearest node, drops a layer, repeats until layer 0, then expands neighbors to collect top-k. Tunables: M (edges), ef_search (beam width). Complexity ~O(log N); recall usually >95% with tuned params.
When would you choose IVF over HNSW?
IVF when N is very large (100M+) and RAM is tight, or you already use Faiss/Milvus IVF-PQ pipelines. IVF needs good centroid training and nprobe tuning; recall can cliff if clusters are poor. For most RAG (<50M chunks), HNSW is the simpler default with better out-of-box recall.
How do metadata filters interact with ANN search?
Pre-filter applies predicates before/during graph traversal (Pinecone, Weaviate, SQL WHERE in pgvector) — correct for tenant ACLs. Post-filter retrieves k×N then filters in app code — risky when filters are selective; you may return fewer than k relevant hits. Interview fix: namespace per tenant or over-fetch 5×k.
What is hybrid search and when is it worth the complexity?
Combine sparse (BM25) and dense (embedding) retrieval, fuse with RRF or weighted sum, then rerank. Worth it when queries contain exact tokens (SKUs, statutes, stack traces) that embeddings smear. Weaviate ships this natively; pgvector needs FTS sidecar. Cost: 2× retrieval + fusion + rerank latency (~50–120 ms total).
Pinecone vs pgvector — how do you decide in a system design round?
Pick pgvector if: already on Postgres, <10M vectors, need transactional joins, team knows SQL ops. Pick Pinecone if: no vector ops expertise, many tenants, rapid scale, managed SLA worth cost. State assumptions: QPS, N vectors, filter selectivity, hybrid requirement. See comparison table in section 08.
What happens when you change the embedding model?
All stored vectors are invalid — different geometry and dimension. You must re-embed the full corpus and write to a new namespace/index version; blue/green cutover after recall eval. Never mix models in one index. Version tag in metadata: embed_model=text-embedding-3-small.
How do you measure if your vector index is good enough?
Build a golden query set (50–200 questions) with human-labeled relevant chunk IDs. Metrics: recall@k, MRR, nDCG. Compare ANN vs brute-force on a sample to estimate recall gap. Increase ef_search or nprobe until recall@10 ≥ 0.92, then profile p99 latency.
Why not just put everything in the LLM context window?
Cost scales with tokens; latency grows superlinearly; hallucination risk without grounded citations. Vector retrieval selects top-k relevant chunks (2–8K tokens) from millions. Long context helps for single large docs, not entire corpora. Production RAG = retrieve + cite + generate.
What is Chroma good for vs dangerous for?
Good: local dev, CI tests, demos, <500K vectors, zero infra. Dangerous in prod: no managed HA, limited multi-tenant isolation, in-process scaling limits. Graduate to pgvector or managed store before paying customers depend on retrieval SLAs.
Cosine vs L2 vs inner product — which do you use?
Use whatever the embedding model vendor documents. OpenAI text-embedding-3 recommends cosine. If vectors are L2-normalized, inner product equals cosine. Mismatch between metric and normalization degrades ranking. Set pgvector ops class accordingly (vector_cosine_ops).
